# 第三十九章 创建数据库表的脚本（DDL 建表脚本）系统学习

> 本章目标：从"会写一句 `CREATE TABLE`"升级到"**写好一份工程化的建表脚本**"——完整拆解建表脚本的每一个要素（字段类型、约束、索引、表选项），掌握主键与索引设计、公共字段模板、经典业务表模型，学会组织与管理建表脚本（初始化脚本、版本化脚本、幂等写法、从现有库导出），并对比 MySQL / PostgreSQL / Oracle 的建表语法差异。全部示例基于 **MySQL 8.0**，可在第 35 章 Docker 一键拉起的 MySQL 中直接执行。
>
> 前置知识：第三十三章 MySQL 系统学习（SQL 基础）、第二十五章 MySQL 调优（索引原理）、第三十八章 数据迁移（Flyway 版本化脚本）。

## 39.1 为什么需要专门研究"建表脚本"

第 33 章已经讲过一句基础建表语句，但真实项目中**表不是"敲出来"的，而是"写脚本管理"的**：

| 场景 | 只会基础语法的后果 | 会写工程化脚本的解法 |
| --- | --- | --- |
| 开发环境 | 打开 Navicat 手动点几下，表建好了 | 一份初始化 SQL，任何人一条命令重建 |
| 发版 | 上线前手工在测试库/生产库执行，容易漏 | 脚本进 Git + Flyway 版本化，自动执行 |
| 团队协作 | 每人手搓的表结构五花八门 | 统一的字段类型、命名、公共字段模板 |
| 排查问题 | 不知道线上表"长什么样、加了哪些索引" | `SHOW CREATE TABLE` 随时还原脚本 |
| 换数据库 | MySQL 的脚本拿到 PG 上全是语法报错 | 了解多库差异，写好可移植脚本 |

> **一句话定位**：第 33 章讲"建表语法"，第 38 章讲"迁移工具"，本章讲"**脚本本身怎么写好**"——是两者之间的技能专题。

**建表脚本要回答的三个问题**：

1. **建什么**（结构）：字段、类型、约束、索引、表选项；
2. **建多好**（质量）：命名规范、公共字段、防坑；
3. **怎么管**（工程）：初始化脚本、版本化脚本、幂等、多库差异。

## 39.2 CREATE TABLE 完整语法拆解（重点）

### 39.2.1 一份"满配"建表脚本

```sql
-- 39.2.1 一张完整的表：逐行拆解
CREATE TABLE `t_order` (                          -- 1. 表名：t_ 前缀 + 业务名，反引号包住
    `id`            BIGINT       NOT NULL         -- 2. 主键：BIGINT + 自增（小表也可 INT）
                      AUTO_INCREMENT COMMENT '主键',
    `order_no`      VARCHAR(32)  NOT NULL         -- 3. 业务单号：唯一键（外部可读）
                      COMMENT '订单号',
    `user_id`       BIGINT       NOT NULL         -- 4. 逻辑外键：只存 ID，不建 FOREIGN KEY
                      COMMENT '用户ID',
    `status`        TINYINT      NOT NULL DEFAULT 0
                      COMMENT '状态 0待支付 1已支付 2已发货 3已完成 4已取消',
    `total_amount`  DECIMAL(12,2) NOT NULL DEFAULT 0.00
                      COMMENT '订单总额（精确小数）',
    `remark`        VARCHAR(255) DEFAULT NULL COMMENT '备注',
    `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
                      COMMENT '创建时间',
    `update_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP
                      ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `deleted`       TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除 0否 1是',
    PRIMARY KEY (`id`),                           -- 5. 主键约束
    UNIQUE KEY `uk_order_no` (`order_no`),        -- 6. 唯一索引（uk_ 前缀）
    KEY `idx_user_id` (`user_id`),                -- 7. 普通索引（idx_ 前缀）
    KEY `idx_status_create` (`status`, `create_time`)  -- 8. 联合索引（列顺序有讲究）
) ENGINE=InnoDB                                    -- 9. 存储引擎（InnoDB 唯一选择）
  DEFAULT CHARSET=utf8mb4                          -- 10. 字符集（utf8mb4 必选）
  COLLATE=utf8mb4_general_ci                       -- 11. 排序规则
  COMMENT='订单表';                                -- 12. 表注释（必须有！）
```

### 39.2.2 每个要素的"为什么"（面试高频）

| 要素 | 推荐写法 | 原因 |
| --- | --- | --- |
| 表名 | `t_订单表` 或 `订单表` | `t_` 前缀与关键字区分（`t_order` 不会与 `ORDER` 冲突）；统一团队约定即可 |
| 反引号 | `` ` ` `` | 包住表名/列名，避免与保留字冲突（如 `order`、`desc`、`group`） |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` | 见 39.4.1，主键设计是建表第一决策 |
| 时间默认值 | `DEFAULT CURRENT_TIMESTAMP` | 应用层不传也会自动写；`ON UPDATE CURRENT_TIMESTAMP` 让更新自动刷新时间（**仅 MySQL 特有**） |
| 状态字段 | `TINYINT` + 注释枚举含义 | 不用字符串（'0'/'1'）也不要用 `ENUM`（改枚举要改表，不灵活） |
| 金额 | `DECIMAL(M,2)` | 浮点有精度误差，见 33.2.2 |
| 字符集 | `utf8mb4` + `utf8mb4_general_ci` | 支持 emoji/生僻字；`utf8mb4_unicode_ci` 排序更准确但略慢，两者皆可 |
| 存储引擎 | `InnoDB` | 支持事务、行级锁、崩溃恢复；MySQL 8.0 默认 |

### 39.2.3 表选项与分区

```sql
-- 表选项：字符集、排序规则、自增起点、行格式、压缩
CREATE TABLE `t_log` (
    `id`   BIGINT NOT NULL AUTO_INCREMENT,
    `msg`  TEXT,
    PRIMARY KEY (`id`)
) ENGINE=InnoDB
  AUTO_INCREMENT=10000                            -- 自增从 10000 开始
  DEFAULT CHARSET=utf8mb4
  ROW_FORMAT=DYNAMIC                              -- 8.0 默认 DYNAMIC，长字段不进数据页
  COMMENT='日志表';

-- 分区表（大日志/大流水常用，MySQL 8.0 建议用 RANGE 分区）
CREATE TABLE `t_access_log` (
    `id`        BIGINT NOT NULL AUTO_INCREMENT,
    `path`      VARCHAR(255) NOT NULL,
    `visit_time` DATETIME NOT NULL,
    PRIMARY KEY (`id`, `visit_time`)              -- 分区键必须包含在主键里！
) ENGINE=InnoDB
  PARTITION BY RANGE (YEAR(visit_time)) (         -- 按年份分区
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p2026 VALUES LESS THAN MAXVALUE
  );
```

> 分区表注意：分区键必须在主键/唯一键中（MySQL 的限制）；分区能加速"按分区裁剪"的查询与归档删除，但 5000 万以内普通表 + 索引足够，**不要一上来就分区**。

### 39.2.4 建表脚本的三个变体

```sql
-- ① IF NOT EXISTS：幂等建表（脚本可重复执行）
CREATE TABLE IF NOT EXISTS `t_user` ( ... );

-- ② 临时表：会话内使用，断开自动删除（中间结果、SQL 复杂拆解）
CREATE TEMPORARY TABLE tmp_active_user AS
SELECT id, username FROM t_user WHERE status = 1;

-- ③ 建表后立刻补注释/索引（把 DDL 拆成多条语句，便于单独管理）
CREATE TABLE `t_user` ( `id` BIGINT NOT NULL, PRIMARY KEY (`id`) ) COMMENT='用户表';
ALTER TABLE `t_user` ADD COLUMN `email` VARCHAR(64) DEFAULT NULL COMMENT '邮箱';
```

## 39.3 字段类型选型：建表脚本的核心决策

第 33 章已有类型速查表，这里给出**决策思路**（选错类型是建表脚本最常见的问题）：

### 39.3.1 类型选型速查表

| 数据类型 | 什么时候用 | 什么时候不要用 |
| --- | --- | --- |
| `INT` / `BIGINT` | 自增主键、ID、计数 | 超过 21 亿用 BIGINT（用户量/订单量很快） |
| `TINYINT` | 状态、开关、枚举值 | 别当布尔用 `BOOLEAN`（MySQL 里 BOOLEAN 就是 TINYINT(1)，语义不清） |
| `DECIMAL(M,D)` | **金额、比例、经纬度精度** | 不要用 FLOAT/DOUBLE 存钱 |
| `VARCHAR(n)` | 名字、手机号、邮箱、描述 | **n 别拍脑袋**：VARCHAR 按字符计，且 65535 字节是行上限；索引长度也受限 |
| `CHAR(n)` | 定长：身份证(18)、手机号(11)、状态码 | 变长内容用 CHAR 浪费空间 |
| `TEXT` / `MEDIUMTEXT` | 长文、JSON 字符串、富文本 | **不要在 TEXT 上建索引**（只能前缀索引）；排序/分组用 TEXT 受限 |
| `DATE` / `DATETIME` | 生日、创建/更新时间 | `DATETIME` 比 `TIMESTAMP` 推荐（见下） |
| `JSON` | MySQL 5.7+ 结构化半结构化数据 | 查询依赖 JSON 内字段时，考虑拆列 + 索引 |
| `BLOB` | 二进制文件 | **文件别存库**：存 OSS/对象存储路径即可 |

### 39.3.2 两个最容易踩的坑

**坑 1：DATETIME vs TIMESTAMP（MySQL 面试经典）**

| 维度 | DATETIME | TIMESTAMP |
| --- | --- | --- |
| 存储 | 8 字节 | 4 字节 |
| 范围 | 1000-01-01 ~ 9999-12-31 | 1970 ~ 2038（2038 年问题） |
| 时区 | 不随会话时区变 | **随会话时区变**（存 UTC 转本地） |
| 默认值 | MySQL 5.6.5+ 可用 CURRENT_TIMESTAMP | 可用 CURRENT_TIMESTAMP |

> **结论**：业务表用 `DATETIME`（范围大、不受时区惊吓、符合"存进去是什么就是什么"）；跨时区分布式系统再考虑 TIMESTAMP 或统一存 UTC。**面试答"为什么用 DATETIME 不用 TIMESTAMP"**：范围、8 字节 vs 4 字节、时区影响。

**坑 2：VARCHAR 长度的"隐藏成本"**

```sql
-- ❌ 常见反面：长度随手写，索引放不下
CREATE TABLE t_user (
    name VARCHAR(200),          -- 一个名字用 200？索引最大 767 字节（或 3072 按版本）
    UNIQUE KEY uk_name (name)   -- utf8mb4 下 200 字符 = 800 字节 → 超索引长度限制报错！
);

-- ✅ 正确：按真实业务上限定长度
CREATE TABLE t_user (
    name VARCHAR(50) NOT NULL COMMENT '姓名',
    UNIQUE KEY uk_name (name)   -- 50 字符 × 4 字节 = 200 字节，安全
);
```

> 长度规则：**满足业务上限 + 留一点余量**即可。手机号 `VARCHAR(20)`（留国际区号）、姓名 `VARCHAR(50)`、邮箱 `VARCHAR(128)`、URL `VARCHAR(500)`。越长 = 越占内存排序空间 + 索引越小能建的越少。

## 39.4 主键与索引：建表脚本的"设计含量"

### 39.4.1 主键三选一（面试必问）

| 方案 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| **自增 BIGINT** | 简单、插入快（顺序写）、索引紧凑 | 可被爬取、分库分表后冲突、迁移麻烦 | 中小型单库表（**默认首选**） |
| **雪花 ID / 分布式 ID** | 全局唯一、趋势递增、不暴露规律 | 需要 ID 生成器（Redis/号段/雪花算法） | 分库分表、跨库关联 |
| **UUID** | 生成简单、全局唯一 | **随机无序** → 主键索引频繁页分裂，插入性能差、索引膨胀 | 基本不用（可用有序 UUID 替代） |

```sql
-- 自增主键（单库默认）
CREATE TABLE `t_user` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
    ...
    PRIMARY KEY (`id`)
) ENGINE=InnoDB COMMENT='用户表';

-- 分布式表：业务主键为雪花 ID，自增列仅作辅助
CREATE TABLE `t_order` (
    `id`         BIGINT NOT NULL COMMENT '订单ID（雪花算法生成）',
    `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (`id`)
) ENGINE=InnoDB COMMENT='订单表（分布式ID）';
```

> **InnoDB 聚簇索引**：主键即数据组织方式，**主键必须是"趋势递增"**（自增/雪花），随机 UUID 会让 B+Tree 频繁页分裂。这是"为什么不用 UUID 做主键"的根因。

### 39.4.2 唯一键：业务唯一性的第一道防线

```sql
CREATE TABLE `t_user` (
    `id`       BIGINT NOT NULL AUTO_INCREMENT,
    `username` VARCHAR(50) NOT NULL COMMENT '用户名',
    `email`    VARCHAR(128) DEFAULT NULL COMMENT '邮箱',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_username` (`username`),          -- 用户名唯一
    UNIQUE KEY `uk_email` (`email`)                 -- 邮箱唯一（注意 NULL：MySQL 允许多个 NULL！）
) ENGINE=InnoDB COMMENT='用户表';
```

> **易错点**：MySQL 的 UNIQUE 索引对 `NULL` 不生效（多个 NULL 互不冲突）。所以"业务上必须唯一"的字段要 `NOT NULL`（如 username），可空的 email 用唯一索引只能拦重复值、拦不住多个 NULL。

### 39.4.3 联合索引列顺序（建表时就该定好）

第 25 章讲最左前缀，这里给**建表时怎么排**的结论：

```sql
-- 业务查询：按 status 过滤 + create_time 排序分页（高频）
KEY `idx_status_create` (`status`, `create_time`)
-- ✅ 选择性高的放前面：status（区分度低但常用于过滤+后续排序，仍可放前）

-- 反例：把高区分度列放前面
KEY `idx_user_status` (`user_id`, `status`)
-- 如果高频查询是 WHERE status=? ORDER BY create_time，这个索引完全用不上！
```

| 原则 | 说明 |
| --- | --- |
| 写进脚本的索引 = 给查询设计的 | 先看业务 SQL（WHERE + ORDER BY + GROUP BY），再定索引 |
| 最左前缀 | `(a, b, c)` 能覆盖 `a`、`a,b`、`a,b,c` 三种查询 |
| 排序友好 | `WHERE a=? ORDER BY b` → 索引 `(a,b)` 直接有序 |
| 覆盖索引 | 查询列都在索引里 → 不回表（`(status, create_time)` 覆盖"按状态统计"） |
| 索引不是越多越好 | 每个索引都占空间 + 拖慢写入（INSERT/UPDATE 要同步维护），冗余索引（如已有 `(a,b)` 再建 `(a)`）要删 |
| 区分度 | 索引列的选择性 = COUNT(DISTINCT col)/COUNT(*)；性别/状态这种低区分度列单独建索引收益低，一般放联合索引里 |

### 39.4.4 索引命名与类型速查

```sql
PRIMARY KEY (`id`),                      -- 主键
UNIQUE KEY `uk_xxx` (`col`),             -- 唯一索引（uk_ 前缀）
KEY `idx_xxx` (`col`),                   -- 普通索引（idx_ 前缀）
KEY `idx_a_b` (`a`, `b`),                -- 联合索引（列名_列名）
FULLTEXT KEY `ft_title` (`title`),       -- 全文索引（中文需分词器，生产用 ES）
SPATIAL KEY `sp_pos` (`pos`)             -- 空间索引（地理坐标，少用）
```

> 命名规范统一为 `uk_`/`idx_`/`ft_` + 列名组合，靠名字就能读懂的索引。

## 39.5 公共字段与表设计规范（团队模板）

### 39.5.1 公共字段模板（几乎所有业务表都带）

```sql
-- 三个"基础设施字段"：时间戳 + 逻辑删除 + 版本号
`create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
`update_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
              ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
`deleted`     TINYINT  NOT NULL DEFAULT 0 COMMENT '逻辑删除 0否 1是',
-- 可选：乐观锁版本号（配合 MyBatis-Plus @Version 用，见 17 章）
`version`     INT      NOT NULL DEFAULT 0 COMMENT '乐观锁版本号'
```

**为什么用逻辑删除（deleted）而不是 DELETE**：可恢复、可审计、不影响历史关联数据。代价是**所有查询都要带 `deleted=0` 条件**，且唯一索引要小心（被删行的唯一值占坑）——方案：唯一索引列同时包含 deleted，或用"删除时改唯一字段"（如 username 删了改成 `username_del_{id}`）。

> **唯一索引 + 逻辑删除的经典坑**：`uk_username` 唯一，用户删了（deleted=1），再注册同名 → 唯一冲突。解决：唯一索引 `(username, deleted)`，或删除时改写 username。**这是面试加分点**。

### 39.5.2 命名与设计规范清单

| 规范 | 示例 | 反例 |
| --- | --- | --- |
| 表名：模块前缀 + 复数或单数业务名（团队统一） | `t_user`、`t_order`、`sys_dict` | `userinfo`、`OrderTable`（大小写混） |
| 列名：小写下划线 | `create_time` | `createTime`、`CreateTime` |
| 字段语义清晰，不用拼音缩写 | `phone`、`email` | `sjh`（手机号拼音）、`bm` |
| 状态/类型字段加枚举注释 | `status TINYINT COMMENT '0待支付 1已支付'` | `status INT` 无注释 |
| 布尔用 TINYINT(1)，语义如 `is_deleted` | `is_deleted TINYINT(1)` | `flag INT` |
| 表与每列都写 COMMENT | `COMMENT='订单表'`、`COMMENT '订单号'` | 裸表无注释，过三个月没人看得懂 |
| 金额列名带单位语义 | `total_amount DECIMAL(12,2)` | `price DOUBLE` |
| 时间统一 DATETIME | `create_time` | 有的表 DATE、有的 TIMESTAMP |
| 删除/禁用用 TINYINT 枚举 | `status 0正常 1禁用` | `is_delete` 与 `status` 混用 |
| 逻辑外键不加 FOREIGN KEY 约束 | `user_id BIGINT` | `FOREIGN KEY (user_id) REFERENCES t_user(id)` |

> **为什么生产不加外键约束**：外键强制一致性在写入时带来锁与校验开销，分布式/微服务分库后根本无法跨库引用；一致性由应用层（事务、状态机）保证。**面试常问**。

### 39.5.3 表设计自查清单（写脚本前过一遍）

```
□ 表名/列名符合团队命名规范，且不是保留字
□ 每列都有类型 + 注释，枚举字段注释里写全枚举含义
□ 主键是趋势递增（自增/雪花），不是 UUID 乱序
□ 金额用 DECIMAL，不用 FLOAT/DOUBLE
□ 必填字段 NOT NULL，可空字段显式 DEFAULT NULL
□ 字符串长度按业务上限，不随手 255/500
□ 有 create_time / update_time 默认值
□ 需要逻辑删除的表有 deleted 字段（且唯一索引已规避占坑）
□ 索引按真实查询设计，无冗余、无重复前缀
□ 字符集 utf8mb4，引擎 InnoDB，表和列都有 COMMENT
□ 数值范围：主键 BIGINT 还是 INT？状态 TINYINT 够不够？
```

## 39.6 经典业务表模型（可直接套用的模板）

### 39.6.1 用户表 + 扩展表（1:1 拆分）

```sql
-- 主表：高频、小字段
CREATE TABLE `t_user` (
    `id`          BIGINT       NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    `username`    VARCHAR(50)  NOT NULL COMMENT '用户名',
    `password`    VARCHAR(128) NOT NULL COMMENT '密码（BCrypt 密文）',
    `phone`       VARCHAR(20)  DEFAULT NULL COMMENT '手机号',
    `email`       VARCHAR(128) DEFAULT NULL COMMENT '邮箱',
    `status`      TINYINT      NOT NULL DEFAULT 1 COMMENT '状态 1正常 0禁用',
    `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `update_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `deleted`     TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除 0否 1是',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_username` (`username`),
    KEY `idx_phone` (`phone`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

-- 扩展表：低频、大字段，1:1 用相同主键
CREATE TABLE `t_user_profile` (
    `user_id`     BIGINT       NOT NULL COMMENT '用户ID（同主键）',
    `avatar_url`  VARCHAR(500) DEFAULT NULL COMMENT '头像地址',
    `bio`         VARCHAR(255) DEFAULT NULL COMMENT '个人简介',
    `birthday`    DATE         DEFAULT NULL COMMENT '生日',
    `create_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    `update_time` DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户扩展信息表';
```

> **1:1 拆分理由**：主表行短 → 页能装更多行 → 查询快；低频大字段不拖累高频查询；行宽超过 16KB 会触发行溢出。

## 39.7 脚本的组织与版本管理（工程化）

### 39.7.1 三种脚本的分工

| 脚本类型 | 命名/目录 | 何时执行 | 注意 |
| --- | --- | --- | --- |
| 建库脚本 | `01-init-schema.sql`（先建库再建表） | 环境初始化一次 | 全量、可重跑（IF NOT EXISTS） |
| 初始化数据脚本 | `02-init-data.sql` | 环境初始化 | 幂等（见下） |
| 版本化变更脚本 | `V1__xx.sql` / `V2__xx.sql` | 每次发版 | 交给 Flyway（38 章），**只增不改** |

```sql
-- 01-init-schema.sql：先建库
CREATE DATABASE IF NOT EXISTS `mall` DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
USE `mall`;

-- 建表：所有表按依赖顺序（先父表后子表，虽然 MySQL 无外键也建议有序）
CREATE TABLE IF NOT EXISTS `t_user` ( ... );
CREATE TABLE IF NOT EXISTS `t_order` ( ... );
```

> 为什么"先建库"要单独成行：**新建环境一键执行**；不同环境（dev/test/prod）库名可配置化（`mall_dev`/`mall_test`/`mall`），脚本里用占位符或仅 dev 直写。

### 39.7.2 幂等写法（脚本可安全重复执行）

```sql
-- 建表幂等
CREATE TABLE IF NOT EXISTS `t_user` ( ... );

-- 加列幂等（MySQL 8.0 不支持 ALTER ... IF EXISTS，用存储过程或先查后加）
SET @col_exists = (
    SELECT COUNT(*) FROM information_schema.COLUMNS
    WHERE TABLE_SCHEMA = 'mall' AND TABLE_NAME = 't_user' AND COLUMN_NAME = 'email'
);
SET @ddl = IF(@col_exists = 0,
    'ALTER TABLE `t_user` ADD COLUMN `email` VARCHAR(128) DEFAULT NULL COMMENT ''邮箱''',
    'SELECT 1');
PREPARE stmt FROM @ddl; EXECUTE stmt; DEALLOCATE PREPARE stmt;

-- 索引幂等（先查后建）
SET @idx_exists = (
    SELECT COUNT(*) FROM information_schema.STATISTICS
    WHERE TABLE_SCHEMA = 'mall' AND TABLE_NAME = 't_user' AND INDEX_NAME = 'idx_phone'
);
SET @ddl = IF(@idx_exists = 0, 'ALTER TABLE `t_user` ADD KEY `idx_phone` (`phone`)', 'SELECT 1');
PREPARE stmt FROM @ddl; EXECUTE stmt; DEALLOCATE PREPARE stmt;
```

> 生产大表**加列/加索引要评估锁**：`ALTER TABLE` 会锁表（MySQL 8.0 的 INSTANT 算法只对部分加列免锁），大表用影子表/pt-osc/gh-ost（见 38.5.2）。

### 39.7.3 从现有库导出建表脚本（日常高频技能）

```sql
-- ① 查看完整建表语句（最常用！还原任意表）
SHOW CREATE TABLE `t_order`\G

-- ② 命令行导出全部表结构（不含数据）
mysqldump -uroot -p --no-data --single-transaction mall > schema_only.sql

-- ③ 命令行导出部分表
mysqldump -uroot -p --no-data mall t_user t_order > user_order_schema.sql

-- ④ Navicat / MySQL Workbench：反向数据库 → 生成 SQL 文件
```

> `SHOW CREATE TABLE` 是最快的"看线上表长什么样"的方式；`mysqldump --no-data` 用于环境复制与备份结构。

## 39.8 多数据库建表差异（可移植性）

同一张"用户表"，三种数据库的写法对比：

```sql
-- MySQL 8.0
CREATE TABLE t_user (
    id       BIGINT       NOT NULL AUTO_INCREMENT,
    username VARCHAR(50)  NOT NULL,
    status   TINYINT      NOT NULL DEFAULT 1,
    remark   VARCHAR(255) DEFAULT NULL,
    PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

-- PostgreSQL 15（序列 + 标识列）
CREATE TABLE t_user (
    id       BIGINT       GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- 自增
    username VARCHAR(50)  NOT NULL,
    status   SMALLINT     NOT NULL DEFAULT 1,
    remark   VARCHAR(255),                                           -- 默认可空，不需要 DEFAULT NULL
    create_time TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_user_username UNIQUE (username)
);
COMMENT ON TABLE t_user IS '用户表';
COMMENT ON COLUMN t_user.remark IS '备注';

-- Oracle 19c（Oracle 12c+ 才有 IDENTITY）
CREATE TABLE t_user (
    id       NUMBER(20)    GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    username VARCHAR2(50)  NOT NULL,
    status   NUMBER(1)     DEFAULT 1 NOT NULL,
    remark   VARCHAR2(255)
);
COMMENT ON TABLE t_user IS '用户表';
```

| 差异点 | MySQL | PostgreSQL | Oracle |
| --- | --- | --- | --- |
| 自增 | `AUTO_INCREMENT` | `GENERATED ALWAYS AS IDENTITY` / `SERIAL` | `GENERATED ALWAYS AS IDENTITY` / 序列 |
| 变长字符串 | `VARCHAR(n)` | `VARCHAR(n)` | `VARCHAR2(n)` |
| 布尔 | `TINYINT(1)` | `BOOLEAN`（原生） | `NUMBER(1)` |
| 注释 | `COMMENT 'xxx'`（列内联/表尾） | `COMMENT ON TABLE/COLUMN` | `COMMENT ON TABLE/COLUMN` |
| 时间默认值 | `CURRENT_TIMESTAMP` + `ON UPDATE` | `CURRENT_TIMESTAMP` | `DEFAULT SYSDATE` |
| 保留字 | `order`、`group` 需反引号 | 需双引号 | 需双引号 |
| 大小写 | 表名列名 Linux 下区分大小写 | 默认折叠为小写 | 默认折叠为大写 |

> **可移植策略**：① 团队定"最小公共方言"（类型用 VARCHAR/INT/DECIMAL/DATETIME 这类通用词）；② 保留字规避（表名加前缀 `t_` 基本不会撞）；③ 注释与自增语法差异交给 ORM/迁移工具层（MyBatis 的 Schema 生成、Flyway 多目录、Liquibase 的多数据库支持）。**生产场景：选一种数据库深耕，脚本为它优化，不要追求"一份脚本跑所有库"。**

## 39.9 常见坑与自查清单

### 39.9.1 高频坑汇总

| 坑 | 表现 | 规避 |
| --- | --- | --- |
| 字段名撞保留字 | `create`、`order`、`desc`、`group` 直接报语法错 | 反引号包住 or 改名（`order_no`、`create_time`） |
| 字符串长度随手写 | 索引超 767/3072 字节建不了；行超 65535 字节 | 按业务定长（39.3.2） |
| FLOAT 存金额 | 对账差 0.01 | 一律 DECIMAL |
| 自增 INT 撑爆 | 21 亿后报 `Out of range` | 用户/订单/流水主键直接 BIGINT |
| 无默认值 NOT NULL | 应用漏传字段报错、批量插入报错 | 能给默认值就给（0 / '' / CURRENT_TIMESTAMP） |
| 没有表注释/列注释 | 三个月后没人知道字段含义 | 建表必带 COMMENT |
| 忘了 utf8mb4 | emoji 存不进去报 `Incorrect string value` | 建库建表统一 utf8mb4 |
| UUID 主键 | 插入慢、碎片多、主键索引膨胀 | 自增/雪花（39.4.1） |
| 冗余索引 | `KEY(a)` 与 `KEY(a,b)` 并存，浪费写开销 | 用 `(a,b)` 覆盖，删 `(a)` |
| 逻辑删除 + 唯一索引 | 删除后再注册同用户名冲突 | `(username, deleted)` 联合唯一 / 删除时改写唯一字段 |
| 多个 NULL 违反唯一直觉 | `UNIQUE` 拦不住多个 NULL | 必须唯一的字段设 NOT NULL |
| DDL 隐式提交 | 建表脚本中间失败，已执行部分不自动回滚 | 脚本拆分 + 幂等写法 + 失败后修复重跑 |

### 39.9.2 提交代码前的最终自查（Checklist）

```
□ 脚本能重复执行（IF NOT EXISTS / 先查后建），不因"再跑一遍"报错
□ 编码 UTF-8（Windows 记事本别存 ANSI，中文注释乱码）
□ 用 SHOW CREATE TABLE 复核一次实际建出来的表
□ 建表顺序：先建库 → 父表/主表 → 子表/明细表 → 中间表 → 初始化数据
□ 索引与业务查询对齐，无冗余
□ 唯一键考虑 NULL 与逻辑删除场景
□ 金额 DECIMAL、时间 DATETIME、状态 TINYINT + 注释
□ 生产大表变更用增量脚本 + 在线工具，不直接 ALTER 锁表
```

### 面试高频问题清单

| 问题 | 答案要点 |
| --- | --- |
| 建表脚本的完整要素有哪些？ | 字段定义（类型/默认值/注释）、主键、唯一键、普通/联合索引、ENGINE、CHARSET、COLLATE、COMMENT |
| 为什么主键推荐自增 BIGINT？ | InnoDB 聚簇索引按主键组织，趋势递增避免页分裂；UUID 乱序导致写放大 |
| 自增主键的缺点？分库分表怎么办？ | 可被爬取、单库自增冲突；用雪花/号段等分布式 ID |
| DATETIME 与 TIMESTAMP 区别？ | 存储 8/4 字节、范围、是否随时区变、2038 问题 |
| 金额字段为什么用 DECIMAL？ | 浮点二进制无法精确表示十进制小数 |
| 为什么不加外键？ | 锁与校验开销、分库后无法跨库引用、一致性交给应用层 |
| 为什么不用 ENUM 存状态？ | 修改枚举需 ALTER TABLE，扩展不灵活；用 TINYINT + 注释 |
| 逻辑删除和唯一索引冲突怎么解决？ | 联合唯一 (业务字段, deleted) 或删除时改写唯一字段 |
| 联合索引列顺序怎么定？ | 最左前缀：等值条件列放前，其次排序列，覆盖索引可回表优化 |
| VARCHAR 长度怎么定？ | 按业务上限 + 余量；影响索引长度（utf8mb4 一字符 4 字节） |
| 如何幂等建表/加列？ | IF NOT EXISTS；加列先查 information_schema 再执行；或交给 Flyway |
| MySQL/PostgreSQL/Oracle 建表差异？ | 自增、注释、布尔、VARCHAR2、时间默认值语法不同（39.8） |
| 如何查看线上表的建表脚本？ | SHOW CREATE TABLE；mysqldump --no-data 导出全库 |

### 本章小结

- **建表脚本的定位**（39.1）：从"语法"到"工程化"，回答建什么 / 建多好 / 怎么管；
