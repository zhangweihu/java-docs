## 48.1 可观测性三支柱：出了问题"看得见"

### 48.1.1 为什么需要"三支柱"

第 47 章保证了"扛得住、不会挂"，但**挂了怎么快速定位**？微服务几十个实例，报错只在一个实例上——没有可观测性，等于在黑暗里修飞机。

可观测性三支柱（Observability）：

| 支柱 | 回答的问题 | 数据形态 | 典型工具 |
| --- | --- | --- | --- |
| **日志（Logs）** | 具体发生了什么（细节） | 结构化文本，含时间/级别/追踪 ID | ELK、Loki、SkyWalking 日志 |
| **指标（Metrics）** | 整体健康度（趋势/告警） | 数值序列：QPS、RT、错误率、GC | Prometheus + Grafana、Micrometer |
| **链路追踪（Traces）** | 一次请求经过了哪些服务（关联） | 调用树：span、traceId | SkyWalking、Zipkin、Jaeger、OpenTelemetry |

> **一句话记忆**：指标告诉你"出事了"，日志告诉你"出了什么事"，链路告诉你"事出在哪一环"。三者用**traceId 串起来**才是完整的。

### 48.1.2 traceId：三支柱的"粘合剂"

```
用户请求 ──► 网关生成 traceId（如 8a9f...）──► 透传到所有下游（Header）

日志：   {traceId: 8a9f..., level: ERROR, msg: "库存不足", service: order-service}
指标：   {traceId 关联的 RT/错误率聚合}
链路：   [gateway 5ms] → [order 120ms] → [inventory 300ms] ✗ ← 瓶颈在这
```

- **透传方式**：HTTP Header（`X-Trace-Id`）、MQ 消息属性、Dubbo/Feign 拦截器自动注入；
- **Java 侧**：MDC（Mapped Diagnostic Context）把 traceId 放进日志上下文（第 11 章），线程池要传递（TaskDecorator 复制 MDC）。

## 48.2 日志体系：规范与聚合

### 48.2.1 日志规范（错误日志可被快速检索）

| 规范 | 示例 |
| --- | --- |
| 结构化（JSON） | `{"time":...,"level":"ERROR","traceId":"...","service":"order","msg":"..."}` |
| 必带上下文 | 订单号/用户 id/参数摘要（定位必备） |
| 分级正确 | ERROR=系统异常；WARN=可恢复（重试）；INFO=关键业务节点；DEBUG=禁上生产 |
| 不记敏感信息 | 密码/身份证/银行卡必须脱敏 |
| 统一格式 | 时间 | traceId | 级别 | 服务 | 类名:行号 | 消息 |

### 48.2.2 日志聚合链路（ELK/Loki）

```
应用实例（logback 输出 JSON 日志）
   │ Filebeat / Promtail（轻量采集）
   ▼
Logstash / Loki（聚合、解析）
   │
   ▼
Elasticsearch / Loki（存储 + 索引）
   │
   ▼
Kibana / Grafana（检索 UI：按 traceId/订单号/服务名过滤）
```

> 第 20 章 ELK 已讲实现，本章补充**运维规范**：日志保留周期（热 7 天/温 30 天/冷归档）、磁盘水位告警、大日志（单条 > 10KB）单独处理。

## 48.3 指标监控：Prometheus + Grafana

### 48.3.1 指标四类（RED/USE 方法论）

| 方法 | 指标 | 含义 |
| --- | --- | --- |
| **RED**（服务视角） | Rate / Errors / Duration | QPS、错误率、RT |
| **USE**（资源视角） | Utilization / Saturation / Errors | CPU 使用率、等待队列、IO 错误 |

```
应用指标（Spring Boot Actuator + Micrometer 暴露 /actuator/prometheus）
   │ Prometheus 定时拉取（服务发现：K8s Pod / 注册中心）
   ▼
Prometheus（时序存储 + 告警规则）
   │
   ▼
Grafana（可视化大盘）+ Alertmanager（告警通知：钉钉/短信/电话）
```

### 48.3.2 必须盯的黄金指标（业务 + 技术）

| 类别 | 指标 | 告警阈值（示例） |
| --- | --- | --- |
| 业务 | 下单接口 QPS / 成功率 / 超时率 | 成功率 < 99.5% 告警 |
| 应用 | JVM：GC 次数/耗时、堆使用率 | Full GC 连续 > 3 次告警（第 24 章） |
| 应用 | 线程池活跃度、连接池使用率 | 连接池 > 80% 告警 |
| 基础设施 | CPU / 内存 / 磁盘 / 网络 | CPU > 85% 持续 5 分钟 |
| 中间件 | Redis 命中率/内存、MySQL 慢查询数、MQ 堆积 | 慢查询 > 100 条/分 |

> **告警不是越多越好**：告警噪音是"狼来了"——太多假警报会导致真警报没人看。**先做告警收敛（去重/聚合/分级），再做告警升级**。

## 48.4 链路追踪：SkyWalking / OpenTelemetry

### 48.4.1 核心概念

```
Trace（一次请求）           = 由多个 Span 组成
├─ Span：order 服务查询订单库    parent = gateway
├─ Span：inventory 服务扣库存    parent = order（RT 最高 → 瓶颈）
└─ Span：account 服务扣款        parent = order
```

- **traceId**：贯穿整个调用的唯一 id（48.1.2）；
- **spanId / parentSpanId**：父子关系，构成调用树；
- **SkyWalking**（第 30/32 章已用）：Java Agent 无侵入埋点（`-javaagent:skywalking-agent.jar`），自动采集 HTTP/DB/MQ 调用，UI 展示拓扑图、慢调用、错误链路。

### 48.4.2 排查实战（结合三支柱）

```
现象：下单接口 TP99 从 200ms 飙到 2s
① 指标：看下单 QPS/RT 曲线 → 确认 14:00 起恶化
② 链路：SkyWalking 找到慢 trace → inventory 扣库存 span 占 1.8s
③ 日志：按 traceId 查 inventory 日志 → "DB 连接池获取超时"
④ 根因：连接池被打满（慢 SQL 占着连接）→ 第 25 章 SQL 优化
```

> 这就是企业级排障标准动作：**指标定位 → 链路定位 → 日志定位 → 根因修复**。三支柱缺一个，这个流程都走不通。

## 48.5 发布与变更：稳定性的最大杀手也是最大机会

> 统计表明**变更（发布/配置/扩容）是线上故障的第一大来源**（约 40%+）。所以稳定性保障的核心战场在"变更"。

### 48.5.1 三种发布策略对比

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **蓝绿部署** | 两套环境切换（旧=蓝、新=绿，切流量） | 回滚瞬间完成 | 资源翻倍 |
| **金丝雀（灰度）** | 新版本先接 1%/5% 流量，验证再全量 | 风险可控、渐进 | 多版本共存复杂 |
| **滚动更新** | 逐批替换实例（K8s 默认） | 资源省 | 新旧共存期间兼容性要求高 |

### 48.5.2 灰度发布落地要点

```
灰度发布（企业标配）：
① 小流量：1% 用户/实例接新版 ──► 观察指标（错误率、RT）
② 放大：5% → 20% → 50%（每级观察 10~30 分钟）
③ 全量：指标稳定才全量
④ 回滚：任何一级异常 ──► 一键回滚上一版本（回滚预案先写好）
```

配套能力：**版本兼容**（新旧版本并存期间 API/DB schema 都要兼容——第 38 章迁移脚本 + 第 43 章事件版本策略是基础设施）、**配置中心**（Nacos，第 37 章：开关即配置，改配置不下线）。

## 48.6 稳定性保障：SRE 与混沌工程

### 48.6.1 SRE 与 SLO/SLI

**SRE**（Site Reliability Engineering）：用软件工程方法做运维。核心是**用数字定义稳定性**：

```
SLI（指标）：真实测量的值，如"下单成功率"、"接口 95 分位 RT < 300ms"
SLO（目标）：承诺的目标，如"下单成功率 ≥ 99.9%"、"月可用性 ≥ 99.95%"
错误预算：1 - SLO（如 0.05% 的故障时间是"预算"），
         超预算 → 冻结新功能、专注稳定性（用钱买创新空间）
```

> **SLO 的意义**：把"稳定性"从口号变成**可度量、可问责、可决策**的数字。第 47 章的 RPO/RTO 与这里的 SLO 是配套的（一个是容灾目标、一个是服务目标）。

### 48.6.2 混沌工程（Chaos Engineering）

**主动制造故障，验证系统"会不会挂、能不能自动恢复"**：

```
原则：
  ① 先定义"稳态"（正常指标基线）
  ② 假设（"杀一个 Pod 不影响可用性"）
  ③ 小范围制造故障：杀 Pod / 断网 / 注入延迟 / CPU 打满（ChaosBlade/Litmus）
  ④ 观察指标是否回归稳态，验证自动恢复
  ⑤ 范围逐渐放大（生产前先在测试/灰度环境）

常用故障注入（ChaosBlade，阿里开源）：
  blade create kill process --process java        # 杀应用进程
  blade create delay --time 3000 --percent 50     # 注入 3s 延迟
  blade create cpu fullload --cpu-count 2          # CPU 打满
```

> **与 47.4.4 故障演练的关系**：故障演练是"走一遍预案"，混沌工程是"持续、自动化、随机"地验证系统韧性——后者是前者的工程化升级。

### 48.6.3 稳定性保障全景（一图）

```
事前：容量规划（47.5）+ 压测 + 架构设计（冗余/多活）+ 混沌演练
事中：可观测（指标/日志/链路）+ 告警 + 限流熔断降级（47.3.4）+ 应急预案
事后：复盘（根因分析、改进项、跟进闭环）+ 错误预算治理
```

## 48.7 架构治理：让系统"可持续演进"

### 48.7.1 治理对象与手段

| 治理对象 | 问题 | 手段 |
| --- | --- | --- |
| **API 治理** | 接口随意变、没人知道谁在调 | API 文档（OpenAPI）、版本策略（/v1/v2）、兼容性测试 |
| **配置治理** | 配置散落、改错全挂 | 配置中心（Nacos）统一管理 + 灰度推送 + 审计 |
| **依赖治理** | 依赖冲突、漏洞、升级难 | 依赖清单（SBOM）、升级看板、安全扫描（OWASP） |
| **数据治理** | 表结构混乱、口径不一 | 第 38 章迁移规范、字段字典、口径文档 |
| **代码治理** | 重复代码、坏味道（第 28 章） | 架构评审、SonarQube 扫描、约束性架构测试 |
| **技术债务** | 债越欠越多 | 债务清单 + 预算制度（每次迭代还一点） |

### 48.7.2 演进式架构：允许变化的结构

**演进式架构**（Evolutionary Architecture）：架构设计时**把"怎么改"也设计进去**——可替换组件、可演进接口、增量迁移（绞杀者模式：新功能走新架构，老功能逐步迁移，第 32 章 mall-boot→mall-cloud 就是绞杀者迁移）。

```
绞杀者模式（Strangler）：
  老系统（单体）       新系统（微服务）
  /api/order  ──► 网关 ──► 逐步迁移到 order-service（新请求走新架构）
  /api/other  ──► 先留在老系统，后续逐个绞杀替换
```

> **一句话**：好的企业级架构不是"一步到位"，而是"**每一步都留着下一步的路**"。

到此，Java 体系 48 章全部完成。把企业级架构串成一条线：

```

找得到吗？      日志/指标/链路三支柱（48）
敢变更吗？      灰度发布 + SLO/混沌 + 架构治理（48）

┌──────────────────────── 企业级架构能力金字塔 ────────────────────────┐
│             ⑯ 可观测 + ⑰ 稳定性（48）——看得见、敢变更                  │
│           ⑮ 高并发 + 高可用（47）——扛得住、不会挂                      │
│     ⑭ 分布式事务/Saga（46）——跨服务一致性                            │
│ ⑫ Axon（45）/⑬ CQRS+ES（43）/⑪ 状态机（42）——事件驱动与流程工程化      │

```
