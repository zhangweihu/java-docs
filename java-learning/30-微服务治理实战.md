# 第三十章 微服务治理实战（从能跑到能扛）

> 第十五章学会了 Spring Cloud 全家桶的"用法"，本章回答"**线上怎么管理几十上百个服务**"：注册发现、配置中心、网关治理、熔断限流、分布式事务、可观测性、稳定性与安全。**这是一章"架构师视角"的实战课。**

## 30.1 什么是微服务治理

微服务不是把服务拆开就完事。拆开后你立刻面临：

- 服务间怎么找到彼此？（**注册发现**）
- 配置改了怎么不重启就生效？（**配置中心**）
- 请求从哪里进？怎么统一鉴权限流？（**网关治理**）
- 一个服务挂了，怎么不拖垮整个链路？（**熔断降级**）
- 跨服务的数据一致性怎么保证？（**分布式事务**）
- 出了问题怎么快速定位？（**可观测性**）

**微服务治理 = 把这些问题全部体系化解决**。本章沿用第十五章的 Nacos + OpenFeign + Gateway + Sentinel 技术栈，但聚焦"治理"而非"入门"。

### 30.1.1 治理全景图

```
                    ┌────────────── 流量治理 ──────────────┐
                    │  路由 / 鉴权 / 限流 / 熔断 / 降级 / 灰度    │
                    └─────────────────────────────────────┘
┌───────────┐   ┌───────────────────────────────────────┐   ┌───────────┐
│ 用户/入口    │──►│       微服务集群（几十上百个实例）             │──►│  数据层     │
└───────────┘   └───────────────────────────────────────┘   └───────────┘
                    │         │          │         │
              ┌─────▼──┐ ┌───▼────┐ ┌───▼────┐ ┌──▼──────┐
              │ 注册发现  │ │ 配置中心 │ │ 链路追踪 │ │ 监控告警  │
              └────────┘ └────────┘ └────────┘ └─────────┘
```

**治理六大主题**：注册发现、配置管理、流量治理、数据一致性、可观测性、安全与稳定性。

## 30.2 服务注册与发现（Nacos 深度）

### 30.2.1 注册中心原理

```
                 ┌─────────────────┐
                 │     Nacos        │
                 │  服务注册表(内存)   │
                 └─────────────────┘
                       ▲ 注册/心跳        ▲ 拉取/订阅
        ┌──────────────┴──┐       ┌──────┴──────────────┐
        │ 服务提供者 (实例A/B/C) │       │ 服务消费者            │
        └─────────────────┘       └─────────────────────┘
```

1. 提供者启动 → 向 Nacos **注册**（服务名、IP、端口、权重）
2. 提供者每 5 秒发**心跳**续约；Nacos 超过 15 秒没收到心跳标记不健康，30 秒剔除
3. 消费者从 Nacos **拉取**服务列表（默认 10 秒轮询），本地缓存
4. 服务列表变化 → Nacos **推送**变更给消费者（UDP）

**面试高频**：Nacos 是 AP 还是 CP？——**服务发现是 AP（最终一致，可用性优先）**，注册表用临时实例（客户端心跳）；配置管理走 CP（分布式一致性）。

### 30.2.2 优雅上下线（治理的关键细节）

**普通下线的问题**：实例直接 kill，但消费者的本地缓存里还留着它 → 请求打到死实例 → 报错。

```
✅ 优雅下线流程：
1. 实例调用 Nacos deregister（主动摘除）
2. 等待消费者感知（最多 10 秒轮询）
3. 停止接收新请求（网关下线）
4. 处理完存量请求后退出（Spring 的 @PreDestroy 钩子）
```

```java
@PreDestroy
public void gracefulShutdown() {
    log.info("开始优雅下线");
    // 1. 主动注销（Nacos 客户端自动做）
    // 2. 等待 10s 让消费者刷新
    try { Thread.sleep(10_000); } catch (InterruptedException e) { }
    log.info("优雅下线完成");
}
```

**生产建议**：用 K8s 的 `preStop` 钩子 + Nacos 权重归零（`nacos: weight 0`），双保险。

### 30.2.3 负载均衡策略选择

| 策略 | 说明 | 适用 |
| --- | --- | --- |
| 轮询（RoundRobin） | 默认，依次分发 | 实例配置均匀 |
| 随机（Random） | 随机选择 | 均匀性要求低 |
| 权重 | 按实例权重分发 | 新机器少给流量（灰度观察） |
| 最少活跃调用（LeastActive） | 分给正在处理的请求最少的 | 实例性能不均 |

## 30.3 配置中心（Nacos Config 深度）

### 30.3.1 动态刷新原理

```
ConfigService（客户端）──长轮询──► Nacos Server
     │                                   │
     │  30 秒超时（长轮询，有变更立刻返回）      │  配置变更
     ▼                                   ▼
  本地缓存 ◄──拉取最新──┘                控制台/接口修改
```

- **长轮询**：客户端发起请求后服务器"挂起"连接，配置变更立刻返回结果；没有变更 30 秒超时重连。**所以配置变更秒级生效**
- Spring Cloud 中 `@RefreshScope` 标记的 Bean 在配置变更后重建

### 30.3.2 配置管理最佳实践

```
✅ 配置分类：
├── 公共配置（数据源、Redis、MQ 地址）→ 放 shared-configs
├── 服务专属配置 → 放本服务 dataId（服务名.properties）
└── 敏感配置（密码、密钥）→ 用 Nacos 加密插件或外部密钥管理

✅ 配置命名规范：{服务名}-{profile}.{格式}
   user-service-dev.yml / user-service-prod.yml

✅ 灰度发布配置：先在小范围实例验证，再全量推送
```

> **深坑提醒**：`@RefreshScope` 对 `@Value` 注入的字段有效，但对 `static` 字段、构造器注入的参数**无效**。配置变更后要确认 Bean 真的被刷新了。

### 30.3.3 本地配置兜底

```yaml
# bootstrap.yml：本地配置作为兜底，Nacos 挂了也能启动
spring:
  application:
    name: user-service
  cloud:
    nacos:
      config:
        server-addr: ${NACOS_ADDR:127.0.0.1:8848}
        namespace: ${NACOS_NAMESPACE:prod}
        file-extension: yml
        # 扩展配置，按需引入
        shared-configs:
          - data-id: common-db.yml
            refresh: true
```

**生产要点**：Nacos 挂掉后，已加载的配置在本地有缓存，服务**能继续跑但配置改不了**——这就是为什么配置中心也要做集群（Nacos 本身集群 + 持久化到 MySQL）。

## 30.4 网关治理（Gateway 深度）

### 30.4.1 网关的职责边界

```
┌──────────────────────────────────────────────┐
│               API 网关（Gateway）               │
│  路由转发 │ 统一鉴权 │ 限流 │ 跨域 │ 灰度 │ 日志 │ 聚合  │
└──────────────────────────────────────────────┘
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   order-service  user-service  product-service
```

**网关只做"横切关注点"**，不写业务逻辑——业务逻辑必须在服务内，网关加了业务逻辑就变成"巨型应用"。

### 30.4.2 全局过滤器实现统一鉴权

```java
@Component
public class AuthGlobalFilter implements GlobalFilter, Ordered {

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        ServerHttpRequest request = exchange.getRequest();
        String path = request.getURI().getPath();

        // 白名单（登录、注册、验证码等）
        if (path.startsWith("/api/auth/") || path.startsWith("/api/captcha")) {
            return chain.filter(exchange);
        }

        // 校验 JWT（第 13 章已实现签发与校验）
        String token = request.getHeaders().getFirst("Authorization");
        if (token == null || !token.startsWith("Bearer ")) {
            return unauthorized(exchange, "未登录");
        }
        try {
            Claims claims = JwtUtil.parse(token.substring(7));
            // 把用户信息透传到下游服务（Header 传递）
            ServerHttpRequest mutated = request.mutate()
                    .header("X-User-Id", claims.get("userId").toString())
                    .build();
            return chain.filter(exchange.mutate().request(mutated).build());
        } catch (Exception e) {
            return unauthorized(exchange, "登录已过期");
        }
    }

    @Override
    public int getOrder() {
        return -100;   // 最先执行
    }

    private Mono<Void> unauthorized(ServerWebExchange exchange, String msg) {
        exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
        return exchange.getResponse().writeWith(
                Mono.just(exchange.getResponse().bufferFactory()
                        .wrap(msg.getBytes(StandardCharsets.UTF_8))));
    }
}
```

### 30.4.3 网关限流（RequestRateLimiter）

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: order-route
          uri: lb://order-service
          predicates:
            - Path=/api/order/**
          filters:
            - name: RequestRateLimiter
              args:
                # 每秒令牌数（容量）
                redis-rate-limiter.replenishRate: 10
                # 桶容量（突发）
                redis-rate-limiter.burstCapacity: 20
                # 按用户维度限流（SpEL 取 Header 中的用户）
                key-resolver: "#{@userKeyResolver}"
```

```java
@Bean
public KeyResolver userKeyResolver() {
    return exchange -> {
        String userId = exchange.getRequest().getHeaders().getFirst("X-User-Id");
        return Mono.just(userId == null ? "anonymous" : userId);
    };
}
```

### 30.4.4 灰度发布（金丝雀发布）

```
灰度规则：按 Header（如 X-Gray: canary）或按用户百分比
├── 90% 流量 → 稳定版本 v1
└── 10% 流量 → 新版本 v2（先放少量用户验证）
    ├── 观察指标正常 → 逐步提高灰度比例 → 全量
    └── 指标异常 → 快速回滚（流量全部切回 v1）
```

**Nacos 灰度实现**：给新版本实例设置权重 0.1（10%），老实例权重 0.9，验证没问题逐步调高权重直到 100%，全程无感。

## 30.5 熔断降级限流（Sentinel 深度）

第十五章用了 Sentinel 基础功能，本章讲清楚**原理和治理姿势**。

### 30.5.1 三种手段的区别

| 手段 | 解决什么 | 触发后表现 | 类比 |
| --- | --- | --- | --- |
| 限流 | 请求太多，保护自己 | 直接拒绝（快速失败） | 红绿灯 |
| 熔断 | 下游不可用，保护自己不被拖死 | 快速失败，不发起调用 | 断路器 |
| 降级 | 部分功能不可用，保证主流程 | 返回兜底结果 | 备用方案 |

**一句话**：**限流是怕自己被打爆，熔断是怕别人拖死自己，降级是坏了也能给个"能用"的结果。**

### 30.5.2 滑动窗口限流原理（Sentinel 默认）

```
时间窗口：1 秒，分成 2 个格子（每格 500ms）
┌────────────┬────────────┐
│ 格子1: 60个请求 │ 格子2: 40个请求 │
└────────────┴────────────┘
滑动到下一格时，旧格子的计数被"滑动出去"
当前窗口总请求 = 格子1 + 格子2 = 100 个 → 超过阈值 80 → 拒绝
```

- **固定窗口问题**：窗口边界处可能瞬时 2 倍流量（第 59.9 秒和第 60.0 秒各 80 个请求都通过）
- **滑动窗口解决**：细粒度统计，边界流量被摊平
- **令牌桶 vs 漏桶**：令牌桶允许一定突发（桶里攒了令牌）；漏桶恒定速率输出，适合保护下游

### 30.5.3 Sentinel 熔断降级实战配置

```java
@Configuration
public class SentinelConfig {

    @Bean
    public SentinelResourceAspect sentinelResourceAspect() {
        return new SentinelResourceAspect();
    }
}

@RestController
public class OrderController {

    // 订单接口：限流 100 QPS；熔断：5 秒内异常比例 > 20% 则熔断 10 秒
    @SentinelResource(
            value = "createOrder",
            blockHandler = "createOrderBlock",     // 限流/熔断时执行
            fallback = "createOrderFallback")      // 业务异常时执行
    @PostMapping("/api/order/create")
    public Result createOrder(@RequestBody OrderDTO dto) {
        // 调用商品服务、库存服务……
        return orderService.create(dto);
    }

    // 限流兜底：返回友好提示
    public Result createOrderBlock(OrderDTO dto, BlockException e) {
        return Result.error(429, "系统繁忙，请稍后再试");
    }

    // 异常兜底：业务异常统一处理
    public Result createOrderFallback(OrderDTO dto, Throwable t) {
        log.error("下单异常", t);
        return Result.error(500, "下单失败，请稍后重试");
    }
}
```

**配置项**（控制台或代码均可）：
- 限流：`qps`、`flowQps`、`maxQueueingTimeMs`
- 熔断（`degradeRule`）：`slowRatio`（慢调用比例）、`errorRatio`（异常比例）、`minRequestAmount`、`statIntervalMs`、`timeWindow`（熔断恢复时间）

### 30.5.4 隔离（线程池 vs 信号量）

```
❌ 默认：所有接口共享同一组线程，一个慢接口占满线程池 → 全站瘫痪（线程池隔离问题）

✅ 线程池隔离：A 服务调用 B 用独立线程池
   B 挂了最多耗尽 B 的线程池，不影响 A 其他接口
   ✅ 隔离最彻底，❌ 线程切换有开销

✅ 信号量隔离：限制并发调用数（如 B 最多同时 50 个调用）
   超出直接拒绝，✅ 轻量，❌ 不能应对超时堆积
```

**Feign 调用的生产标配**：`feign.client.config.default.connectTimeout=2000`、`readTimeout=3000` + Sentinel 熔断 + 线程池/信号量隔离。

## 30.6 分布式事务（Seata）

### 30.6.1 为什么需要

```
下单要扣库存（库存服务）→ 扣余额（账户服务）→ 生成订单（订单服务）
任何一个失败，其他服务的数据必须一起回滚 —— 本地事务管不了跨服务
```

### 30.6.2 四种方案对比

| 方案 | 原理 | 一致性 | 适用 |
| --- | --- | --- | --- |
| 两阶段提交（2PC/XA） | 先 prepare 再 commit，事务管理器协调 | 强一致 | 银行等低并发核心场景 |
| AT 模式（Seata 默认） | 本地事务 + 回滚日志（undo_log），自动生成反向 SQL | 最终一致（框架保证） | **大部分业务，首选** |
| TCC | Try-Confirm-Cancel 三阶段，业务自己写补偿 | 最终一致 | 强事务且高并发（如扣款） |
| Saga | 正向操作 + 反向补偿链 | 最终一致 | 长流程、事务边界长 |

### 30.6.3 Seata AT 模式原理

```
┌────────────┐        ┌────────────┐        ┌────────────┐
│ 订单服务      │        │ 库存服务      │        │ 账户服务      │
│ ①本地事务提交  │        │ ②本地事务提交  │        │ ③本地事务提交  │
│ ④全局回滚时    │        │ ④全局回滚时    │        │ ④全局回滚时    │
│   执行反向SQL │        │   执行反向SQL │        │   执行反向SQL │
└──────┬─────┘        └──────┬─────┘        └──────┬─────┘
       └──────────┬───────── TC（事务协调器）─────────┘
                  │ 记录全局事务状态，二阶段提交/回滚
```

**AT 模式为什么"自动"**：每个参与事务的本地库都有 `undo_log` 表，操作前记录数据快照（before/after），全局回滚时用快照生成反向 SQL 恢复。**业务代码零侵入**，只要加 `@GlobalTransactional` 注解。

```java
@GlobalTransactional(name = "create-order-tx", rollbackFor = Exception.class)
public void createOrder(OrderDTO dto) {
    // 扣库存（远程调用，参与全局事务）
    stockClient.deduct(dto.getSkuId(), dto.getNum());
    // 扣余额（远程调用，参与全局事务）
    accountClient.deduct(dto.getUserId(), dto.getAmount());
    // 本地保存订单
    orderMapper.insert(buildOrder(dto));
    // 任一环节抛异常 → 全部回滚
}
```

### 30.6.4 最终一致性方案（不用 Seata 也能做）

**本地消息表**（最经典的最终一致性）：

```
① 订单服务：订单表 + 本地消息表 同一个本地事务写入
② 异步任务轮询消息表 → 发送 MQ（RabbitMQ/Kafka）
③ 库存服务消费消息扣库存
④ 库存服务处理成功后回调/或消息消费成功后删消息表记录
⑤ 对账任务：定期扫超时未确认的消息，重发或人工处理
```

> **选型建议**：资金相关、强校验用 Seata AT；纯异步场景（发短信、更新统计）用 MQ + 本地消息表即可，别为所有场景上分布式事务——**能用最终一致性就不要强一致**。

## 30.7 可观测性（三件套）

### 30.7.1 三大支柱

| 支柱 | 工具（本系列） | 回答的问题 |
| --- | --- | --- |
| 日志（Logging） | ELK（第 20 章）+ 统一 traceId | 发生了什么？ |
| 指标（Metrics） | Prometheus + Grafana | 现在系统状态如何？ |
| 链路追踪（Tracing） | SkyWalking / Zipkin | 一个请求经过了哪些服务，哪里慢？ |

### 30.7.2 链路追踪原理（SkyWalking）

```
用户请求 ──► 网关 ──► 订单服务 ──► 库存服务 ──► MySQL
              │          │           │
              └── 生成 traceId（一次请求的唯一 ID）──┘
每个服务生成 span（调用片段），上报到 SkyWalking
SkyWalking 按 traceId 把 span 串成整条链路
能看出：总耗时、每段耗时、哪段最慢、是否有异常
```

**实现方式**：SkyWalking Agent 挂在 JVM 上（`-javaagent:skywalking-agent.jar`），**字节码注入，业务零侵入**。Spring Cloud 项目也可以直接用 OpenFeign 的 `X-B3-TraceId` 传播 traceId，配合日志打印实现"日志按 traceId 检索"。

```yaml
# logback 打印 traceId（配合 OpenFeign/MDC，第 11 章讲过 MDC）
logging:
  pattern:
    level: "%5p [%X{traceId:-}] [%thread]"
```

### 30.7.3 监控告警体系

```
Prometheus（采集指标）──► Grafana（可视化面板）
        │
        └── 告警规则 ──► Alertmanager ──► 钉钉/企微/邮件
```

**核心指标**：
- **RED**：Rate（请求速率）、Errors（错误率）、Duration（耗时）
- **USE**：Utilization（利用率）、Saturation（饱和度）、Errors（错误）
- 实例级：CPU、内存、GC、线程、连接池
- 业务级：订单量、支付成功率、核心接口 QPS/TP99

## 30.8 稳定性治理

### 30.8.1 容量评估与压测

```
容量评估公式：
  单实例 QPS = 100（压测得出）
  目标峰值 QPS = 5000（预估）
  ✅ 实例数 = 5000 / 100 × 1.5（冗余 50%）= 75 个

压测类型：
  单接口压测 → 全链路压测 → 灰度压测（生产流量模拟）
  发现瓶颈 → 优化（索引/缓存/异步）→ 再压
```

### 30.8.2 混沌工程（故障演练）

```
故意制造故障，验证系统自愈能力：
✅ 杀掉一个订单服务实例 → 观察负载均衡是否剔除、是否报错
✅ 停掉 Redis 主节点 → 观察哨兵切换、业务降级
✅ 模拟数据库慢查询 → 观察连接池是否被打满、熔断是否生效
✅ 断网 30 秒 → 观察重试与超时是否正常

原则：先小范围（1 个实例）→ 再放大；先演练再上线
```

### 30.8.3 应急预案（Runbook）

```
每次故障后必做三件事：
① 复盘：时间线 / 根因 / 影响范围
② 改进：代码修复 + 监控补充 + 预案更新
③ 演练：下次故障前验证预案有效

预案示例（写进文档）：
【故障】订单服务 CPU 飙高
【现象】请求超时率上升、Prometheus CPU 告警
【排查】1. jstack 看线程栈 → 2. 查慢 SQL → 3. 查 Redis 连接
【处理】1. 限流保护 → 2. 摘除异常实例 → 3. 修复后逐步恢复流量
【恢复标准】TP99 恢复到正常、错误率归零、CPU 回落
```

```
用户请求
   │
   ▼
Gateway ──统一鉴权(JWT)──统一限流(Redis 令牌桶)──跨域──灰度路由
   │
   ├──► order-service（下单）
   │       ├── ① 校验（调用 user-service，Feign + 超时 + 熔断）
   │       ├── ② 扣库存（Seata @GlobalTransactional，库存服务参与）
   │       ├── ③ 扣余额（账户服务参与）
   │       ├── ④ 发消息（RabbitMQ 异步，订单创建事件）
   │       └── ⑤ 本地事务提交，undo_log 记录

   ├──► 消费者（异步）：发短信、更新统计（最终一致，失败重试 + 死信）
   │
   └──► 可观测：SkyWalking 链路 + Prometheus 指标 + ELK 日志(traceId)
```

## 30.11 小结与练习

**本章重点**：
- 治理六大主题：注册发现、配置、流量、数据一致性、可观测、稳定安全
- Nacos：AP（服务发现）+ CP（配置），心跳 5s/剔除 30s，优雅上下线
- 配置中心：长轮询秒级生效，`@RefreshScope` 的局限，本地兜底
- 网关：只做横切关注点，全局过滤器统一鉴权，RequestRateLimiter 限流，权重灰度
- 限流/熔断/降级三者区别，滑动窗口原理，线程池 vs 信号量隔离
- 分布式事务：Seata AT 自动回滚、TCC 业务补偿、本地消息表最终一致
- 可观测三件套：日志 + 指标 + 链路追踪
- 稳定性：容量评估、混沌工程、应急预案三件套
- 治理的本质：**让系统在故障中仍可用，故障后能快速恢复**
