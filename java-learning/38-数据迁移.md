# 第三十八章 数据迁移（Database Migration）系统学习

> 本章目标：分清"Schema 迁移 / 数据迁移 / 数据同步"三类问题，掌握版本化迁移工具 Flyway 的原理（迁移历史表、命名规则、校验机制）与命令（migrate/info/validate/repair/baseline），对比 Liquibase 的选型，掌握上线增量脚本规范、大数据量分批迁移、影子表、跨库同步（DataX/Canal）等实战方案，最后打通 CI/CD 集成与生产回滚预案。配套可运行实操项目 **`migration-demo`**（Spring Boot + Flyway + MySQL，含 5 个版本迁移脚本）。
>
> 前置知识：第二十五章 MySQL 调优、第三十一章 Spring Boot 项目实战、第三十五章 Docker 系统学习。

## 38.1 先分清：三类"数据迁移"不是一回事

| 类型 | 做什么 | 典型工具/手段 | 频率 |
| --- | --- | --- | --- |
| **Schema 迁移**（结构变更） | 建表、加字段、加索引、改约束（DDL） | Flyway、Liquibase | 每次发版 |
| **数据迁移**（内容变更） | 数据清洗、补数、修复、搬运（DML） | 迁移脚本、分批任务、存储过程 | 按需 |
| **数据同步 / ETL**（持续搬运） | 跨库跨系统持续同步、异构导入 | DataX、Canal（binlog）、Kettle | 持续/定时 |

> 三者的共同敌人：**"在开发库手工执行一遍，生产却没人记得执行"** 以及 **"重复执行报错"**。本章重点解决 Schema 迁移与数据迁移，同时给出跨库同步的选型指引。

## 38.2 为什么需要版本化迁移工具

手工执行 SQL 的痛点：

| 痛点 | 表现 |
| --- | --- |
| 环境不一致 | 开发/测试/生产各缺各的字段，代码一上线直接 500 |
| 重复执行 | 同一段 `ALTER TABLE` 跑两次就报"Duplicate column" |
| 无法审计 | 谁、什么时候、改了库结构？无记录 |
| 无法回滚 | 上线失败，数据库结构没法跟着回退 |
| 协作冲突 | 两个同事同时建同名字段/索引 |
| 依赖顺序 | 建表依赖必须先建库、先建父表，手工排序易错 |

**Flyway / Liquibase 的答案**：把每一次结构变更做成**版本化的迁移脚本**，进 Git、随代码走，应用启动时自动按版本顺序执行且**只执行一次**，全程可查、可校验、可回滚（通过新增迁移脚本）。

## 38.3 Flyway 原理与核心用法（重点）

### 38.3.1 核心原理：一张表管天下

```
首次启动
   │ 创建 flyway_schema_history（迁移历史表）
   ▼
读取 classpath:db/migration 下的迁移脚本
   │ 按版本号升序排序（V1 < V2 < V10 < V11，不是字典序！）
   ▼
逐条比对历史表：未执行过的 → 在一个事务里执行并记录
   │ 执行成功后写一行：version / description / checksum / success
   ▼
下次启动 → 只执行比历史表"更新"的版本
```

关键表结构（`flyway_schema_history`）：

```sql
+-----------------+---------+----------------+------------------+---------+
| installed_rank  | version | description    | checksum         | success |
+-----------------+---------+----------------+------------------+---------+
| 1               | 1       | create user    | -1398005434      | 1       |
| 2               | 2       | add user email | 1605052167       | 1       |
+-----------------+---------+----------------+------------------+---------+
```

- **checksum**：脚本内容的哈希。已执行的脚本内容被改动 → `validate` 报错（防止"偷偷改已上线脚本"）；
- **success=0**：记录执行失败的版本，修复后 `repair` 清掉重跑。

### 38.3.2 目录与命名规则

```
src/main/resources/db/migration/
├── V1__create_user_table.sql      # 版本迁移（常规，不可重复执行）
├── V2__add_user_email.sql
├── V3__seed_user_data.sql
├── V4__create_order_table.sql
└── R__load_default_config.sql     # 可重复迁移（每次 checksum 变化才重跑）
```

命名规则：

| 前缀 | 含义 | 说明 |
| --- | --- | --- |
| `V` | 版本迁移 | `V{版本}__{描述}.sql`，版本只能递增，**执行后不可修改** |
| `U` | 撤销迁移 | 企业版功能，`U{版本}` 与 V 对应 |
| `R` | 可重复迁移 | `R__{描述}.sql`，内容变了就重新执行（适合视图/函数/初始化数据） |
| `T` | Java 迁移 | 写 Java 类实现复杂逻辑 |

> 版本号比较是**按数字**：`V10` 在 `V9` 之后、在 `V1` 之后。不要写 `V1_0`/`V1_1` 这种会让排序出错的格式。分隔符固定为**双下划线** `__`。

### 38.3.3 核心命令

```bash
# 查看当前状态与执行计划（谁执行了、谁待执行）
flyway info

# 执行迁移（开发/CI 常用）
flyway migrate

# 校验：检查已执行脚本是否被改动（checksum 不一致会报错）
flyway validate

# 把数据库标记到指定版本（不实际执行，用于对接存量库）
flyway baseline -baselineVersion=1.2

# 修复历史表：清理失败记录、修正 checksum（慎用！）
flyway repair

# 清空所有表（仅限测试环境！生产禁用）
flyway clean
```

### 38.3.4 Spring Boot 集成（实操项目 migration-demo 即此配置）

```yaml
# application.yml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/migration_demo?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
    username: root
    password: root123
  flyway:
    enabled: true
    locations: classpath:db/migration   # 迁移脚本目录
    baseline-on-migrate: true           # 存量库自动 baseline，防"已有表报错"
    validate-on-migrate: true           # 迁移前校验（生产建议开启）
    encoding: UTF-8
    # 多环境：dev 可开 clean-on-validation-error（仅测试）
```

依赖（Spring Boot 3.x，注意 MySQL 需单独加 `flyway-mysql` 模块）：

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-mysql</artifactId>
</dependency>
```

### 38.3.5 回滚策略（面试高频）

**Flyway 没有"自动回滚已执行版本"（undo 仅企业版）**。生产推荐策略：

| 场景 | 做法 |
| --- | --- |
| 迁移脚本执行失败（还没提交） | 脚本整体在一个事务里，失败自动回滚，修脚本后 `repair` 再 migrate |
| 新版本已上线，要回退功能 | **新增一个 V 脚本把结构/数据改回去**（正向回滚），不用 undo |
| 上线前想预览回滚 | 备份 + 在测试环境完整演练 |
| 存量库接入 Flyway | `baseline` 标记当前版本，之后正常增量 |

> **铁律**：已经合并进主干/已上线的迁移脚本**永远不要修改**，改动只能新增版本。否则 checksum 校验会把整个发布卡死。

## 38.4 Liquibase 对比与选型

| 维度 | Flyway | Liquibase |
| --- | --- | --- |
| 迁移文件格式 | SQL（必须 SQL） | XML / YAML / JSON / SQL |
| 变更集 | 版本号排序 | changeset（id + author + file） |
| 幂等 | V 脚本只执行一次（版本去重） | changeset 按 id 去重，天然幂等 |
| 回滚 | undo 仅企业版；社区靠新增脚本 | **自带 rollback**（需写 rollback SQL） |
| 校验 | checksum 强校验 | 支持 contexts/labels 按环境筛选 |
| 上手成本 | 低（就是写 SQL） | 中（要学 XML/YAML 语法） |
| 生态 | Spring Boot 原生支持好 | 功能全但配置重 |

**选型建议**：团队以 SQL 为中心、想要简单可靠 → **Flyway**（本章实操项目选它）；需要复杂变更编排、多环境条件执行、强回滚要求 → **Liquibase**。两者选一个，**不要混用**。

## 38.5 数据迁移实战方案

### 38.5.1 上线增量脚本规范（DDL + DML 混合）

```sql
-- V2__add_user_email.sql 示例：一次迁移干一件"逻辑内聚"的事
-- 1. 结构变更
ALTER TABLE `user` ADD COLUMN `email` VARCHAR(128) NULL COMMENT '邮箱' AFTER `phone`;
-- 2. 数据补齐（同版本内 DDL 在前，DML 在后）
UPDATE `user` SET email = CONCAT('user_', id, '@example.com') WHERE email IS NULL;
-- 3. 收尾约束（加索引注意：先数据后索引，避免大表索引重建阻塞写）
ALTER TABLE `user` ADD UNIQUE KEY `uk_user_email` (`email`);
```

规范要点：

| 原则 | 说明 |
| --- | --- |
| 一个脚本一个主题 | 拆分 V2/V3/V4，别把十件事塞一个脚本（失败难排查、难回滚） |
| DDL 在前，DML 在后 | 先改结构再补数据 |
| 先小表加索引 | 大表加索引会锁表/重建，见 38.5.2 |
| 脚本必须幂等可重跑语义 | 虽然 Flyway 只跑一次，但 SQL 本身要防御性写法（如 `IF NOT EXISTS`） |
| 写清注释 | 每条变更注明：目的、关联需求、是否影响存量数据 |

> **MySQL 注意**：DDL 语句**隐式提交**（不在事务内），Flyway 的"整体一个事务"对纯 DDL 不生效——所以 DDL 失败时可能已部分生效，修复策略是"继续写下一个修复版本"，而不是依赖事务回滚。

### 38.5.2 大数据量迁移：分批处理 + 影子表

**分批处理（Update/Insert 大表）**——避免一次性大事务锁表、长事务拖垮主库：

```sql
-- 伪代码：循环分批更新，每批 1000 条（配合索引 + sleep 控制压力）
UPDATE big_table
   SET status = 'ACTIVE'
 WHERE status = 'OLD'
   AND id BETWEEN :start AND :start + 1000
 LIMIT 1000;              -- 循环执行直到影响行数为 0
```

**影子表（大表加列/改列的稳妥方案，gh-ost / pt-online-schema-change 的思路）**：

```
1. 建新表 big_table_new（含目标结构）
2. 全量拷贝旧数据 → 增量同步 binlog 变更（或应用双写）
3. 校验数据一致
4. 原表改名 big_table_old，新表改名 big_table（原子 RENAME）
5. 观察无问题后删除旧表
```

> 生产大表（千万级）加列/改列，永远不要直接 `ALTER TABLE`（会锁写）。用影子表或 `pt-online-schema-change`/`gh-ost` 在线变更工具。

### 38.5.3 跨库/跨系统数据同步

| 场景 | 工具 | 原理 |
| --- | --- | --- |
| 异构数据源之间批量搬运 | **DataX**（阿里） | 插件式读-写，内存管道流式搬运 |
| 增量同步（MySQL → 缓存/ES/数仓） | **Canal** | 伪装从库，解析 binlog 增量 |
| 定时离线同步 | Kettle / 自研定时任务 | 抽取-转换-加载 |
| 库表搬迁（同构） | mysqldump + 导入 | 停机/低峰搬移 |

```bash
# mysqldump 库表搬迁示例
mysqldump -h 旧库 -u root -p --single-transaction --routines --triggers mall > mall_backup.sql
mysql -h 新库 -u root -p mall < mall_backup.sql
```

> 数据同步要额外关注：**一致性校验**（比对行数/关键字段 checksum）、**延迟监控**（Canal 场景）、**失败重试与幂等**（同步任务可重跑不产生脏数据）。

### 38.5.4 数据修复与清洗脚本

```sql
-- V5__fix_duplicate_order_no.sql：清理重复订单号（保留 id 最小的一条）
DELETE t1 FROM `order` t1
INNER JOIN `order` t2
  ON t1.order_no = t2.order_no AND t1.id > t2.id;

-- 清洗：去掉手机号里的空格和横线
UPDATE `user` SET phone = REPLACE(REPLACE(phone, ' ', ''), '-', '') WHERE phone LIKE '% %' OR phone LIKE '%-%';
```

原则：**可重复执行（幂等）**、**先备份/导出受影响行**、**加 WHERE 限制影响范围**、**执行前后核对行数**。

### 38.5.5 回滚预案（Checklist）

```
□ 迁移前：全量备份（mysqldump / 云 RDS 快照）
□ 迁移前：记录当前 flyway 版本（flyway info / select * from flyway_schema_history）
□ 迁移中：监控锁等待、主从延迟（show processlist / show slave status）
□ 迁移后：应用冒烟验证（关键接口、数据抽查）
□ 失败时：判断 DDL 是否已部分生效 → 决定"写修复版本"还是"备份回滚"
□ 演练：每个重大迁移先在 staging 完整演练一遍
```

## 38.6 生产实践与 CI/CD 集成

### 38.6.1 发布流程（迁移与代码发布的顺序）

```
代码合并 → CI 构建 → 环境初始化/升级
   │
   ├─ 步骤 1：备份数据库（自动或人工确认）
   ├─ 步骤 2：执行迁移（flyway migrate / mvn flyway:migrate）
   ├─ 步骤 3：启动新版本应用（代码必须与 Schema 兼容！）
   └─ 步骤 4：冒烟验证 → 观察指标 → 完成
```

> **黄金法则**：迁移脚本必须**先于**代码生效（或至少同版本发布），且**向后兼容**——线上旧代码读新 Schema 不能挂（所以"加列"用可空/默认值，别用 NOT NULL 无默认值）。

### 38.6.2 Jenkins 流水线集成示例

```groovy
stage('Database Migration') {
    steps {
        // 使用 Flyway Maven 插件执行迁移（生产环境用插件 validate + migrate）
        sh 'mvn -DskipTests flyway:migrate'
        // 或调用 Flyway 命令行
        // sh 'flyway -configFiles=flyway-prod.conf migrate'
    }
}
```

```xml
<!-- pom.xml 中配置 flyway-maven-plugin（与 Spring Boot 的 spring-boot-maven-plugin 配合） -->
<plugin>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-maven-plugin</artifactId>
    <configuration>
        <url>${flyway.url}</url>
        <user>${flyway.user}</user>
        <password>${flyway.password}</password>
        <locations>
            <location>classpath:db/migration</location>
        </locations>
    </configuration>
</plugin>
```

### 38.6.3 常见坑与规避

| 坑 | 规避 |
| --- | --- |
| 迁移脚本被修改导致 checksum 报错 | 铁律：已发布脚本只增不改；改本地未发布版本用 `flyway repair` 修正历史 |
| 大表 DDL 锁表阻塞线上 | 影子表 / pt-osc / gh-ost；低峰执行；监控锁等待 |
| 多环境配置不一致 | 用 profile 区分 datasource；脚本目录统一，禁止"测试库脚本和生产库脚本"两套 |
| 迁移在 CI 里执行了、生产没人执行 | 迁移纳入发布流水线；**应用启动自动 migrate**（开发/测试），生产可关自动迁移改为流水线显式执行 |
| 忘记备份 | 回滚预案强制第一步备份 |
| 长事务 / 大批量 UPDATE | 分批处理，限制单批条数，避免拖垮主从复制 |

### 面试高频问题清单

| 问题 | 答案要点 |
| --- | --- |
| Flyway 原理？ | flyway_schema_history 记录版本 + checksum，启动时按版本升序只执行未执行的 |
| V 与 R 脚本区别？ | V 只执行一次（版本递增）；R 每次内容变化都重跑（视图/函数/初始数据） |
| 已上线的迁移脚本能改吗？ | 不能！只能新增版本，否则 checksum 校验失败 |
| Flyway 怎么回滚？ | 无 undo（企业版才有）；社区版用新增脚本正向回滚，失败场景 repair 后重跑 |
| baseline 是干嘛的？ | 存量库接入时把当前状态标记为某版本，跳过历史脚本 |
| 大表加列为什么不直接 ALTER？ | 锁表/重建，阻塞写；用影子表或 pt-osc/gh-ost 在线变更 |
| DDL 事务注意点？ | MySQL DDL 隐式提交，不参与事务回滚 |
| 迁移脚本何时执行？ | 先于代码生效且向后兼容；生产用流水线显式执行 |
| Flyway 与 Liquibase 选型？ | 简单 SQL 中心选 Flyway；复杂编排/回滚选 Liquibase |
| 跨库同步工具？ | 批量 DataX；增量 Canal（binlog）；离线 Kettle/定时任务 |
