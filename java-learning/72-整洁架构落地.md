# 第七十二章 整洁架构（Clean Architecture 落地）

> **本章目标**：把 Robert C. Martin 的 Clean Architecture 落到 Spring Boot 工程上，掌握"同心圆 + 依赖规则 + 跨边界适配器"三大支柱。
>
> **前置知识**：第 71 章（分层架构全景）、第 41 章（DDD 战术设计、仓储接口倒置）、第 28 章（依赖倒置原则）。

> 一句话：**整洁架构不是"再多分一层目录"，而是把"依赖方向"作为可被 ArchUnit 自动守护的硬约束**。

---

## 72.1 整洁架构的核心思想

Robert C. Martin 在 2012 年的博客《The Clean Architecture》中提出的目标：

> **让业务规则（高层策略）独立于技术细节（低层机制）**。

实现这个目标有两个手段：

1. **依赖方向单向**：源代码依赖由外向内。
2. **跨边界用接口 + DTO**：业务核心不感知外部技术，外部技术也不持有业务核心的对象。

### 72.1.1 同心圆与对应层

```
            ┌─────────────────────────────────┐
            │  Frameworks & Drivers           │  ── Spring Boot、MyBatis、JPA
            │  ┌───────────────────────────┐  │
            │  │  Interface Adapters       │  ── Controller、Repository 实现、网关
            │  │  ┌─────────────────────┐  │  │
            │  │  │  Use Cases          │  │  ── 应用服务（AppService）
            │  │  │  ┌───────────────┐  │  │  │
            │  │  │  │  Entities     │  │  │  ── 实体、值对象、领域服务、领域事件
            │  │  │  └───────────────┘  │  │  │
            │  │  └─────────────────────┘  │  │
            │  └───────────────────────────┘  │
            └─────────────────────────────────┘
```

四层命名在不同文献里有差异，但本质一致：

| Uncle Bob 命名 | Vaughn Vernon 命名 | Spring Boot 工程对应包 |
| --- | --- | --- |
| Entities | Domain | `domain.model` |
| Use Cases | Application | `application.service` |
| Interface Adapters | Interfaces + Infrastructure | `interfaces.web` + `infrastructure.persistence` |
| Frameworks & Drivers | Infrastructure（运行时） | `infrastructure.config`（Spring 配置类） |

## 72.2 依赖规则：源代码依赖只能由外向内

### 72.2.1 反例：领域层直接 import 框架

```java
// ❌ 反例：Order 是"领域实体"，但依赖了 Spring Data
package com.ddd.ecommerce.order.domain.model;

import org.springframework.data.annotation.Id;        // ❌ 框架依赖泄漏
import org.springframework.data.annotation.Version; // ❌

@Entity  // ❌
public class Order {
    @Id
    private Long id;
    // ...
}
```

后果：

- 业务核心被绑定到 Spring Data，换取 JPA 时要改 Order 类本身。
- 单元测试必须启动 Spring 容器，无法纯 JUnit。
- 跨边界（如响应给前端）"对象先要 detach session"——各种麻烦。

### 72.2.2 正例：领域层保持纯净

```java
// ✅ 正例：Order 只依赖 JDK + 自家值对象
package com.ddd.ecommerce.order.domain.model;

import java.time.Instant;
import java.util.List;

public class Order {
    private final OrderId id;
    private final CustomerId customerId;
    private OrderStatus status;
    private final List<OrderItem> items = new ArrayList<>();

    public Order(OrderId id, CustomerId customerId, List<OrderItem> items) {
        // 不变量校验写在这里
        if (items.isEmpty()) {
            throw new IllegalArgumentException("订单至少一件商品");
        }
        this.id = id;
        this.customerId = customerId;
        this.items.addAll(items);
        this.status = OrderStatus.PENDING;
    }

    public void pay() {
        if (status != OrderStatus.PENDING) {
            throw new IllegalStateException("当前状态" + status + "不允许支付");
        }
        this.status = OrderStatus.PAID;
    }

    public Money total() {
        return items.stream()
                    .map(OrderItem::subtotal)
                    .reduce(Money.ZERO, Money::add);
    }

    public OrderId id() { return id; }
    public CustomerId customerId() { return customerId; }
    public OrderStatus status() { return status; }
    public List<OrderItem> items() { return List.copyOf(items); }   // 防御性拷贝
}
```

> 单元测试可以**纯 JUnit**，不起 Spring 容器：

```java
class OrderTest {
    @Test
    void shouldRejectEmptyOrder() {
        assertThrows(IllegalArgumentException.class,
            () -> new Order(OrderId.generate(), new CustomerId(1L), List.of()));
    }

    @Test
    void shouldChangeStatusWhenPaid() {
        Order order = sampleOrder();
        order.pay();
        assertEquals(OrderStatus.PAID, order.status());
    }
}
```

## 72.3 跨边界数据传递：DTO 边界

整洁架构严格禁止"内部实体穿透"——Order 对象**绝不**直接传给 Controller 反序列化给客户端。

### 72.3.1 为什么必须跨边界传 DTO

| 风险 | 场景 |
| --- | --- |
| **字段外泄** | 内部审计字段（如 `internalReason`）意外暴露给前端 |
| **框架依赖泄漏** | JPA `@ManyToOne` 触发懒加载异常 |
| **序列化失控** | Lombok `@Data` 自动 toString 把所有字段打印到日志 |
| **演进困难** | 实体加字段直接破坏 API 兼容 |

### 72.3.2 跨边界 DTO 三件套

```java
// 1. Controller 入参 DTO
public record SubmitOrderRequest(
    @NotNull Long customerId,
    @NotEmpty List<OrderItemRequest> items
) {}

// 2. Controller 响应 DTO
public record OrderResponse(
    String orderId,
    String status,
    BigDecimal totalAmount,
    String currency
) {}

// 3. 转换器（边界 Adapter）
@Component
public class OrderResponseAssembler {
    public OrderResponse toResponse(Order order) {
        Money total = order.total();
        return new OrderResponse(
            order.id().value(),
            order.status().name(),
            total.amount(),
            total.currency().code()
        );
    }
}
```

> **核心纪律**：DTO 放在 `interfaces.dto` 包，Assembler 放在 `interfaces.web` 或 `application.service` 包。**绝不让 Order 直接出现在 Controller 返回值中**。

## 72.4 适配器（Adapter）的角色

整洁架构里所有"与外部世界交互的代码"都是适配器，分两类：

### 72.4.1 主适配器（Inbound Adapter / Driving Adapter）

**驱动业务核心运行**——Controller、CLI、消息消费者、定时任务。

```java
// 主适配器：REST Controller
@RestController
@RequestMapping("/clean/orders")
public class CleanOrderController {
    private final SubmitOrderUseCase useCase;          // 依赖用例接口

    @PostMapping
    public OrderResponse create(@RequestBody SubmitOrderRequest req) {
        SubmitOrderCommand cmd = new SubmitOrderCommand(
            req.customerId(), req.items()
        );
        OrderId orderId = useCase.execute(cmd);
        return new OrderResponse(orderId.value(), "PENDING", null);
    }
}
```

### 72.4.2 从适配器（Outbound Adapter / Driven Adapter）

**被业务核心调用**——MyBatis 实现仓储、Feign 调用远程服务、Redis 缓存、消息发布。

```java
// 从适配器：MyBatis 实现 OrderRepository
@Repository
public class MybatisOrderRepository implements OrderRepository {
    private final OrderMapper orderMapper;
    private final OrderItemMapper itemMapper;
    private final OrderAssembler assembler;

    @Override
    public void save(Order order) {
        OrderPO po = assembler.toPO(order);
        if (po.getId() == null) {
            orderMapper.insert(po);
        } else {
            orderMapper.updateById(po);
        }
        // ... 处理 items
    }

    @Override
    public Optional<Order> findById(OrderId id) {
        OrderPO po = orderMapper.selectById(id.value());
        return Optional.ofNullable(po).map(assembler::toDomain);
    }
}
```

## 72.5 实战：整洁架构的 Spring Boot 工程结构

```
ecommerce-clean/
├── pom.xml
├── src/main/java/com/ddd/ecommerce/order/
│   ├── interfaces/                          ← 主适配器 + DTO
│   │   ├── web/OrderController.java
│   │   └── dto/{OrderRequest,OrderResponse}.java
│   ├── application/                          ← 用例层
│   │   ├── usecase/SubmitOrderUseCase.java  (interface)
│   │   ├── usecase/SubmitOrderUseCaseImpl.java
│   │   └── command/SubmitOrderCommand.java
│   ├── domain/                               ← 实体、值对象
│   │   ├── model/Order.java
│   │   ├── model/Money.java
│   │   ├── model/OrderStatus.java
│   │   └── repository/OrderRepository.java   (interface)
│   └── infrastructure/                       ← 从适配器
│       ├── persistence/OrderMapper.java
│       ├── persistence/OrderPO.java
│       └── persistence/MybatisOrderRepository.java
└── src/main/resources/
    ├── application.yml
    └── mapper/OrderMapper.xml
```

> **整洁 vs DDD 四层**：整洁把"Interfaces + Infrastructure" 合并为"Interface Adapters"层（主适配 + 从适配），其他完全等价。

## 72.6 整洁架构 vs 三层架构：差异对照表

| 维度 | 三层架构 | 整洁架构 |
| --- | --- | --- |
| 实体类 | POJO（含 setter） | 充血实体（无 setter、有行为） |
| Service 角色 | 业务规则 + 事务 + 编排 | 仅编排（"UseCase"），业务规则入实体 |
| Controller 依赖 | Service（直接注入） | UseCase 接口（注入接口） |
| 仓储实现位置 | Service 同层（Dao） | 基础设施层（与 Controller 解耦） |
| 跨层数据 | 实体直接传 | DTO + Assembler 转换 |
| 单元测试 | 难（依赖 Spring 容器） | 易（领域层纯 JUnit） |
| 业务规则散落 | Service 臃肿 | 实体封装 |
| 适用规模 | 中小项目 | 中大型、长期维护项目 |

> **最关键的差异**：Service 是否做业务规则。在整洁架构中，**业务规则永远进不了 Service**。

## 72.7 整洁架构的边界守护：ArchUnit

光靠"程序员自律"是无法维护依赖规则的。**ArchUnit** 是 Java 生态里最成熟的架构守护工具，能在 JUnit 测试中自动验证包依赖关系。

### 72.7.1 引入依赖

```xml
<dependency>
    <groupId>com.tngtech.archunit</groupId>
    <artifactId>archunit-junit5</artifactId>
    <version>1.3.0</version>
    <scope>test</scope>
</dependency>
```

### 72.7.2 规则示例

```java
import com.tngtech.archunit.core.domain.JavaClasses;
import com.tngtech.archunit.core.importer.ClassFileImporter;
import com.tngtech.archunit.lang.ArchRule;
import org.junit.jupiter.api.Test;

import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.*;

class CleanArchitectureRulesTest {
    private static final JavaClasses classes = new ClassFileImporter()
        .importPackages("com.ddd.ecommerce.order");

    @Test
    void domain_should_not_depend_on_application() {
        ArchRule rule = noClasses()
            .that().resideInAPackage("..domain..")
            .should().dependOnClassesThat().resideInAPackage("..application..");
        rule.check(classes);
    }

    @Test
    void domain_should_not_depend_on_infrastructure() {
        ArchRule rule = noClasses()
            .that().resideInAPackage("..domain..")
            .should().dependOnClassesThat().resideInAPackage("..infrastructure..");
        rule.check(classes);
    }

    @Test
    void domain_should_not_depend_on_interfaces() {
        ArchRule rule = noClasses()
            .that().resideInAPackage("..domain..")
            .should().dependOnClassesThat().resideInAPackage("..interfaces..");
        rule.check(classes);
    }

    @Test
    void controllers_should_not_depend_on_repositories_directly() {
        ArchRule rule = noClasses()
            .that().haveSimpleNameEndingWith("Controller")
            .should().dependOnClassesThat().haveSimpleNameEndingWith("Repository");
        rule.check(classes);
    }

    @Test
    void repositories_should_be_interfaces_in_domain() {
        ArchRule rule = classes()
            .that().haveSimpleNameEndingWith("Repository")
            .should().beInterfaces();
        rule.check(classes);
    }
}
```

### 72.7.3 把 ArchUnit 测试模块化

在大型工程中，把所有 ArchUnit 规则集中到独立模块 `modular-archunit/`：

```
modular-archunit/
├── pom.xml
└── src/test/java/com/ddd/modular/archunit/
    ├── CleanArchitectureRulesTest.java     ← 整洁架构通用规则
    ├── ModularBoundaryRulesTest.java        ← 模块边界规则
    └── DddLayeringRulesTest.java            ← DDD 四层规则
```

测试报告可以接入 CI（持续集成），任何人提交违反规则的代码都会自动阻断。

## 72.8 整洁架构的常见误区

### 72.8.1 误区一：分层等于多建几个空包

> 错。整洁架构的关键是"依赖方向约束"，不是"包结构多漂亮"。

如果你的 Order 实体被允许 `import org.springframework.*`，那再多包也是假整洁。

### 72.8.2 误区二：所有项目都要整洁架构

> 错。CRUD 工具型项目用整洁架构是过度设计。

整洁架构的代价是：

- 模板代码多（DTO、Assembler、Repository interface 各一份）
- 团队需要训练（充血模型、依赖倒置）
- 调试栈深（多一层 Adapter）

只在业务规则复杂、长期维护的项目才值得这个代价。

### 72.8.3 误区三：整洁架构 = DDD

> 错。整洁架构是"分层方法"，DDD 是"建模方法"。两者独立但互补。

没有 DDD 的整洁架构只是"整齐的贫血模型"——分户边界整齐但内部仍是 setter 集合。

没有整洁架构的 DDD 只是"先进建模思想"——业务规则在 Order 里，但 Service 仍然调用所有基础设施。

### 72.8.4 误区四：测试覆盖率 100% 就够了

> 错。ArchUnit 比测试覆盖率更重要——它守护的是**结构**，不是行为。

即使 100% 测试覆盖，如果有 Service 偷偷调用了外部 HTTP API，整个架构就已崩塌。

### 本章小结

- 整洁架构 = 同心圆 + 依赖规则 + 跨边界 DTO。
- 领域层**绝对**不依赖 Spring、MyBatis、JPA 等框架。
- 跨边界必须用 DTO + Assembler 转换，杜绝内部实体穿透。
- ArchUnit 是把"架构约束"变成可执行测试的标准方案。
- 整洁架构不是 DDD，但常与 DDD 一起用。
