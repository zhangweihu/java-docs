# 第四十四章 事件风暴工作坊实操（从业务便签到领域模型）

> 本章目标：掌握事件风暴（Event Storming）这一 DDD 落地第一步的完整方法论——六大基本元素、Big Picture 与 Design Level 两种规模、八步时间线建模法、主持与参与者组织技巧，并通过"电商订单"完整工作坊实战，把一墙便签最终变成第 41 章那样的聚合/仓储/限界上下文代码。
>
> 前置知识：第四十一章 DDD 战术设计（事件风暴的产出物就是战术元素）、第四十三章 CQRS 与事件溯源（事件是 CQRS/ES 的核心载体）、第四十章 贫血模型与充血模型。

## 44.1 为什么 DDD 落地第一件事是事件风暴

### 44.1.1 两个角色的语言鸿沟

第 41 章我们学了限界上下文与通用语言，但**通用语言从哪里来**？它不会从需求文档里自动长出来。现实是：

- **业务专家**说："下单成功后要**扣库存**，库存不够要**锁定**，超时要**释放**……"——他们用的是业务语言，脑子里是流程和异常分支。
- **开发人员**说："这是一张 `t_order` 表，一个 `OrderService`，下单走 `@Transactional`，失败抛异常回滚……"——他们用的是技术语言，脑子里是表和接口。

两份"语言"之间的鸿沟，就是大量返工、伪需求、上线后才发现"逻辑根本不对"的根源。第 40 章的"漏改状态判断"事故，本质也是业务规则没有在建模阶段对齐。

### 44.1.2 事件风暴解决了什么

**事件风暴**（Alberto Brandolini 提出）：让业务专家和开发人员**围着一面墙（或一面虚拟白板）**，用彩色便签把业务的"发生过的事实"按时间顺序贴出来，共同把系统"演"一遍。

| 传统需求会议 | 事件风暴工作坊 |
| --- | --- |
| 讲 PPT、提需求、会后写 PRD | 全员动手贴便签、演流程、当场对齐 |
| 抽象描述"系统要做什么" | 具体还原"业务发生过什么" |
| 需求条目不负责（改需求成本高） | 业务专家亲自参与（认知直接固化） |
| 产出：文档（没人细看） | 产出：事件墙（大家共同贴出来的共识） |

> **一句话记忆**：事件风暴不讨论"系统怎么做"，只讨论"业务到底发生了什么"——把"发生过的事实"按时间线排出来，模型的边界和规则自然就浮出来了。

### 44.1.3 它处于 DDD 落地链条的第一环

```
事件风暴（本章 44）──► 限界上下文/通用语言 ──► 聚合/实体/值对象/仓储（第 41 章）
      │                        │                          │
      └──── 业务事实清单 ──► 上下文边界 ──────► 战术设计（代码落地）
```

第 41 章是"施工图怎么画"，本章是"**怎么带着业务专家一起把施工图画出来**"。

## 44.2 六大基本元素：一墙便签的"词汇表"

事件风暴只有六种颜色，每种颜色一种业务含义。先记住颜色→含义，后面全是用它们拼出来的：

| 颜色 | 元素 | 命名规则 | 示例 |
| --- | --- | --- | --- |
| 🟧 橙 | **领域事件**（Domain Event） | 过去式动词，已经发生的事实 | `订单已下单`、`库存已扣减`、`支付已成功` |
| 🟦 蓝 | **命令**（Command） | 祈使句，某个人/系统发起的动作 | `提交订单`、`扣减库存`、`确认支付` |
| 🟨 黄 | **聚合**（Aggregate） | 名词，承载业务规则的对象 | `订单`、`库存`、`账户` |
| 🟩 绿 | **读模型**（Read Model） | 名词，用户想看的数据形态 | `订单列表`、`销售报表` |
| 🟪 紫 | **外部系统/角色**（Actor） | 系统或角色名 | `用户`、`支付网关`、`物流系统` |
| ⚪ 白 | **业务规则/热点**（Business Rule/Hotspot） | 一句话规则 | `库存不足不能下单`、`支付有 30 分钟超时` |

**事件是主角**：它是一墙便签的中轴线，所有建模都围绕"发生过什么"展开。

> **为什么要用"事件"而不是"用例/接口"开头**：事件是**客观事实**，业务专家闭着眼睛都能确认"这事确实发生过"；而接口/用例是技术抽象，业务专家说不出话。从事实出发，通用语言最容易建立。

## 44.3 两种规模：Big Picture 与 Design Level

事件风暴分两种规模，**别混着做**：

| 维度 | Big Picture（大图式） | Design Level（设计级） |
| --- | --- | --- |
| 目的 | 摸清业务全貌、划定限界上下文 | 深挖单个上下文的细节、产出聚合 |
| 参与者 | 业务专家 + 架构师 + 决策者 | 业务专家 + 该上下文开发者 |
| 粒度 | 粗：只贴"大事"（订单已创建，不拆内部） | 细：贴到"每张表都能对应一个聚合" |
| 时间 | 半天~1 天 | 1~3 天 |
| 产出 | 上下文地图（限界上下文 + 依赖关系） | 聚合清单、事件清单、命令清单、读模型 |

> **实战顺序**：先 Big Picture 划清边界（哪些该是订单上下文、哪些是物流上下文），再对每个上下文开 Design Level 工作坊。一次 Design Level 只覆盖**一个限界上下文**，这是铁律。

## 44.4 八步时间线法：从空墙到模型

以"电商下单"为例，走完整八步（这是本章的核心方法论，配合 44.6 实战代码食用）。

### 第一步：贴领域事件（橙色，时间线主体）

在墙上画一条时间轴（从左到右），让业务专家按时间顺序贴**已经发生过的事实**：

```
[用户已注册] ──► [购物车已添加] ──► [订单已提交] ──► [库存已锁定] ──► [支付已完成]
    ──► [订单已发货] ──► [订单已签收] ──► [订单已确认收货]
```

规则：
- **只贴客观事实**，不贴"系统要做的事"（那是命令）；
- 事件名用**过去式**，中文直接"已 xx"；
- 业务专家贴，开发只提问（"然后呢？""还有别的分支吗？"）。

**追问异常分支**（这是宝藏）：业务专家会自己补出 `[订单已取消]`、`[库存已释放]`、`[支付已超时]`、`[退款已发起]`……**异常分支里藏着最多的业务规则**。

### 第二步：补命令（蓝色，贴在事件左边）

每个事件都是某个命令的结果，把**触发者 + 动作**贴在事件左边：

```
[用户] 提交订单 ──► [订单已提交] ──► [系统] 锁定库存 ──► [库存已锁定]
                        │
                        └── [系统] 发起支付 ──► [支付已发起]
```

命令三要素：**谁发起（Actor）+ 做什么动作 + 期望产生的事件**。一个命令可以对应多个可能事件（成功/失败/超时）。

### 第三步：识别聚合（黄色，圈出事件簇）

把"共享同一批数据、必须强一致"的事件/命令圈成一组，组名就是聚合：

```
┌──────────────── 订单聚合（黄色便签覆盖） ────────────────┐
│ [订单已提交] [订单已支付] [订单已取消] [订单已发货] [订单已签收] │
│ 命令：提交订单 / 确认支付 / 取消订单 / 发货 / 签收              │
│ 规则：只有"已支付"才能发货；已发货不能取消                      │
└──────────────────────────────────────────────────────┘

┌──────────── 库存聚合 ────────────┐   ┌──────────── 支付聚合 ────────────┐
│ [库存已锁定] [库存已扣减] [库存已释放] │   │ [支付已发起] [支付已成功] [支付已退款] │
└──────────────────────────────────┘   └──────────────────────────────────┘
```

**判断"该不该是一个聚合"**：两个事实必须**同事务**（要么都成、要么都败）就合一个聚合；可以**最终一致**就拆开（这正是第 43 章 CQRS/ES 的拆分依据）。

### 第四步：划分限界上下文（画边界）

看事件簇，把**语义独立、演化独立**的组框起来命名：

```
┌─────────────────── 订单上下文 ───────────────────┐
│  订单聚合 / 用户读模型 / 命令：提交订单、确认支付      │
└──────────────────────────────────────────────────┘
┌────────── 库存上下文 ──────────┐   ┌────────── 支付上下文 ──────────┐
│  库存聚合 / 命令：锁定、扣减、释放  │   │  支付聚合 / 命令：发起、确认、退款 │
└───────────────────────────────┘   └───────────────────────────────┘
```

> 上下文边界 = **微服务边界的最佳候选**（但不强制一一对应，先按业务划，再决定技术怎么拆）。

### 第五步：上下文映射（画依赖箭头）

在上下文之间画箭头，标注协作方式（第 41 章 41.9 的防腐层概念在这里落地）：

```
订单上下文 ──调用──► 库存上下文（锁定库存）    依赖关系：订单→库存，异步补偿
订单上下文 ──调用──► 支付上下文（发起支付）    依赖关系：订单→支付，超时回滚
```

箭头上的标注：同步调用 / 异步消息 / 防腐层（ACL）/ 共享内核……**不一致的地方在墙上一眼看出**。

### 第六步：补读模型（绿色）

问业务专家："**哪些地方要看数据？看什么形态？**"贴在对应命令下方：

```
[提交订单] 下方贴：订单详情页（商品、金额、地址）
[订单已发货] 下方贴：物流跟踪页（快递单号、轨迹）
[订单已签收] 下方贴：销售报表（按日/按商品统计）
```

读模型回答"用户怎么看"，它就是第 43 章**读模型/投影**的输入。

### 第七步：标注业务规则与热点（白色）

把"特殊业务规则、风险点、争议点"贴白便签，标记 ⚠️：

```
⚠️ 库存不足不能提交订单（防超卖，第 31 章防超卖在这里来源）
⚠️ 支付 30 分钟未完成自动取消并释放库存（超时，接第 42 章状态机超时事件）
⚠️ 已发货订单取消要进入售后流程（异常分支）
⚠️ 优惠券与满减的叠加规则（业务争议热点）
```

**白便签是最有价值的部分**——它们是测试用例的来源、代码里规则的来源。

### 第八步：映射到代码结构（落地清单）

工作坊产出物与代码一一对应：

| 墙上产物 | 代码产物（第 41 章） |
| --- | --- |
| 黄色聚合 | 聚合根类 + 实体 + 值对象（`OrderAggregate`） |
| 橙色事件 | 领域事件类（`OrderPlacedEvent`，第 43 章事件命名） |
| 蓝色命令 | 应用层命令对象 + 应用服务方法（`SubmitOrderCommand`） |
| 白色规则 | 聚合根内的不变量校验（第 40 章充血模型行为） |
| 绿色读模型 | 读模型 DTO + 仓储查询方法 / 投影器 |
| 上下文边界 | 模块/服务边界 + 防腐层 |

## 44.5 主持工作坊：角色、节奏与技巧

### 44.5.1 三种角色

| 角色 | 谁 | 做什么 |
| --- | --- | --- |
| **主持人（Facilitator）** | 懂 DDD 的架构师/技术教练 | 控场、提问、引导、防跑偏，**不替业务做决定** |
| **领域专家（Domain Expert）** | 最懂业务的 1~3 人 | 贴事件、讲流程、定规则（**全场主角**） |
| **记录员（Scribe）** | 开发/PO | 拍照、记录争议、整理电子版产出 |

### 44.5.2 五个控场技巧（都是血泪经验）

1. **时间盒（Timebox）**：每个步骤设死时间（如事件风暴 45 分钟），到点强制收——否则一墙贴到天黑；
2. **只问开放问题**："然后呢？""还会发生什么？""库存不够怎么办？"——不引导答案；
3. **禁止技术语言**：主持人要拦住"这个用 Redis 锁""这里建张表"，转译成业务问题；
4. **争议先挂墙**：规则有争议就贴白便签标记"待定"，不打断主线，会后单独解决；
5. **墙即文档**：结束前拍照 + 记录员当天整理成"事件风暴纪要"（事件清单/命令清单/上下文地图），当天同步给全员。

### 44.5.3 工作坊前 Checklist

```
□ 选好参与者（业务专家必须到场，技术侧不超过 6 人）
□ 准备白墙/大屏 + 大量便签（六色各 100+）+ 粗马克笔
□ 明确本次规模（Big Picture 还是 Design Level）与目标上下文
□ 主持人提前 1 小时到场，画好时间轴、写好开场问题
□ 声明规则：先贴全再讨论、不评价别人的便签、时间盒到点收
```

## 44.6 实战：订单事件风暴 → 代码全链路

用第 41 章的订单聚合作为 Design Level 工作坊的"标准答案"，演示**墙上怎么贴、代码怎么写**。

### 44.6.1 工作坊产出：订单上下文事件墙（精简版）

```
时间轴 →→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→
[用户] 提交订单     [系统] 锁定库存      [系统] 发起支付      [用户] 确认支付
     │                   │                   │                   │
     ▼                   ▼                   ▼                   ▼
[订单已提交]        [库存已锁定]         [支付已发起]         [支付已成功]
     │                   │                                       │
     └── ⚠️ 库存不足则 [订单已取消]        ⚠️ 30 分钟未支付        ▼
         ⚠️ 超时释放库存 [库存已释放]          → [支付已超时]    [订单已支付]
                                                                  │
                                      ┌───────────────────────────┤
                                      ▼                           ▼
                             [系统] 发货                 ⚠️ 已支付不可取消
                                      │
                                      ▼
                                  [订单已发货] ──► [订单已签收] ──► [订单已完成]

读模型：订单详情页 / 订单列表页 / 销售报表
外部系统：支付网关、物流系统、短信服务
```

### 44.6.2 从事件墙直接生成聚合骨架

事件墙上的黄色簇 → 第 41 章聚合根，每个事件 → 一个方法 + 一个领域事件：

```java
// 订单聚合根（黄色簇的直接翻译）
@AggregateRoot
public class Order {
    private OrderId id;
    private OrderStatus status;          // 接第 42 章状态机语义
    private List<OrderItem> items;       // 实体集合
    private Money totalAmount;           // 值对象（第 41 章）
    private Address shippingAddress;     // 值对象

    // 命令：提交订单 ──► 事件：订单已提交
    public static Order submit(SubmitOrderCommand cmd) {
        // ⚠️ 白便签：订单总额必须与明细一致（不变量）
        Money total = cmd.items().stream().map(OrderItem::subtotal).reduce(Money.ZERO, Money::add);
        if (!total.equals(cmd.amount())) throw new BusinessException("金额校验失败");
        Order order = new Order(...);
        order.applyEvent(new OrderSubmittedEvent(order.id, cmd.items(), total));
        return order;
    }

    // 命令：确认支付 ──► 事件：订单已支付（⚠️ 只有待支付才能支付）
    public void confirmPayment(PaymentConfirmedEvent evt) {
        if (status != OrderStatus.PENDING_PAYMENT)
            throw new BusinessException("当前状态不可支付");   // 第 40 章充血模型
        applyEvent(new OrderPaidEvent(id, evt.paidAt()));
    }
}
```

### 44.6.3 事件清单 → 测试用例清单

白便签上的规则，直接变成单元测试（这是事件风暴"免费赠送"的测试资产）：

```java
@Test
void 库存不足时订单不能提交() { /* 对应 ⚠️ 库存不足则取消 */ }
@Test
void 待支付订单超时30分钟自动取消并释放库存() { /* 对应 ⚠️ 超时 */ }
@Test
void 已支付订单不可取消() { /* 对应 ⚠️ 已支付不可取消 */ }
@Test
void 订单金额与明细不符时拒绝提交() { /* 对应 ⚠️ 金额校验 */ }
```

### 44.6.4 上下文地图 → 微服务/模块边界

订单上下文（独立演进）→ 微服务 `order-service`；库存上下文 → `inventory-service`；支付上下文 → `payment-service`（这正是第 32 章 mall-cloud 拆分的建模依据）。上下文间用第 43 章的事件 + 第 46 章 Saga 做最终一致。

## 44.7 常见坑与误区

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| **开发反客为主** | 开发贴便签、业务只在旁边点头 | 业务专家必须亲自贴，开发只提问 |
| **把"功能"当"事件"** | 贴"提交订单"（动词原形） | 过去式！`订单已提交`；动作是命令不是事件 |
| **一上来就贴到表** | 开始讨论 `t_order` 加不加字段 | 先建模后建表，表是落地的最后一环 |
| **事件太粗/太细** | 只贴"订单已处理"；或贴"金额已加1分" | 粒度 = "业务专家能确认发生过"即可 |
| **一次风暴想覆盖全部** | 10 个上下文一次贴完 | 先 Big Picture 划界，再逐个 Design Level |
| **忽略异常分支** | 墙上一马平川全是 happy path | 刻意追问"失败了怎么办/超时怎么办" |
| **墙上共识不等于落地** | 风暴结束即散场，代码还是老样子 | 8 小时风暴 + 48 小时代码骨架，趁热打铁 |
| **没有记录** | 便签一撕全没了 | 拍照 + 记录员当天整理纪要 |
| **把风暴当评审会** | 变成汇报 PPT、没人动手 | 全员动手贴，嘴比手多的环节直接砍 |

## 44.8 从事件风暴到完整代码的落地路径

```
事件风暴产出（墙）                         代码落地（仓库）
─────────────────                         ─────────────────
上下文地图 ──► 模块/服务划分（防腐层、共享内核）
聚合簇    ──► 聚合根 + 实体 + 值对象（第 41 章）
事件清单  ──► 领域事件类（过去式命名，第 43 章）
命令清单  ──► 应用服务 + 命令对象
规则白贴  ──► 聚合内不变量 + 单元测试 + 状态机 Guard（第 42 章）
读模型    ──► 读模型 DTO + 投影器 / 仓储查询（第 43 章）
```

> **落地建议**：工作坊当天结束前，开发小组直接基于事件墙写**聚合骨架 + 规则测试**（2 天内的"趁热期"），否则墙上的共识会迅速蒸发回每个人的脑袋里。

## 44.9 练习与思考

1. **练习 A（Big Picture）**：选一个你熟悉的业务（订餐、打车、酒店预订），按 44.3 方法画 Big Picture，产出 3~5 个限界上下文及依赖箭头；
2. **练习 B（Design Level）**：对其中"订单"上下文走八步法，产出事件清单（≥10 个，含 3 个以上异常分支事件）、命令清单、聚合划分；
3. **练习 C（规则→代码）**：把练习 B 的白便签规则翻译成聚合根方法 + 单元测试（参照 44.6.3）；
4. **练习 D（对照）**：把工作坊产物与第 31 章 mall-boot 订单模块对照——哪些规则在现状代码里**丢失**了（第 40 章"知识丢失"），哪些聚合应该拆开。

## 44.10 面试考点

1. 事件风暴解决了什么问题？为什么它是 DDD 落地第一步？

9. 事件风暴常见的坑（至少三个）。
