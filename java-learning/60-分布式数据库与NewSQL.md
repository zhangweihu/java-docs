# 第六十章 分布式数据库与 NewSQL（告别分库分表？）

> 本章目标：前几章讲"用 MySQL 分库分表对抗数据增长"，本章跳出这个框架——理解 NewSQL 分布式数据库的诞生逻辑、TiDB 的架构原理（存储/计算/调度三层分离）、Java 应用接入 TiDB 的零改造体验，对比 OceanBase 与云数据库，并用一张决策树回答终极问题："单机 MySQL、分库分表、NewSQL、云数据库，我的场景该选哪个？" 同时收官 60 章数据专题。
>
> 前置知识：第五十七章 分库分表、第五十八章 数据库高可用、第五十九章 数据迁移、第三十三章 MySQL、第二十五章 MySQL 调优。

## 60.1 分库分表的痛，就是 NewSQL 的出发点

回顾 57 章，分库分表虽然解决了容量/写并发，但引入了系统性复杂度：

| 分库分表的痛 | 具体表现 |
| --- | --- |
| 业务侵入 | 分片键约束所有查询、跨片查询/事务是禁区 |
| 运维复杂 | 扩容要搬数据（59 章）、拓扑管理、主从 × 分片 |
| 能力受限 | 分布式事务、全局唯一、跨片 JOIN 都要绕路 |
| 技术债务 | 分片规则一旦定死，几乎无法回退 |

**NewSQL 的核心承诺**：像用单机数据库一样使用，却拥有水平扩展 + 高可用的分布式能力——**分片/扩缩容/故障转移由数据库自己完成**，应用无感知。

> **一句话记忆**：分库分表是"应用替数据库分片"，NewSQL 是"数据库自己分片"。前者你背着复杂度走，后者数据库帮你扛。

## 60.2 NewSQL 演进：三个流派

```
NewSQL 三条技术路线：
① 全新架构（TiDB/CockroachDB）：存储-计算分离，从零设计分布式
② 透明中间件（Vitess/ShardingSphere-Proxy）：在 MySQL 之上加分布式层
③ 云数据库（PolarDB/Aurora）：共享存储 + 计算弹性，单写多读扩展
```

| 流派 | 代表 | 定位 | 与 MySQL 兼容度 |
| --- | --- | --- | --- |
| 分布式存储计算 | TiDB、CockroachDB | 原生分布式 OLTP | 高（TiDB 兼容 MySQL 协议） |
| 中间件 | Vitess、MyCat、ShardingSphere | MySQL 水平扩展 | 高（就是 MySQL） |
| 云原生 | Aurora、PolarDB | 单写多读弹性 | 极高（兼容 MySQL/PG） |

## 60.3 TiDB 架构原理：三层分离

TiDB 是 NewSQL 的代表，理解它的架构就能理解整个流派：

```
                  SQL 客户端（JDBC/MyBatis，连接串 = MySQL 协议）
                            │
                 ┌──────────▼──────────┐
                 │   TiDB Server（计算层） │  无状态、SQL 解析/优化/执行、跨节点聚合
                 └──────────┬──────────┘
          SQL 下推          │        结果汇总
   ┌───────────────────────┴───────────────────────┐
   │                TiKV（存储层）                     │  数据按 Region 分片（默认 96MB/片）
   │    Region 0..N（多副本 Raft 同步，故障自动选举）     │  LSM-Tree 存储引擎
   └───────────────────────┬───────────────────────┘
                           │  Region 调度（分裂/合并/迁移/均衡）
                 ┌──────────▼──────────┐
                 │  PD（Placement Driver） │  全局时钟（TSO）+ Region 元数据 + 调度中心
                 └─────────────────────┘
```

### 60.3.1 三个核心设计

| 设计 | 说明 | 解决的问题 |
| --- | --- | --- |
| **Region 自动分片** | 数据自动按行切成 96MB 的 Region，Region 可分裂/合并 | 分库分表的"分片"由数据库自动完成 |
| **Raft 多副本** | 每 Region 3 副本，多数派写成功即提交 | 高可用 + RPO=0，故障自动选主 |
| **PD 调度** | 按存储/负载自动搬 Region | 扩缩容、负载均衡全自动 |

### 60.3.2 与传统 MySQL 对比

| 维度 | MySQL + 分库分表 | TiDB |
| --- | --- | --- |
| 分片 | 人工设计分片键、业务感知 | Region 自动，应用无感知 |
| 扩容 | 搬数据（59 章）、停机窗口 | 加节点，Region 自动迁移，不停机 |
| 高可用 | MHA/MGR/Orchestrator 搭建 | Raft 内置，RPO=0 |
| 分布式事务 | 应用层方案（46 章） | 内置（两阶段提交 + 全局时间戳） |
| 跨片查询/JOIN | 禁区 | 原生支持（分布式执行器） |
| 运维复杂度 | 高（拓扑/分片/迁移） | 低（扩缩容自动化） |

> **面试题**：TiDB 怎么解决"分库分表的扩容难题"？答：数据切成 Region 由 PD 调度，扩容 = 加 TiKV 节点 + Region 自动迁移，扩容过程应用零感知；且多副本 Raft 保证故障自动转移，RPO=0。

## 60.4 Java 接入 TiDB：零改造体验

TiDB 兼容 MySQL 协议，**JDBC 连接串几乎不改**：

```yaml
# Spring Boot + MyBatis-Plus 直接连 TiDB
spring:
  datasource:
    driver-class-name: com.mysql.cj.jdbc.Driver   # 还是 MySQL 驱动
    url: jdbc:mysql://tidb-host:4000/mall?rewriteBatchedStatements=true
    username: root
    password: root
```

```java
// 业务代码零感知：没有分片键、没有分布式 ID、直接 JOIN 和事务
@Transactional
public void createOrder(Order order, List<OrderItem> items) {
    orderMapper.insert(order);            // 任意写，数据库自动分片
    for (OrderItem item : items) {
        orderItemMapper.insert(item);     // 跨"片"也在同一事务（分布式事务内置）
    }
    userMapper.updateBalance(order.getUserId());  // 关联更新无压力
}
```

**接入注意事项**：

| 项 | 说明 |
| --- | --- |
| 连接池 | 复用 HikariCP，`rewriteBatchedStatements=true` 开启批量 |
| 慢 SQL | TiDB 自带 dashboard，慢查询可视化 |
| 自增 ID | 支持 `AUTO_INCREMENT`（内部处理），也可用雪花 |
| 与 MySQL 差异 | 部分语法/函数差异需兼容性测试（如 `SELECT ... FOR UPDATE` 行为） |

> **迁移路径**：现有 MySQL → TiDB 可用官方迁移工具（Dumpling 全量 + TiCDC 增量），本质上就是 59 章的"全量+增量+双写"方法论，目标端换成 TiDB。

## 60.5 OceanBase 与国产分布式数据库

| 数据库 | 架构特点 | 典型场景 |
| --- | --- | --- |
| **OceanBase**（蚂蚁） | 存储-计算分离、Paxos 多副本、兼容 MySQL/Oracle 语法 | 金融核心（支付宝/网商银行） |
| **TDSQL**（腾讯） | 分布式事务强一致、兼容 MySQL | 金融、政务 |
| **GaussDB**（华为） | 分布式 + 集中式双形态 | 政企、电信 |
| **PolarDB**（阿里云） | 共享存储、一写多读、计算弹性 | 云上 MySQL 兼容扩展 |

> **选型提示**：国产数据库选择的核心维度——**语法兼容度、生态工具链、团队熟悉度、信创合规要求**。业务系统迁移的首要成本不是数据，而是 SQL 方言和运维习惯。

## 60.6 终极选型决策树：我的场景该用哪个？

```
数据量/并发评估
├── 单表 < 500 万、QPS < 2000
│     └──► 单机 MySQL（25/33 章优化足够）✅ 别折腾
├── 读多写少、单库能扛
│     └──► 读写分离（33 章）✅
├── 数据量大/写并发高
│     ├── 团队熟悉 MySQL、愿意接受复杂度
│     │     └──► 分库分表（57 章）⚠️ 慎重，复杂度终身伴随
│     ├── 想要"应用无感知的水平扩展"
│     │     └──► TiDB 等 NewSQL ✅ 新项目优先考虑
│     └── 在云上、业务弹性大
│           └──► 云数据库（Aurora/PolarDB）✅ 省心
└── 关键判断：现有系统改造 vs 全新系统
      ├── 老系统 MySQL + 分库分表已稳定 → 维持（迁移成本大于收益）
      ├── 老系统要大规模扩容 → 评估用 59 章方法论迁到 TiDB
      └── 新系统 → 默认考虑 NewSQL，省掉分库分表复杂度
```

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 新项目、预期数据量大 | TiDB/云原生 | 一开始就避免分库分表复杂度 |
| 已有 MySQL 分库分表稳定运行 | 维持现状 | 迁移成本大于收益，别为技术炫技 |
| 强金融监管、国产化要求 | OceanBase/TDSQL | 信创合规 + 金融级一致性 |
| 中小业务、云上 | 云数据库 | 托管高可用，性价比高 |

> **一句话记忆**：能单机就别分片，能 NewSQL 就别手写分片，老系统稳定就别折腾。**技术选型的本质是复杂度管理**——选一个能把复杂度藏起来的方案，而不是选一个"看起来最强"的方案。

**面试速查**：

| 问题 | 一句话答案 |

| NewSQL 和分库分表本质区别？ | 分片由数据库自动完成 vs 应用替数据库分片 |

### 本章小结

- **出发点**（60.1）：分库分表的复杂度痛点催生 NewSQL；
- **流派**（60.2）：全新架构 / 透明中间件 / 云数据库三条路线；
- **TiDB**（60.3~60.4）：Region 自动分片 + Raft 副本 + PD 调度，JDBC 零改造接入；
- **国产化**（60.5）：OceanBase/TDSQL 面向金融信创，兼容度与生态是迁移关键；
- **选型**（60.6）：单机 → 读写分离 → 分库分表 / NewSQL / 云数据库，复杂度管理优先；
- **收官**（60.7）：57~60 数据专题形成"拆分 → 高可用 → 迁移 → 替代"完整闭环。
