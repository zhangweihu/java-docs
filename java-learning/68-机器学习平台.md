# 第六十八章 机器学习平台（从特征到模型服务的工程化）

> 本章目标：第六十一~六十七章把数据"管起来、算得快"，本章让数据开始"预测"——以 Java 后端视角掌握机器学习平台的工程全景：ML 平台分层架构、特征平台（特征即服务）、训练（Spark MLlib/Flink 在线学习）、模型服务与 Java 工程集成（HTTP/gRPC/PMML/ONNX）、MLOps 全流程（实验/版本/发布/监控），并用一个"订单流失预警 + 推荐召回"实战把整条链路串起来。
>
> 前置知识：第六十三/六十六章（Spark 与离线数据）、第六十一/六十二章（Flink 实时特征）、第二十九章 Redis（特征缓存）、Spring Boot（第九章）。

## 68.1 机器学习平台全景：算法之外，工程才是主战场

算法工程师往往只占 ML 项目的 20% 工作，剩下 80% 是"数据、特征、训练、上线、监控"的工程问题。**机器学习平台就是把这条链路标准化、产品化**：

```
┌────────────────────────────────────────────────────────┐
│ ⑤ 应用层：推荐 / 风控 / 搜索 / 报表预测 / 大模型 Agent     │
├────────────────────────────────────────────────────────┤
│ ④ 服务层：模型服务（TensorFlow Serving / Triton）         │
│           特征服务（在线特征 API）                        │
├────────────────────────────────────────────────────────┤
│ ③ 训练层：训练平台（Spark MLlib / PyTorch / XGBoost）     │
│           实验管理（MLflow）                            │
├────────────────────────────────────────────────────────┤
│ ② 特征层：特征平台（离线特征湖 / 在线特征 Redis）          │
├────────────────────────────────────────────────────────┤
│ ① 数据层：ODS/DWD（66 章 Hive）/ 湖（67 章 Iceberg）      │
│           实时（62 章 Flink）                            │
└────────────────────────────────────────────────────────┘
```

> **核心洞察**：**机器学习平台 = 特征平台 + 训练平台 + 模型服务 + MLOps**。对 Java 后端工程师，最重要的两个接口点是"特征如何供给"和"模型如何被调用"。

## 68.2 特征平台：特征即服务

模型的输入是特征，而特征的生产是"离线 + 实时"两套系统的老难题：**离线训练用的特征和线上推理用的特征必须完全一致**（否则训练 A、上线 B，效果崩盘——这叫"特征一致性"问题）。

| 特征类型 | 例子 | 生产链路 |
| --- | --- | --- |
| 离线特征 | 用户 30 天消费总额 | Spark/Hive 每日算好，落 Hive/Iceberg（66/67 章） |
| 实时特征 | 用户最近 5 分钟点击数 | Flink 窗口实时算，写 Redis（62/29 章） |
| 维表特征 | 用户等级、商品类目 | 数仓维表，双写离线湖 + 在线缓存 |

```
特征平台架构（特征一致性关键）：
离线侧：Hive/Iceberg 特征表（历史全量，训练用）
   └─ 同一套特征定义 ──► 在线侧：Redis/特征服务 API（实时取数，推理用）
   （离线特征也写 Redis 一份，线上能查到一样的值 = 训练/线上同特征）
```

**特征一致性铁律**：

1. 特征定义统一（同一 SQL 逻辑，离线 Spark 算、在线 Flink/Redis 同口径）；
2. 离线特征表每日也同步到在线存储（回刷时线上能取到历史值）；
3. 上线新特征必须离线回填历史（否则训练样本缺特征）。

> **Java 视角**：特征服务就是一个高吞吐的 Redis/缓存查询服务（29 章缓存治理的实战场景），关键在设计"特征 key"：`user:{id}:feat:30d_gmv`、`item:{id}:feat:ctr`。

## 68.3 训练：Spark MLlib 与 Flink 在线学习

### 离线批量训练（Spark MLlib，Java 可直接调用）

```java
import org.apache.spark.ml.classification.RandomForestClassifier;
import org.apache.spark.ml.feature.VectorAssembler;
import org.apache.spark.sql.Dataset;
import org.apache.spark.sql.Row;

// 读特征表（Hive/Iceberg，66/67 章）
Dataset<Row> train = spark.sql(
    "SELECT user_id, 30d_gmv, 30d_order_cnt, avg_amount, is_churn FROM dws_user_feature WHERE dt='2026-08-23'");

// 特征向量化：把多个特征列合成一个向量列
VectorAssembler assembler = new VectorAssembler()
        .setInputCols(new String[]{"30d_gmv", "30d_order_cnt", "avg_amount"})
        .setOutputCol("features");

Dataset<Row> data = assembler.transform(train);

// 训练随机森林（流失预测二分类）
RandomForestClassifier rf = new RandomForestClassifier()
        .setLabelCol("is_churn").setFeaturesCol("features")
        .setNumTrees(100).setMaxDepth(10);
var model = rf.fit(data);

// 保存模型 + 注册到模型仓库
model.write().overwrite().save("hdfs:///models/churn_prediction/v12");
```

### 实时在线学习（Flink：模型随数据滚动更新）

```scala
// Flink SQL 风格：实时窗口算特征 → 增量更新模型参数（逻辑示意）
// 场景：点击率模型，每 5 分钟用最近 1 小时数据重训/增量更新
INSERT INTO model_param_sink
SELECT item_id, COUNT(*) AS click_cnt, SUM(label) AS pos_cnt,
       SUM(label) / COUNT(*) AS cur_ctr
FROM click_stream
GROUP BY TUMBLE(ts, INTERVAL '5' MINUTE), item_id;
```

> **训练分层总结**：**离线批量（Spark，T+1 重训）+ 近线增量（Flink 窗口重训）+ 在线实时（上线后在线学习）**三档，延迟与算力成反比。多数业务"每日离线重训 + 实时特征推理"就够。

## 68.4 模型服务：Java 怎么调用模型

训练完的模型要变成"能被 Java 业务调用的服务"，有四条主流路径：

| 方式 | 原理 | 延迟 | 适用 |
| --- | --- | --- | --- |
| **HTTP/gRPC 调模型服务** | TensorFlow Serving / Triton 独立部署，Java 用 HTTP/gRPC 调用 | 毫秒~十毫秒 | **生产主流**，模型独立升级不重启业务 |
| **Java 直接加载（PMML/ONNX）** | 模型导出 PMML/ONNX，Java 用 jpmml/onnxruntime 库本地推理 | 亚毫秒 | 轻量场景，特征简单、模型小 |
| 规则/分桶近似 | 把模型预测规则化成查表/评分公式 | 微秒 | 极低延迟风控场景 |
| 大模型 API | 调外部 LLM/Embedding 服务 | 百毫秒+ | 大模型应用（68.7） |

### 路径一：Java 通过 gRPC/HTTP 调用模型服务（生产标准）

```java
// 伪代码：Java 业务调模型服务（TensorFlow Serving REST）
// 特征拼好 → POST /v1/models/churn/versions/12:predict
String json = """
    {"instances": [{
        "30d_gmv": 1280.5,
        "30d_order_cnt": 3,
        "avg_amount": 426.8
    }]}
    """;
HttpResponse resp = httpClient.post("http://tf-serving:8501/v1/models/churn:predict")
        .body(json).send();
// 返回 {"predictions": [[0.87]]} → 流失概率 87%
double churnProb = parsePredictions(resp.body())[0];
if (churnProb > 0.8) { sendCouponAlert(userId); }
```

### 路径二：Java 本地推理（PMML/ONNX，轻量场景）

```java
// PMML：模型导出成标准 XML，Java 用 jpmml 库本地打分
import org.jpmml.evaluator.Evaluator;
import org.jpmml.evaluator.ModelEvaluatorBuilder;
import java.io.FileInputStream;

Evaluator evaluator = new ModelEvaluatorBuilder()
        .loadModel(new FileInputStream("models/churn_v12.pmml"))
        .build();

Map<String, Object> input = Map.of(
        "30d_gmv", 1280.5, "30d_order_cnt", 3.0, "avg_amount", 426.8);
Map<String, Double> result = evaluator.evaluate(input);  // 返回概率值
```

> **选型建议**：模型大、特征多、要独立扩展 → 独立模型服务（gRPC/HTTP）；模型小、要求极低延迟、不想多运维一套 → PMML/ONNX 本地推理。

## 68.5 MLOps：实验、版本、发布、监控

模型和代码一样要"版本管理、灰度发布、监控告警"。**MLOps = 把 DevOps（53 章）的工程纪律搬到机器学习**：

| 环节 | 传统算法做法 | MLOps 做法 |
| --- | --- | --- |
| 实验 | 本地跑一堆 notebook，靠记忆 | **MLflow 实验跟踪**：参数/指标/产物自动记录 |
| 模型版本 | 文件乱存 `model_final_v2(1).pkl` | **模型仓库**：版本 + 血缘（用哪个特征版本训的） |
| 发布 | 手动换文件重启 | **灰度/金丝雀**：先切 5% 流量，效果达标再全量（50 章 Istio 思路） |
| 监控 | 上线后不管 | **数据漂移/效果监控**：线上特征分布变了要告警（48 章可观测性） |
| 回滚 | 找旧文件 | 一键回滚到上个模型版本 |

```
一次完整的 MLOps 闭环：
① 特征版本 v3 上线（离线回填 + 在线同步）
② MLflow 记录实验：v12 模型 AUC 0.86 > v11 的 0.84
③ 模型入库 v12，走 CI：离线评测通过
④ 金丝雀发布：5% 流量 → 观察线上 CTR +5% → 全量
⑤ 持续监控：每日特征漂移检测，异常自动告警/回滚 v11
```

> **数据漂移（Data Drift）是模型退化的头号杀手**：业务变了，训练时的特征分布和线上实际分布越走越远，模型悄悄失效。监控"线上特征分布 vs 训练分布"是 MLOps 的必修课。

## 68.6 实战：Java 后端接入"流失预警"全链路

一个完整案例，把 68.1~68.5 串起来（衔接 62/63/66/67 章数据层）：

```
① 数据：订单明细入 Iceberg 湖（67 章实时 UPSERT）
② 特征：Spark 每日算 30d_gmv/order_cnt/avg_amount（68.2）→ Hive 特征表 + Redis 在线副本
③ 训练：Spark MLlib 随机森林训练流失模型（68.3）→ MLflow 记录 → 模型仓库 v12
④ 服务：TensorFlow Serving 加载 v12，暴露 gRPC（68.4）
⑤ 应用：Java 订单服务，下单后调特征服务拿特征 → 调模型服务算流失概率
        → 概率 > 0.8 触发优惠券发放（Spring 定时/事件，9/16 章）
⑥ 监控：每日特征漂移 + 效果回灌（68.5），异常回滚 v11
```

```java
@Service
public class ChurnService {
    private final FeatureClient featureClient;  // Redis/特征服务
    private final ModelClient  modelClient;     // gRPC 模型服务

    // 下单完成后调用：评估流失风险并触发策略
    public void onOrderPaid(Long userId) {
        Map<String, Double> feats = featureClient.getUserFeatures(userId); // 特征
        double prob = modelClient.predict("churn_v12", feats);             // 推理
        if (prob > 0.8) {
            couponService.sendWelcomeBackCoupon(userId);                   // 策略
        }
    }
}
```

> **Java 工程师在这个链路里的分工**：数据与特征工程、模型服务接入、策略落地、监控——**模型训练（算法）只是其中一环**，这正是本章想传达的"平台思维"。

## 68.7 推荐系统与大模型：平台的两种扩展

### 推荐系统（传统 ML 的经典形态）

```
推荐链路：召回（粗筛 1 万 → 500）→ 排序（精排 CTR 预估）→ 重排（去重/多样性）
 召回：协同过滤 / 向量召回（Embedding，Redis 存向量）
 排序：CTR 模型（特征 = 用户特征 + 商品特征 + 上下文，68.2 特征平台现成）
 重排：规则 + 业务约束（广告位、新品加权）
```

### 大模型时代：平台如何演进

| 能力 | 传统 ML 平台 | + 大模型（LLM） |
| --- | --- | --- |
| 特征 | 结构化特征 | + 向量特征（Embedding） |
| 训练 | 小模型调参 | 微调（Fine-tune）/ RAG 检索 |
| 服务 | 模型服务 | + LLM 网关、Prompt 管理 |
| 新增 | — | 向量数据库（Milvus/ES dense vector，20 章 ES 可扩展） |

> **大模型的工程化同样复用本章平台骨架**：数据（语料清洗入库）→ 特征（Embedding 向量化）→ 服务（LLM 网关）→ 监控（幻觉/效果评估）。Java 侧重点是 **RAG 链路**：文档 → 切块 → Embedding → 向量库 → 检索 → 拼 Prompt → 调 LLM。

## 68.8 生产踩坑清单与面试速查

**踩坑清单**：

- [ ] 特征不一致：训练用离线特征、线上用实时特征，两边口径不同，模型线上崩（68.2 铁律）；
- [ ] 上线新特征不回填历史：训练样本缺列，模型训练直接失败或带病上线；
- [ ] 模型文件乱存：`model_v12_final_真的最终版.pkl` 没有版本仓库，回滚靠猜（MLflow/模型仓库）；
- [ ] 直接全量切新模型：不灰度，效果差一晚上才能发现（先 5% 流量）；
- [ ] 上线后不监控数据漂移：业务变了模型悄悄失效，等业务投诉才发现（每日漂移检测）；
- [ ] Java 直连模型训练框架：把训练/推理混在一个服务，升级模型要重启业务（模型独立服务化）；
- [ ] 推理延迟无预算：gRPC 没连接池、特征查询串行，单次预测 200ms 拖垮主链路（并行化 + 缓存）。

**面试速查**：

| 问题 | 一句话答案 |
| --- | --- |
| 机器学习平台包含什么？ | 特征平台 + 训练平台 + 模型服务 + MLOps |
| 特征一致性是什么？ | 训练与线上用同一套特征逻辑与取值，否则模型带病上线 |
| Java 怎么调模型？ | 独立模型服务 gRPC/HTTP；轻量用 PMML/ONNX 本地推理 |
| 离线/在线训练怎么配合？ | 离线 Spark 每日重训 + Flink 近线增量 + 实时在线学习三档 |
| MLOps 管什么？ | 实验跟踪、模型版本、灰度发布、数据漂移监控、回滚 |
| 推荐系统主链路？ | 召回 → 排序（CTR）→ 重排 |
| 大模型怎么和平台结合？ | 平台骨架复用：数据→向量特征→LLM 网关→监控，RAG 是主流落地 |
