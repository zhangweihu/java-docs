# 第五十八章 数据库高可用与容灾（让数据库永不成为单点）

> 本章目标：第三十三章讲了主从复制与读写分离的"基础用法"，本章讲"高可用体系"——吃透 MySQL 复制原理的深度（异步/半同步/组复制）、主从延迟的成因与治理、主流高可用方案（MHA/MGR/Orchestrator）对比与选择、跨机房多活容灾架构（RPO/RTO），并建立完整的备份恢复体系（全量/增量/PITR）与数据校验机制，能设计一个"数据库挂了业务照跑、机房挂了数据不丢"的生产方案。
>
> 前置知识：第三十三章 MySQL（主从复制/读写分离）、第二十五章 MySQL 调优、第四十七章 高可用与容灾（RPO/RTO）、第五十七章 分库分表。

## 58.1 高可用的目标：从"数据库不挂"到"挂了也不出事"

先建立度量体系（与 47 章衔接）：

| 指标 | 含义 | 高可用目标 |
| --- | --- | --- |
| **RPO**（Recovery Point Objective） | 最多丢失多少数据（时间） | 越低越好：RPO=0 表示零丢失 |
| **RTO**（Recovery Time Objective） | 最长恢复多久 | 越低越好：RTO=分钟级 |
| 可用性 | 年度可用时间 | 99.99% ≈ 年宕机 52.6 分钟 |

```
故障金字塔（按 RTO/RPO 从轻到重）：
节点故障（主库宕机）→ RPO≈0 RTO=秒~分钟（主从切换）
机房故障（整机房断电）→ RPO≈秒 RTO=分钟（跨机房切换）
城市级灾难 → RPO=分钟~小时 RTO=小时级（灾备恢复）
```

> **一句话记忆**：高可用 = 冗余 + 快速切换；容灾 = 数据不丢 + 能恢复。先问"能接受丢多少"（RPO），再问"能接受停多久"（RTO），方案随之确定。

## 58.2 复制原理深化：异步/半同步/组复制

主从复制的三个层次直接决定 RPO：

### 58.2.1 异步复制（MySQL 默认）

```
主库 commit → 写 binlog → 返回成功（不等从库）
从库 IO 线程拉 binlog → relay log → SQL 线程回放
```

- **RPO 不可控**：主库宕机瞬间，已提交但未同步的事务直接丢失。
- 适用于：读写分离（读延迟容忍）、非核心业务。

### 58.2.2 半同步复制（Semi-Sync）

```
主库 commit 前 → 等至少一个从库 ACK（收到 relay log）→ 才返回成功
```

- **RPO=0（至少一个从库有数据）**：主库宕机，从库数据完整。
- 代价：每次提交多一次网络往返 → 性能约降 10%~30%。
- 适用：核心业务主从，是"低成本保 RPO"的甜点位。

### 58.2.3 组复制（MGR，MySQL Group Replication）

```
多主/单主 组内节点，通过 Paxos 类协议（XCom）保证多数派一致性
```

- **RPO=0 + 自动选主**：组内多数派存活即可继续服务。
- 多主写入有冲突检测；单主模式（推荐）自动 failover。
- 适用：高可用自动化需求强、不想引入外部编排工具的团队。

| 复制模式 | RPO | 切换方式 | 复杂度 | 适用 |
| --- | --- | --- | --- | --- |
| 异步 | 不确定 | 手动/脚本 | 低 | 读写分离、非核心 |
| 半同步 | ≈0 | 手动/工具 | 低 | 核心业务主从 |
| 组复制 MGR | 0 | 自动（多数派） | 中 | 自动故障转移 |

## 58.3 主从延迟：成因与治理（高可用的隐形杀手）

主从延迟导致"读不到刚写的数据"，是高可用最容易翻车的地方：

| 成因 | 对策 |
| --- | --- |
| 大事务（单事务改百万行） | 拆小事务、批处理限行数 |
| 从库硬件弱/单线程回放 | 并行复制（`slave_parallel_workers`）、从库与主库同规格 |
| 慢 SQL 拖慢回放 | 25 章优化 + 从库加索引 |
| 写入流量过大 | 读写分离策略调整、分库分表（57 章） |
| DDL 阻塞回放 | 在线 DDL（gh-ost/pt-osc） |

**应用层兜底（最强手段）**：一致性读路由——写后带版本/时间戳，读请求若命中"刚写的数据"强制走主库，其余走从库。读多写少场景下把"读主"比例压到最低。

> **面试题**：主从延迟怎么解决？答：四层——优化 SQL/拆大事务（治本）、并行复制与硬件对齐（提速）、一致性读路由（应用兜底）、必要时半同步+短超时（折中）。永远不要指望"等等就好了"。

## 58.4 高可用方案对比：MHA / MGR / Orchestrator / 代理层

| 方案 | 原理 | 自动切换 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- | --- | --- | --- |
| **MHA**（Master High Availability） | 监控主库，故障时选数据最全的从库提升并补偿 binlog | 半自动（脚本可全自动） | 成熟、切换快（秒级）、不依赖特殊引擎 | 额外组件、不解决脑裂 | 传统主从 + 半同步 |
| **MGR** | 组内多数派自动选主 | 自动 | RPO=0、无需外部工具、内置 | 网络分区敏感、需合理超时 | 单主模式 + 自动切换 |
| **Orchestrator** | 管理复制拓扑，故障自动重接 | 自动（配合 consul/raft） | 拓扑可视化、可编排复杂拓扑 | 组件多、需运维投入 | 大规模复制拓扑 |
| **代理层**（ProxySQL/中间件） | 路由层感知故障并摘除 | 自动（依赖探活） | 应用无感知、读写分离一体 | 代理本身要 HA | 配合上述任一方案 |

**推荐组合（生产常见）**：

```
方案 A（主流）：MGR 单主（自动选主）+ ProxySQL 读写分离 + 应用连接池探活
方案 B（传统）：一主多从（半同步）+ MHA/Orchestrator 自动切换 + 代理层
方案 C（云原生）：托管云数据库（云厂商自动 HA，RPO≈0）+ K8s 部署应用
```

> **脑裂（双主同时写）是最大事故**：所有方案都要考虑——MHA 用 VIP/仲裁、MGR 靠多数派、代理层靠探活一致性。**任何自动切换都必须有"防双主"机制**。

## 58.5 应用层容错：切换时业务不停

数据库切换再快，应用层也要配合（高可用是端到端的）：

| 层 | 措施 |
| --- | --- |
| 连接池 | 配置连接验证（`test-on-borrow`）、池内连接自动重建、快速失败 |
| 重试 | 读写分离路由失败自动切主重试（幂等操作才重试） |
| 中间件 | ProxySQL 自动摘除故障节点；ShardingSphere 感知主从切换 |
| 缓存兜底 | 短暂降级：切换期间读缓存（数据允许最终一致时） |
| 监控 | 复制延迟、切换事件必须告警（48 章可观测性落地） |

## 58.6 跨机房容灾与多活：从"同城双活"到"两地三中心"

```
同城双活：两个机房同时读写，延迟低，单机房故障秒级切换
两地三中心：主中心（同城双活）×2 + 灾备中心 ×1（异地），RPO=分钟级
三地五中心（极致）：三地域、五中心，容忍城市级灾难，成本极高
```

| 容灾形态 | RPO | RTO | 成本 | 适用 |
| --- | --- | --- | --- | --- |
| 同城双活 | ≈0 | 秒~分钟 | 中 | 绝大多数互联网企业 |
| 两地三中心 | 分钟级 | 分钟~小时 | 高 | 金融/政务等强监管 |
| 三地五中心 | ≈0~秒 | 秒~分钟 | 极高 | 顶级金融/关键基础设施 |

**同城双活的两条路线**：

```
路线一：数据库层双写（MGR 跨机房）——应用双机房部署，数据组内多数派
路线二：业务层双活 + 数据按单元分片（单元化，如支付宝 LDC）
   单元化：流量按用户单元化路由，每个单元有自己的库，单元间异步同步
   → 优点：真正读写双活、扩容单元化；缺点：架构复杂度极高
```

> **面试题**：同城双活和异地多活有什么区别？答：同城双活 RPO≈0、RTO 秒级，靠数据库层同步（MGR/半同步）；异地多活 RPO 分钟级，靠异步复制或单元化，主要抗城市级灾难。延迟决定一切——同城光纤延迟 <1ms，异地物理延迟决定只能异步。

## 58.7 备份恢复体系：数据安全最后一道防线

高可用保证"故障切换"，**备份保证"逻辑错误/误删/勒索病毒"也能救**——这两件事必须同时存在：

### 58.7.1 备份类型

| 类型 | 形式 | 恢复速度 | 适用 |
| --- | --- | --- | --- |
| 逻辑备份 | SQL 语句（mysqldump） | 慢 | 小库、迁移 |
| 物理备份 | 数据文件拷贝（xtrabackup） | 快 | 大库、常规备份 |
| 全量备份 | 整个实例 | —— | 定期（每天） |
| 增量备份 | binlog 持续归档 | —— | 结合全量做 PITR |

### 58.7.2 PITR（时间点恢复）：误删数据的解药

```
恢复流程：
1. 取最近一次全量备份恢复出一个临时实例
2. 回放该备份之后的全部 binlog，直到"误操作前一刻"
   mysqlbinlog --stop-datetime='2026-08-23 10:00:00' binlog.000012 | mysql
3. 从临时实例导出被误删的数据，补回生产
```

### 58.7.3 备份最佳实践

| 实践 | 说明 |
| --- | --- |
| 3-2-1 原则 | 3 份副本、2 种介质、1 份异地 |
| 定期恢复演练 | **备份不演练等于没有备份**（季度一次全量恢复演练） |
| 备份监控 | 备份失败/超时/容量不足告警 |
| 加密 | 异地备份必须加密存储 |

> **血泪教训**：只依赖"高可用"而不做备份 → 主从同步一个 DROP TABLE 全挂（误操作会通过复制同步到所有节点）。**高可用防硬件故障，备份防人为/逻辑错误，两者缺一不可**。

## 58.8 数据校验与一致性修复

故障切换、复制延迟后，主从数据可能出现不一致，需要校验与修复：

| 工具 | 原理 | 用法 |
| --- | --- | --- |
| `pt-table-checksum` | 分块计算主从 checksum 对比 | 发现不一致的表 |
| `pt-table-sync` | 按主库数据修复从库 | 修复（建议在低峰执行） |
| 自定义对账 | 抽样/计数/金额汇总对比 | 业务级校验（对账任务） |

```
校验流程：pt-table-checksum 全表比对 → 定位差异表 → 评估影响 → pt-table-sync 修复
         → 复检 → 记录复盘（为什么会不一致：延迟？人为改从库？切换残留？）
```

## 58.9 生产设计检查清单与面试速查

**设计检查清单**：

- [ ] 核心库是否半同步/MGR（RPO 目标明确）？
- [ ] 主从延迟是否有监控与告警阈值？
- [ ] 自动切换是否有防脑裂机制？
- [ ] 应用连接池是否配置故障快速转移？
- [ ] 是否有 3-2-1 备份 + 季度恢复演练？
- [ ] PITR 是否可操作（binlog 归档完整）？
- [ ] 跨机房方案 RPO/RTO 是否与业务要求匹配？

**面试速查**：

| 问题 | 一句话答案 |
| --- | --- |
| 主从切换怎么做？ | MHA/Orchestrator/MGR 自动选主 + 代理层摘除 + 防脑裂 |
| RPO/RTO 怎么取舍？ | 业务要求定指标，半同步=低 RPO，异地异步=低成本大 RTO |
| 主从延迟怎么治？ | 拆大事务 + 并行复制 + 一致性读路由 |
| 高可用和备份的区别？ | 高可用防故障切换，备份防逻辑错误/误删，缺一不可 |
| 误删了全表怎么办？ | PITR：全量备份 + binlog 回放到误操作前 |
| 如何发现主从不一致？ | pt-table-checksum 校验 + 业务对账 |

### 本章小结

- **目标**（58.1）：RPO/RTO 先行，故障金字塔决定方案层级；
- **复制深化**（58.2~58.3）：异步/半同步/MGR 三档 RPO，延迟是隐形杀手；
- **方案选型**（58.4~58.5）：MGR 自动化 / MHA 传统 / 代理层兜底，应用层容错配合；
- **容灾**（58.6）：同城双活到两地三中心，延迟决定形态，单元化是终极形态；
- **备份**（58.7）：3-2-1 + PITR + 恢复演练，备份不演练等于没有；
- **校验**（58.8）：pt-table-checksum/sync 定期对账，切换后必查一致性。
