## 52.1 案例学习的方法论：别背架构图，学"决策链"

### 52.1.1 案例分析四步法

```
① 业务挑战：这个行业的本质矛盾是什么？（电商=大促峰值；金融=钱不能错；物流=实时调度）
```

## 52.2 电商行业：大促高并发与库存一致性

### 52.2.1 业务挑战

双 11 当天 1000 万 UV 涌入，秒杀商品 1 秒 10 万请求，库存只有 1 万件——**流量洪峰 + 超卖风险**是电商的两个生死题。

### 52.2.2 架构对策（三层削峰 + 最终一致）

```
用户 ──► CDN(静态资源) ──► API 网关(限流/防刷) ──► 秒杀网关(令牌桶)
                                                      │ 放行 1 万请求
                                                      ▼
                                              商品详情(Redis 缓存)
                                                      ▼
                                              库存扣减(Redis Lua 预扣)
                                                      │ 成功
                                                      ▼
                                              下单(异步化) ──► MQ ──► 订单服务(落库)
                                                              │      │
                                                              ▼      ▼
                                                        发优惠券     库存最终扣减(DB)+ 对账
```

1. **前置削峰**：答题/预约资格 → 把 10 万请求压成 1 万；
2. **Redis Lua 预扣**：原子扣减库存，超卖在 Redis 层就挡住（第 29/34 章）；
3. **异步化**：下单成功后丢 MQ，订单服务异步落库（第 16/27 章），页面先显示"已收到"；
4. **最终一致**：DB 扣库存失败 → MQ 重试 → 对账任务补偿（第 46 章 Saga/本地消息表思路）；
5. **容量**：按第 47 章公式压测算容量，K8s HPA 预热 + 弹性扩（第 49 章）。

### 52.2.3 踩坑复盘

- **缓存击穿**：秒杀商品缓存过期瞬间所有请求打 DB → 用"热点 key 永不过期 + 逻辑过期重建"（第 12/34 章）；
- **库存扣了但订单没生成**：Redis 预扣与 DB 落库必须对账兜底，否则退款投诉；
- **网关本身被打挂**：网关也要集群 + 限流前置，且别把业务逻辑塞进网关（第 36 章 Kong 边界）。

## 52.3 金融行业：钱不能错，一切皆可审计

### 52.3.1 业务挑战

支付/账务系统的底线：**一分钱都不能错**。但拆了微服务后，跨服务转账就是跨库事务——强一致与性能、合规审计（每一笔钱从哪来到哪去）与监管要求（报表、留痕）同时压上来。

### 52.3.2 架构对策（账务模型 + 事务 + 审计）

```
账务核心设计（第 40/41 章 DDD）：
  Account 聚合（不可变 Money 值对象、余额只增不减的流水表）
  转账 = 借 A 流水 + 贷 B 流水（两个聚合用领域事件联动）
  
一致性（第 46 章）：
  关键资金链路用 TCC 或 Seata AT（强一致优先）
  非关键链路用 Saga + 本地消息表（最终一致 + 对账任务兜底）

审计与合规（第 48 章 + 第 39 章建表）：
  流水表 append-only（禁 UPDATE/DELETE，改错只能冲正）
  全链路 traceId 可回溯；操作日志、审批流、脱敏加密（第 13 章）
```

### 52.3.3 踩坑复盘

- **用余额字段直接加减**：并发下丢更新 → 改为"流水驱动"，余额=流水汇总或乐观锁（第 17/33 章）；
- **长事务**：事务里调外部接口 → 把外部调用移出事务，用本地消息表过渡（第 46 章）；
- **对账缺失**：任何跨系统资金流转必须有 T+0/T+1 对账，对不上自动告警（第 48 章）。

## 52.4 物流出行行业：实时轨迹与调度匹配

### 52.4.1 业务挑战

上千万辆货车/骑手每秒上报位置，系统要在毫秒级完成：轨迹入库、围栏判断、订单派单、ETA 计算——**海量高吞吐实时数据 + 低延迟调度**。

### 52.4.2 架构对策（高吞吐管道 + 实时计算 + 缓存）

```
千万级终端 ──► 网关(Netty 长连接，第 26 章)
                  │
                  ▼
           Kafka(轨迹流，第 27 章)
                  ├─► 消费入库(轨迹表，分表)
                  ├─► 实时计算(围栏/偏移检测)
                  ├─► Redis Geo(最近车辆检索，第 34 章)
                  └─► 调度引擎(派单/ETA)
                          │
                          ▼
                  派单结果 ──► 推送(WebSocket/长连接)
```

- **Netty 扛长连接**：千万连接、百万 QPS 消息（第 26 章）；
- **Kafka 削峰解耦**：轨迹写库与实时计算互不阻塞；
- **Redis GEO**：周边车辆秒查，替代 DB 空间查询（第 34 章）；
- **状态机派单**：订单"待接单→已接单→配送中→完成"用状态机保证流转合法（第 42 章）。

### 52.4.3 踩坑复盘

- **消息乱序**：同一辆车轨迹乱序导致围栏误判 → 按设备 ID 分区 + 时间戳校验；
- **推送风暴**：大促/高峰所有骑手同时推送 → 推送限流 + 合并推送 + 客户端拉取兜底；
- **轨迹存储膨胀**：位置数据天量 → 冷热分层（热数据 Redis/近期库，冷数据归档对象存储，第 51 章 Serverless 批处理归档）。

## 52.5 社交内容行业：Feed 流与实时消息

### 52.5.1 业务挑战

10 亿用户的微博/抖音式 Feed：每个人刷到的都是"关注的人+推荐"的个性化列表，发布后要**秒级**出现在粉丝时间线上；同时 IM 消息要求实时到达。

### 52.5.2 架构对策（推拉结合 + 缓存 + 异步扩散）

```
用户发布内容
   │
   ├─► 写库(内容表) + 索引(ES，第 20 章)
   └─► 粉丝列表(Redis Set)
           │ 异步扩散(第 16/27 章)
           ▼
      给 10 万粉丝的 Feed 收件箱各 push 一条内容 ID
           │
           ▼
  用户刷 Feed = 拉取自己收件箱(Redis List) + 缓存内容详情
  大 V 粉丝过亿 → 改为"拉取模式"（刷到再合并，不 push）
```

- **推模式**：粉丝少的主播发布 → 直接写粉丝收件箱，读取 O(1)；
- **拉模式**：超大 V → 读者刷新时从"关注列表+发布表"动态合并，避免写放大；
- **真实系统是混合**：阈值以下推、以上拉 + 缓存时间线分页；
- **IM 实时性**：WebSocket 长连接 + 消息序号（第 26 章 Netty），离线消息 Redis/DB 暂存。

### 52.5.3 踩坑复盘

- **发一条微博 10 万次写**：扩散要异步 + 限流 + 失败补偿（重试/降级为拉）；
- **Feed 缓存穿透**：删除的内容仍被缓存 → 缓存标记删除 + 软删；
- **热 key 打爆 Redis**：明星动态同一时刻所有人刷 → 热点 key 多级缓存 + 本地缓存兜底（第 12/29 章）。

## 52.6 游戏行业：排行榜、会话与弹性扩缩

### 52.6.1 业务挑战

开服瞬间万人在线、排行榜实时变化、一场比赛一场活动流量像过山车——**弹性扩缩 + 低延迟读写**是核心诉求，且服务器资源按峰值备会被吐槽浪费。

### 52.6.2 架构对策（Redis 数据结构 + K8s 弹性 + Serverless 边缘）

```
游戏前端 ──► 接入网关
             │
             ├─► 战斗服/会话服（长连接，StatefulSet 稳定会话，第 49 章）
             ├─► Redis：排行榜 ZSet（第 34 章）、在线状态、活动计数
             └─► 活动/开服弹性：K8s HPA 秒级扩容 + 缩到基线
                  开服数据初始化：Serverless 函数批量预热缓存（第 51 章）
             
排行榜：ZADD 玩家分数 → ZREVRANGE 取 Top100（有序集合天然有序，毫秒级）
      分数相同用"分数+时间戳"组合编码保证公平
```

### 52.6.3 踩坑复盘

- **排行榜用 DB ORDER BY**：千万玩家必然超时 → 全部走 Redis ZSet，DB 只做持久化落库；
- **开服瞬间缓存雪崩**：所有玩家同时查同一批热点 → 预热 + 随机过期时间（第 12/34 章）；
- **会话断线重连**：战斗中途掉线 → 会话状态快照进 Redis，重连恢复（状态机第 42 章）。

## 52.7 大数据 AI 行业：数据管道与模型服务

### 52.7.1 业务挑战

业务系统的数据要汇聚成数仓做分析，AI 模型要特征、要训练、要上线服务——**数据从业务库到模型预测的全链路**，且要求"数据可回溯、模型可更新、服务可扩缩"。

### 52.7.2 架构对策（CDC + 消息管道 + Serverless 批处理）

```
业务库(MySQL) ──Canal 监听 binlog(第 38 章)──► Kafka
                                                ├─► 实时 ETL → 数仓(分析报表)
                                                ├─► 特征平台 → 特征库
                                                └─► 事件流 → 模型在线推理
定时/事件任务(报表、特征回填、模型重训)：
  ──► Serverless 函数按 Cron 触发（第 51 章），跑完即走、按量付费
模型服务：
  ──► K8s Deployment + HPA 按 QPS 弹性（第 49 章）
```

### 52.7.3 踩坑复盘

- **CDC 乱序/丢数据**：binlog 消费要幂等（第 27 章），对账任务定期补数；
- **特征不一致**：训练时特征与在线特征口径不一 → 特征平台统一版本管理；
- **模型服务冷启动慢**：Java 模型服务 JVM 启动慢 → GraalVM 原生镜像或预留实例（第 51 章）。

## 52.8 案例复盘方法论与面试话术

### 52.8.1 复盘五问（任何项目都可用）

```
1. 业务目标是什么？量化指标？（QPS、可用性、成本）
2. 最大的技术矛盾是什么？（峰值、一致性、实时性……）
3. 做了哪些架构决策？为什么？（每步给出"对比过的替代方案"）
4. 线上出过哪些事故？怎么解决的？（教训=加分项）
5. 如果再给一次机会，哪里会不同？（体现成长性）
```

### 52.8.2 面试/简历"案例话术"模板（STAR 变体）

> **S（场景）**：XX 电商大促，日订单峰值 500 万，秒杀单 SKU 瞬时 10 万 QPS；
> **T（任务）**：在不超卖的前提下保证 99.9% 可用性，下单体验 < 2s；
> **A（行动）**：Redis Lua 预扣库存挡超卖 → MQ 异步化下单削峰 → Seata 保证库存扣减与订单一致性 → 压测确定容量 + K8s HPA 弹性 + SkyWalking 全链路监控；
> **R（结果）**：大促零超卖、峰值下单成功率 99.95%，扩容响应 < 3 分钟。

**简历写法要点**：每个项目写 1 行背景 + 2~3 个技术亮点（含"为什么选它"）+ 1 个量化结果。
