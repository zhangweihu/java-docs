# 第五十一章 Serverless（无服务器架构：把运维交给平台）

> 本章目标：理解 Serverless 的本质（FaaS + BaaS）、事件驱动执行模型与按量付费模式，掌握函数计算平台（AWS Lambda/阿里云函数计算等）的核心概念与 Java 函数开发实战，吃透冷启动问题的成因与优化手段（GraalVM/预留实例/层），了解 Knative 如何在 K8s 上实现 Serverless，并能在"容器 vs Serverless"之间做出理性选型。
>
> 前置知识：第九/三十一章 Spring Boot、第三十五章 Docker 系统学习、第四十九章 K8s 深度专题（弹性伸缩）、第五十章 Service Mesh（云原生演进脉络）。

## 51.1 Serverless 的本质：连服务器都不用管

### 51.1.1 从"买服务器"到"只管代码"

```
传统部署： 买服务器 → 装 JDK → 部署 JAR → 扩容要买新机器 → 缩容要省成本
容器部署： 写 Dockerfile → K8s 调度 → HPA 自动扩缩 → 但仍要管节点池
Serverless：写一个函数 → 上传 → 完事（平台负责运行、扩缩、计费、高可用）
```

- **FaaS（函数即服务）**：把一段代码（函数）交给平台，平台在事件到来时运行它；
- **BaaS（后端即服务）**：认证、数据库、对象存储、消息队列等"后端能力"直接由平台提供，不用自己建服务；
- **Serverless 不是"没有服务器"**，而是"**你不感知服务器**"——扩缩容、补丁、高可用全是平台的事。

> **一句话记忆**：容器化把"机器"抽象成"资源"，Serverless 把"资源"也抽象掉，剩下只有**代码 + 事件**。

### 51.1.2 核心特征

| 特征 | 说明 |
| --- | --- |
| 事件驱动 | 函数由事件触发（HTTP 请求、消息、文件上传、定时器） |
| 按量付费 | 只按"实际执行时间 × 内存"计费，闲置 0 费用（毫秒级计费） |
| 自动扩缩 | 100 个请求 → 平台自动拉起 100 个实例；0 请求 → 缩到 0 |
| 无状态 | 函数默认不保留本地状态（状态放 Redis/DB/对象存储） |
| 有冷启动 | 空闲后首次调用要"启动运行时"，有秒级延迟 |

## 51.2 核心概念与执行模型

### 51.2.1 触发器：函数怎么被叫醒

| 触发器 | 场景示例 |
| --- | --- |
| HTTP/API 网关 | REST API（图片压缩、短链、Webhook） |
| 消息队列（MQ） | 消费订单事件做异步处理（发短信/对账） |
| 对象存储（OSS/S3） | 文件上传后自动触发（图片处理/转码/病毒扫描） |
| 数据库变更（CDC） | 数据变更流触发（同步到 ES/数仓） |
| 定时器（Cron） | 定时报表、数据清理、健康巡检 |

### 51.2.2 执行生命周期：冷启动 vs 热启动

```
            第一次调用                      后续调用
   ┌──────────────────────┐     ┌────────────────────┐
   │ 冷启动（秒级，贵）      │     │ 热启动（毫秒级）      │
   │ 拉起沙箱 → 加载运行时   │     │ 复用已存活的实例       │
   │ → 加载类/依赖 → 执行    │     │ → 直接执行 Handler    │
   └──────────────────────┘     └────────────────────┘
```

**冷启动延迟构成**（Java 尤其明显）：

1. 平台拉起容器/沙箱（毫秒~百毫秒）；
2. 启动 JVM（几百毫秒）；
3. 加载类与依赖（Spring Boot 全量启动可达秒级）；
4. 初始化连接池/首次建连。

> **对 Java 开发者最重要的警告**：直接把一个完整 Spring Boot 应用塞进函数，冷启动可能 3~8 秒——这通常是"Java 不适合 Serverless"论调的根源。见 51.4/51.5 的解法。

## 51.3 主流平台对比

| 平台 | 语言支持 | 特点 | 计费 |
| --- | --- | --- | --- |
| AWS Lambda | Java/Go/Python/Node… | 生态最成熟，事件源最全 | 按请求数 + 时长 |
| 阿里云函数计算 FC | Java/Python/Go/Node | 国内生态（OSS/MNS/日志服务打通），有预留实例 | 按调用 + 资源使用 |
| 腾讯云 SCF | 同上 | 与微信生态/云函数绑定 | 按调用 + 时长 |
| Azure Functions | C#/Java… | 与微软生态集成 | 按执行 + 请求 |
| 华为云 FunctionGraph | Java 等 | 政企场景 | 按调用 + 时长 |

**共同抽象**：只要理解"Handler 函数 + 事件对象 + 返回对象"三件套，各平台可迁移。

## 51.4 Java 函数开发实战

### 51.4.1 一个最小 Java 函数（阿里云 FC 风格）

```java
public class App implements Function<APIGatewayProxyRequestEvent, APIGatewayProxyResponseEvent> {

    @Override
    public APIGatewayProxyResponseEvent handleRequest(
            APIGatewayProxyRequestEvent event, Context context) {
        String name = event.getQueryStringParameters() != null
                ? event.getQueryStringParameters().getOrDefault("name", "world")
                : "world";
        String body = "{\"message\": \"Hello, " + name + "\"}";
        return new APIGatewayProxyResponseEvent()
                .withStatusCode(200)
                .withHeaders(Map.of("Content-Type", "application/json"))
                .withBody(body);
    }
}
```

- 上传方式：打包成 jar 上传，或直接提交源码平台帮你打包；
- **入口约定**：实现平台定义的 Handler 接口即可，平台负责实例化并调用。

### 51.4.2 Java 函数依赖管理三原则

1. **打 fat-jar 但别打 Spring Boot**：优先用轻量 Handler（Guice 都不必），必要时用 `Spring Cloud Function` 但配 `WebFlux`/精简上下文；
2. **依赖做"层"（Layer）**：公共依赖（JDK/常用库）放层，函数代码薄薄一层，上传快、冷启动快；
3. **避开重量级初始化**：连接池、Bean 扫描尽量放"初始化阶段"（静态块/构造器）而不是每次调用时做。

## 51.5 冷启动优化：Java 的五大手段

| 手段 | 原理 | 效果 |
| --- | --- | --- |
| **预留实例/预置并发** | 平台常驻 N 个实例 | 冷启动归零（有保底费用） |
| **GraalVM Native Image** | AOT 编译成原生可执行文件 | 启动 <100ms（Spring 生态用 Spring Native/Spring Boot 3 AOT） |
| **精简依赖与代码** | 少加载类 = 少启动时间 | 减少 30%~70% 启动时间 |
| **依赖层 + 缓存** | 公共依赖不随函数重新加载 | 减少下载/解压时间 |
| **尽量复用（温启动）** | 缩短空闲回收、提高实例复用 | 减少冷启动概率 |

> **实战结论**：关键 API 用"预留实例 + 精简依赖"；大批量低频计算用"按需 + 原生镜像"。**冷启动不是 Java 的死刑，是工程优化题。**

## 51.6 Serverless 架构模式：适合做什么

### 51.6.1 典型适用场景

| 模式 | 示例 |
| --- | --- |
| 事件型任务 | 图片/视频处理、转码、PDF 生成、报表 |
| 异步消息处理 | 订单事件 → 发通知/对账/风控评分 |
| 定时批处理 | 数据归档、缓存预热、定时清理 |
| 短 API / Webhook | 回调、短信验证码、第三方集成 |
| BaaS 组合 | 函数 + 对象存储 + 数据库 + 消息队列 组装完整业务 |

### 51.6.2 一个完整 Serverless 业务示例（图片上传处理）

```
用户 ──► API 网关（鉴权）──► 上传到 OSS（对象存储）
                                  │ OSS 事件触发
                                  ▼
                             函数A：压缩/裁剪/加水印 ──► OSS 新桶
                                  │
                                  ▼
                             函数B：生成缩略图 URL ──► 写数据库
                                  │
                                  ▼
                             函数C：发通知（短信/邮件）
```

- 全程**无一台你管理的服务器**；
- 每个函数独立扩缩：高峰只扩图片处理，不会拖着整个系统扩容；
- 费用 = 图片数量 × 处理时长，闲时几乎为 0。

## 51.7 Knative：在 K8s 上自建 Serverless

不想被云厂商锁定？Knative 把 Serverless 能力装进你自己的 K8s 集群：

```
Knative Serving（跑"服务"，按流量自动扩缩，可缩到 0）
   ├─ Revision：每次发布的不可变版本（天然灰度/回滚）
   ├─ Route：流量按百分比切给不同 Revision
   └─ 自动扩缩：KPA（Knative Pod Autoscaler），缩到 0 / 秒级拉起
Knative Eventing（事件驱动编排：把事件源接到函数/服务）
```

- 对比第 49 章 HPA：HPA 基于指标扩缩但**不会缩到 0**；Knative 主打"缩到 0 + 冷启动拉起"，所以叫"Serverless on K8s"；
- 适合：已有 K8s 集群、要 Serverless 体验又要数据主权/避免锁定的团队；
- 成本：多一套平台组件，运维复杂度上升——"Serverless 省的是业务运维，不是平台运维"。

## 51.8 选型决策：Serverless vs 容器 vs 单体

| 维度 | 单体/容器（K8s） | Serverless |
| --- | --- | --- |
| 上线速度 | 分钟~小时级 | 秒级（传代码即部署） |
| 成本模型 | 常驻资源费（低谷也付费） | 按量付费（闲时 0） |
| 弹性极限 | 受节点池限制 | 几乎无限（平台兜底） |
| 冷启动 | 无（常驻） | 有（需要优化） |
| 长任务 | 支持（常驻） | 受限（有超时上限，如 5~15 分钟） |
| 有状态应用 | 适合 | 不适合（无状态是铁律） |
| 锁定风险 | 低（可迁移） | 高（平台 API 绑定） |

**决策树**：

```
业务是长驻、高并发、有状态、要精调？     ──► K8s 容器（49/50 章方案）
业务是短任务、事件驱动、流量波动大？      ──► Serverless（函数计算）
要 Serverless 体验又不能上公有云？        ──► Knative（自建）
```

> **Java 工程师定位**：即使主业务留在 K8s，也值得把"异步事件处理、批处理、Webhook、媒体处理"这类任务切成 Serverless——**架构上减负，成本上省钱**，这是真实生产里最常见的混合姿势。

## 51.9 练习与思考

1. **练习 A**：在任意云函数平台创建一个"Hello"函数，接 HTTP 触发器，体验上传→触发→计费全流程；
2. **练习 B**：写一个图片压缩/PDF 生成函数，观察 OSS 事件触发的执行日志与冷/热启动耗时；
3. **练习 C**：用 GraalVM（或 Spring Boot 3 AOT）把一个小函数编译成原生镜像，对比冷启动前后的耗时数据；
4. **练习 D**：设计一个"订单事件 → 通知 + 对账"的 Serverless 链路，画出架构并标注每个函数的触发器与数据流；
