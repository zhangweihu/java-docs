# 第六十五章 大数据平台全景（从零搭建企业级数据平台）

> 本章目标：第六十一~六十四章学了各组件（Flink/Spark/ClickHouse/Doris），本章把它们装进一个"平台"——掌握大数据平台的分层架构（采集/存储/计算/分析/调度/治理）、每层的组件矩阵与选型、数仓 vs 数据湖 vs 湖仓一体的演进、元数据与数据质量管理、任务调度（DolphinScheduler/Airflow），并用一张"从 0 到 1 搭建数据平台"的实战路线图串联全书 61~64 章，收官 65 章体系。
>
> 前置知识：第六十一~六十四章（Flink/Spark/ClickHouse/Doris）、第二十七章 Kafka、第二十章 Elasticsearch、第三十三/二十五章 MySQL。

## 65.1 大数据平台全景：六层架构

```
┌─────────────────────────────────────────────────────────┐
│ ⑥ 应用层：BI 报表 / 大屏 / 数据服务 API / 机器学习          │
├─────────────────────────────────────────────────────────┤
│ ⑤ 治理层：元数据管理 / 数据质量 / 数据血缘 / 权限与安全      │
├─────────────────────────────────────────────────────────┤
│ ④ 分析层：OLAP（ClickHouse/Doris/ES） + Ad-hoc（Presto）  │
├─────────────────────────────────────────────────────────┤
│ ③ 计算层：批量（Spark/Hive）+ 实时（Flink） + 调度          │
│           （DolphinScheduler/Airflow）                    │
├─────────────────────────────────────────────────────────┤
│ ② 存储层：HDFS/对象存储（湖） + Hive 表（仓） + Kafka（流） │
├─────────────────────────────────────────────────────────┤
│ ① 采集层：binlog（Canal/Flink CDC）+ 日志（Filebeat）       │
│           + 批量（DataX/Flume）                            │
└─────────────────────────────────────────────────────────┘
```

| 层 | 解决的问题 | 核心组件 | 对应章节 |
| --- | --- | --- | --- |
| ① 采集 | 数据怎么进来 | Canal/Flink CDC、Filebeat/Logstash、DataX | 59/61/38 |
| ② 存储 | 数据放哪 | HDFS、Kafka、对象存储、Hive | 27 |
| ③ 计算 | 数据怎么算 | Spark、Flink、Hive | 61/62/63 |
| ④ 分析 | 结果怎么秒查 | ClickHouse、Doris、ES、Presto | 64/20 |
| ⑤ 治理 | 数据可不可信 | DataHub/Atlas、数据质量平台、Ranger | 65.5 |
| ⑥ 应用 | 数据怎么用 | BI（Superset）、大屏、数据 API | 62 |

> **一句话记忆**：数据平台的本质是"六层流水线"——采得进、存得住、算得快、查得秒、管得清、用得上。每一层都有多种组件，选型看规模与团队。

## 65.2 组件矩阵与选型：每个位置放什么

| 层 | 小规模（起步） | 中规模（业务增长） | 大规模（成熟平台） |
| --- | --- | --- | --- |
| 采集 | DataX + Canal | + Flink CDC、Filebeat | + 全域实时采集管道 |
| 存储 | Kafka + MySQL | + HDFS | + 数据湖（Iceberg） |
| 计算 | Flink + Spark | + Hive/Spark SQL | + 多引擎统一（Trino） |
| 分析 | ES | + ClickHouse | + Doris + Presto |
| 调度 | DolphinScheduler | + 血缘 | + Airflow/全托管调度 |
| 治理 | 表规范文档 | + 元数据平台 | + 数据质量 + 权限中心 |

**规模决策原则**：

```
数据量 < 100GB、查询简单 → 不用上大数据平台，MySQL + ES 足够（33/20 章）
数据量 TB 级 + 实时 + 分析 → 上最小闭环：Kafka + Flink + ClickHouse
多团队共享 + 数仓治理 → 补 Hive/Spark + 调度 + 元数据（本章平台化）
```

> **切忌堆组件**：平台每一层加一个组件就是一份运维成本。**从最小闭环起步，被业务逼着才加层**——这是平台演进的第一原则。

## 65.3 数仓 / 数据湖 / 湖仓一体：存储架构的演进

| 架构 | 是什么 | 特点 |
| --- | --- | --- |
| **数仓**（Warehouse） | 结构化数据、ETL 后入仓、Schema 先行 | 分析快、治理好；存"清洗后的数据" |
| **数据湖**（Lake） | 原始数据全量存放、Schema 后定 | 存所有原始数据（结构化/半结构化/非结构化）；查询慢、易变数据沼泽 |
| **湖仓一体**（Lakehouse） | 湖的存储 + 仓的治理与性能 | 统一存原始+加工，ACID + 快速分析 |

```
演进路径：
传统数仓（Hive 表 + Spark 算，63 章） 
  → 数据湖（HDFS 原始 + Iceberg/Delta Lake，解决"数据存不下/算不全"）
  → 湖仓一体（Iceberg 元数据 ACID + 分析引擎直查，当前主流趋势）
```

| 关键组件 | 作用 |
| --- | --- |
| **Iceberg / Delta Lake / Hudi** | 湖表格式：ACID、时间旅行、增量读 |
| HDFS / 对象存储（S3/OSS） | 湖的底层存储 |
| 元数据服务 | 表结构、分区、快照管理 |

> **面试题**：数据湖和数仓什么区别？答：数仓存"加工后的好数据"（Schema 先行、分析快）；数据湖存"所有原始数据"（Schema 后定、灵活但需治理）。湖仓一体 = 两者结合，同一份存储上既有原始又有分析就绪。

## 65.4 任务调度：DolphinScheduler / Airflow

数据平台没有调度就是"一堆不会自动跑的脚本"：

| 维度 | DolphinScheduler（国产） | Airflow |
| --- | --- | --- |
| 定义方式 | 可视化 DAG 拖拽 + 任务类型丰富 | Python 代码定义 DAG |
| 易用性 | 界面友好、中文生态 | 需 Python、上手稍陡 |
| 适合 | 数据平台团队（SQL/Shell/Spark/Flink 任务） | Python/ETL 工程化团队 |
| 核心能力 | 定时调度、依赖、告警、补数、工作流 | 同样都有 |

```
典型调度流（离线链路，配合 63 章）：
每天 02:00 采集 → 03:00 同步 ODS → 04:00 DWD 清洗 → 05:00 DWS 汇总
→ 06:00 ADS 出报表 → 07:00 数据质量校验 → 失败自动告警/重跑
```

> **衔接**：实时链路（62 章）由 Flink 作业自身持续运行，不需要调度器；**调度器管的是"定时批任务"**——离线数仓、报表生成、数据质量任务都在这里编排。

## 65.5 治理：元数据 / 数据质量 / 血缘 / 权限

| 治理维度 | 解决什么 | 工具/手段 |
| --- | --- | --- |
| **元数据管理** | "这个表哪来的、字段什么意思" | DataHub/Atlas + 表规范文档 |
| **数据血缘** | "这个指标的上游是谁"（改表影响分析） | 血缘采集（调度 DAG + SQL 解析） |
| **数据质量** | "数据对不对"（空值/重复/波动） | 质量平台：规则校验 + 告警 |
| **权限与安全** | "谁能看什么数据"（脱敏/分级） | Ranger/Sentinel、行级权限 |

**数据质量六性**（面试常考）：

| 维度 | 含义 | 校验示例 |
| --- | --- | --- |
| 完整性 | 无缺失 | 关键字段非空率 |
| 准确性 | 值正确 | 金额 = 明细求和 |
| 一致性 | 口径一致 | 实时与离线对账一致 |
| 及时性 | 按时产出 | 调度成功率、产出延迟 |
| 唯一性 | 无重复 | 主键去重 |
| 有效性 | 值合法 | 状态枚举合法、日期不超范围 |

> **一句话记忆**：数据平台"算得快"是本事，"算得对"是底线。治理层的核心就是让"每一张表、每一个指标可追溯、可校验、可审计"。

## 65.6 实战：从 0 到 1 搭建数据平台（最小闭环）

```
阶段一（1 周）：最小闭环——打通"业务库 → 实时数仓 → 大屏"
  MySQL 业务库 → Flink CDC（61.9）→ Kafka → Flink SQL 分层（62 章）
  → ClickHouse 分析层（64 章）→ 大屏/报表
  产出：实时 GMV、订单分析跑通

阶段二（2 周）：补离线——历史对账与复杂分析
  加 Hive/Spark SQL（63 章）离线分层 + DolphinScheduler 调度（65.4）
  离线/实时共用口径，每日对账（62.6）
  产出：T+1 报表、历史趋势分析

阶段三（持续）：平台化——治理与开放
  元数据 + 血缘 + 数据质量（65.5）→ 数据服务 API → 自助分析（BI）
  产出：多团队自助取数、数据资产化
```

**平台化演进检查清单**：

- [ ] 数据接入是否标准化（统一 Kafka 主题规范 / 字段规范）？
- [ ] 分层口径是否统一（ODS/DWD/DWS/ADS 模板）？
- [ ] 任务调度是否托管（无手动 crontab 散落）？
- [ ] 是否有元数据与血缘（新人能看懂表）？
- [ ] 关键表是否有质量规则与告警？
- [ ] 权限是否分级（敏感表脱敏）？
- [ ] 是否有实时/离线对账闭环？

**面试速查**：

| 问题 | 一句话答案 |
| --- | --- |
| 大数据平台有哪些层？ | 采集/存储/计算/分析/治理/应用六层 |
| 数据湖和数仓区别？ | 原始全量 vs 加工后；湖仓一体两全 |
| 实时和离线怎么配合？ | 实时出快数，离线兜底对账，共用口径 |
| 平台从哪开始搭？ | 最小闭环（CDC→Kafka→Flink→ClickHouse），被业务逼着加层 |
| 数据质量怎么保证？ | 六性校验 + 实时离线对账 + 血缘可追溯 |
| 调度器管什么？ | 定时批任务编排，实时作业自身常驻不需要调度 |

### 本章小结

- **全景**（65.1~65.2）：六层流水线架构，规模决定组件矩阵，切忌堆组件；
- **存储**（65.3）：数仓→数据湖→湖仓一体演进，Iceberg 是当前主流；
- **调度与治理**（65.4~65.5）：DolphinScheduler/Airflow 编排批任务，元数据/血缘/质量/权限四件套；
- **落地**（65.6）：最小闭环 → 补离线 → 平台化三阶段路线，检查清单即成熟度度量；
- **收官**（65.7）：61~65 大数据五连形成"引擎 → 数仓 → 离线 → 分析 → 平台"完整闭环。
