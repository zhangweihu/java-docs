# 第五十四章 云原生安全专项（安全左移与纵深防御）

> 本章目标：第十三章解决了应用认证授权，本章把安全视角扩展到整个云原生架构——理解云原生威胁模型（供应链/镜像/运行时/K8s API/网络/数据六面攻击面），掌握供应链安全（SBOM/镜像签名/漏洞扫描）、镜像与运行时加固、K8s 安全（RBAC 深度/准入控制/NetworkPolicy/Secrets）、零信任（mTLS/东西向安全）与数据安全（KMS/加密），建立 DevSecOps"安全左移"的工程化实践。
>
> 前置知识：第十三章 Spring Security、第四十九章 K8s 深度专题（RBAC/Secret/网络）、第五十章 Service Mesh（mTLS）、第五十三章 DevOps/GitOps（供应链）、第五十二章行业案例（金融合规）。

## 54.1 云原生威胁模型：攻击面变了

### 54.1.1 从"防火墙时代"到"六面攻击面"

传统安全模型：边界防火墙 + 内网信任。云原生是**动态、分散、代码驱动**的，攻击面变成六个：

```
① 供应链：依赖漏洞、恶意镜像、被投毒的第三方库
② 构建：CI 被攻破 → 注入后门到镜像
③ 镜像：漏洞、明文密钥、提权配置（root 运行）
④ 运行时：容器逃逸、提权、敏感挂载
⑤ 控制面：K8s API 未授权访问、RBAC 配置错误
⑥ 数据：未加密存储、Secret 泄露、日志泄漏
```

> **一句话记忆**：传统安全守"城墙"，云原生安全要守"六扇门"——每一层都是独立的攻击面，必须**纵深防御**（多层叠加，单层失效不致命）。

### 54.1.2 云原生安全金字塔（由下到上）

```
        数据安全（加密/KMS/脱敏）
        应用安全（OWASP Top10 / Spring Security）
        运行时安全（非root/只读/沙箱）
        网络安全（NetworkPolicy / mTLS 零信任）
        控制面安全（RBAC / 准入控制 / 审计）
        供应链安全（SBOM / 签名 / 扫描）
```

## 54.2 供应链安全：把住第一道门

### 54.2.1 SBOM：软件物料清单

像"食品配料表"一样，列出镜像里**每个组件及其版本**（OS 包、JAR 依赖、CVE 影响范围）：

```bash
# 生成 SBOM（Syft）并扫描漏洞（Trivy）
syft alpine:3.19 -o cyclonedx-json > sbom.json
trivy image --format table --exit-code 1 --severity HIGH,CRITICAL mall/order:1.2.0
```

- **价值**：出漏洞时 5 分钟定位"哪个镜像、哪个版本受影响"，而不是全量重扫；
- **落地**：CI 里生成 SBOM 随镜像发布，入库 GitOps 仓库（第 53 章）或 OCI 制品库。

### 54.2.2 镜像签名与校验（Cosign）

```
构建机：cosign sign mall/order@sha256:xxx   ← 用私钥签名
部署侧：cosign verify mall/order@sha256:xxx ← 校验签名 + 公钥
```

- 防止"镜像被替换/仓库被篡改"；K8s 侧用准入控制器（如 Kyverno）强制"无签名不部署"。

### 54.2.3 Java 依赖安全

| 措施 | 工具 |
| --- | --- |
| 依赖漏洞扫描 | OWASP Dependency-Check、Snyk、Trivy fs |
| 依赖锁定 | Maven `dependency:tree` + lock 文件、Renovate 自动升级 |
| 内部仓库代理 | Nexus/Artifactory 做镜像源白名单，拦截恶意包 |
| 防止依赖混淆 | 私有仓库域名区分 + `repositories` 精确配置 |

## 54.3 镜像与运行时加固

### 54.3.1 镜像安全基线（Dockerfile 层面）

| 项 | 做法 |
| --- | --- |
| 基础镜像 | 用官方最小镜像（如 eclipse-temurin）并**固定版本 digest** |
| 非 root 运行 | `USER 10001` 创建专用用户，禁止 root |
| 只读文件系统 | `readOnlyRootFilesystem: true`，写路径单独挂 tmpfs |
| 精简内容 | 多阶段构建只留运行产物（第 53 章），减少攻击面 |
| 健康检查 | 显式声明 HEALTHCHECK |
| 机密不进镜像 | 密钥走 Secret/KMS，镜像里不允许硬编码 |

### 54.3.2 运行时沙箱

```
普通容器：共享内核（escape 风险）
加强方案：Seccomp（限制系统调用）/ AppArmor（限制文件/网络访问）
更强隔离：gVisor（用户态内核）/ Kata Containers（轻量 VM）
```

**默认最小权限**：Pod Security Context 关闭 `privileged`、禁止 `hostPID/hostNetwork`、限制 `allowPrivilegeEscalation: false`。

## 54.4 K8s 控制面安全

### 54.4.1 RBAC 深水区（第 49 章进阶）

```
最小权限检查清单：
  □ 每个服务独立 ServiceAccount，禁止默认账户
  □ 用 Role（命名空间级）而非 ClusterRole，除非确需全局
  □ 禁止 wildcard（*）授权；resources/verbs 精确到操作
  □ 定期审计：kubectl auth whoami / 权限扫描工具（kube-hunter）
  □ 匿名访问关闭；apiserver 监听仅限内网/带 TLS
```

### 54.4.2 准入控制：部署前的最后一道闸

```
kubectl apply ──► apiserver：认证 → 授权 → 准入控制（Webhook/内置策略）
                                                │
                        ├─ Pod Security Admission（PSS）：限制 privileged/高危能力
                        ├─ Kyverno/OPA Gatekeeper：自定义策略（如"必须非root""必须签名"）
                        └─ ImagePolicyWebhook：只允许白名单镜像仓库
```

**PSS 三级**（Pod Security Standards）：`privileged`（宽松）/ `baseline`（基础）/ `restricted`（严格，生产推荐）。

### 54.4.3 Secrets 安全

- 第 49 章讲过 Secret 只是 Base64——**生产必须**：
  1. 开启 etcd 静态加密（`--encryption-provider-config` 或云 KMS 集成）；
  2. 用 External Secrets Operator / SealedSecrets 管理（第 53 章）；
  3. 禁止 Secret 出现在日志/环境变量 dump/镜像里。

## 54.5 网络与零信任：东西向不再裸奔

### 54.5.1 NetworkPolicy：默认拒绝，按需放行

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: order-netpol
  namespace: mall
spec:
  podSelector:
    matchLabels: { app: mall-order }        # 目标：order 服务
  policyTypes: [Ingress, Egress]
  ingress:
    - from:
        - podSelector:
            matchLabels: { app: mall-account }  # 只允许 account 调用
        - namespaceSelector:
            matchLabels: { name: gateway-ns }   # 以及网关命名空间
      ports:
        - { protocol: TCP, port: 8080 }
  egress:
    - to:
        - podSelector:
            matchLabels: { app: mall-db }
      ports:
        - { protocol: TCP, port: 3306 }
```

> 默认没有 NetworkPolicy = 全放通。**生产基线**：每命名空间默认拒绝，白名单放行——这是"东西向流量"的第一道防线。

### 54.5.2 零信任与 mTLS（与第 50 章呼应）

```
零信任三原则：永不信任网络（mTLS 双向认证）、永不信任来源（授权策略）、持续验证
Istio PeerAuthentication：自动 mTLS 加密 + 身份（证书）
Istio AuthorizationPolicy：服务级访问控制（第 50.4 节）
```

- **应用层价值**：即使攻击者进了内网，没有合法身份也无法调用你的服务——把"内网=可信"的错误假设彻底打破。

## 54.6 应用安全：OWASP 与 Java 实践

| OWASP Top 10（摘要） | Java 侧对策 |
| --- | --- |
| 注入（SQL/XSS） | MyBatis 参数绑定（第 9 章）、输出转义、禁用拼接 SQL |
| 失效的认证 | Spring Security + JWT 加固（第 13 章）、token 过期/吊销 |
| 敏感数据暴露 | 传输 TLS、存储加密、日志脱敏（第 48 章） |
| XXE/反序列化 | 禁用危险 XML 解析、限制反序列化来源、JEP 290 过滤器 |
| 安全配置错误 | 默认安全配置、禁止 debug/actuator 暴露生产（第 48 章） |
| 组件漏洞 | 依赖扫描 + 升级（54.2） |

> **Java 特有提醒**：反序列化漏洞是 Java 重灾区（Fastjson 等），原则——**不反序列化不可信输入**，必须用时加白名单校验。

## 54.7 数据安全：加密与合规

| 层次 | 手段 |
| --- | --- |
| 传输加密 | TLS（Ingress/服务间 mTLS）、数据库连接 TLS |
| 静态加密 | 云盘加密、etcd 加密、数据库 TDE/透明加密 |
| 密钥管理 | KMS（云）/ Vault，密钥轮换 |
| 字段级 | 身份证/手机号脱敏（第 48 章日志脱敏）+ 存储加密 |
| 合规 | GDPR/等保/金融监管：审计日志、数据留存策略、访问留痕 |

**Java 落地**：Spring Security Crypto（加密工具）、自定义 Jackson 脱敏注解、`@Encrypt` 字段级 AOP 加密，配合 KMS 管理密钥不落代码。

## 54.8 DevSecOps：安全左移

```
传统：开发 → 测试 → 上线 → 安全（事后救火）
左移：安全能力进 CI（第 53 章流水线）：
  提交前：IDE 插件/本地扫描（快速反馈）
  CI 阶段：依赖扫描 + 镜像扫描 + 静态分析（阻塞高危）
  部署前：准入控制强制策略（无签名不放行）
  运行期：审计日志 + 运行时安全（Falco 检测异常行为）
```

- **工具链**：Trivy/Snyk（漏洞）、SonarQube（代码）、Cosign（签名）、Kyverno（准入）、Falco（运行时）、审计日志（kube-apiserver audit）；
- **理念**：安全不是"安全团队的事"，是**流水线上的一道门禁**。
