# 第二十八章 设计原则深度（SOLID 与架构思想）

> 本章目标：在第十四章设计模式的基础上深入理解设计原则的**本质与权衡**，掌握 SOLID 六大原则的实战判定方法（反例→正例），理解组合优于继承、接口隔离的架构含义，能独立完成一次真实的代码重构。
>
> 前置知识：第十四章设计模式（六大原则 + 12 种模式）、第九章 Spring Boot（重构对象）。

## 28.1 为什么还要再讲一次设计原则

### 28.1.1 设计模式 vs 设计原则

| 对比 | 设计模式 | 设计原则 |
| --- | --- | --- |
| 层面 | 具体招式（怎么写出某段结构） | 心法（为什么这样设计） |
| 数量 | 23 种 GoF 模式 | 六大原则 |
| 关系 | 模式是原则的落地实现 | 原则是模式的指导思想 |
| 掌握方式 | 背结构、套模板 | **练判定：看到代码能说出违反了哪条** |

> 第十四章教"招式"，这一章练"心法"。**面试问"你怎么设计一个系统"，答的全是原则，不是模式。**

### 28.1.2 为什么原则比模式重要

```
没有原则的"模式党"：
"这里用个单例，那里用个工厂" → 为了模式而模式，过度设计

有原则的工程师：
"这个类同时干了两件事，违反单一职责，应该拆开" → 结构自然合理
```

**原则是判断标准**：模式不一定用，但原则时时在检验你的代码。

## 28.2 SOLID 五大原则逐个击破

> SOLID 是面向对象设计的五大原则首字母缩写，面试必背。加上迪米特法则（LoD）共六条。

### 28.2.1 S：单一职责原则（SRP）

**定义**：一个类只应该有一个引起它变化的原因（一个类只干一件事）。

**反例**：

```java
// ❌ 这个类干了三件事：用户校验 + 数据库存取 + 发邮件
public class UserService {
    public void register(User user) {
        validate(user);                    // 1. 参数校验
        insertDb(user);                    // 2. 数据存取
        sendWelcomeEmail(user);            // 3. 发送邮件
    }
}
// 问题：改校验规则、改数据库、改邮件模板，都要动这个类
```

**正例**：

```java
// ✅ 每个类一个职责
public class UserValidator {              // 职责 1：校验
    public boolean validate(User user) { ... }
}

public class UserRepository {             // 职责 2：存取
    public void save(User user) { ... }
}

public class EmailService {               // 职责 3：通知
    public void sendWelcome(User user) { ... }
}

// 组合使用
public class UserService {
    public void register(User user) {
        userValidator.validate(user);
        userRepository.save(user);
        emailService.sendWelcome(user);
    }
}
```

**怎么判定"一个职责"**：
1. 类名能不能准确概括它的全部方法？（叫 `UserService` 但里面还有 `sendEmail` → 可疑）
2. 修改一个业务规则，需要动几个类？
3. 类的方法数量太多（> 20 个）且不是纯工具类 → 考虑拆分

> **注意**：单一职责不是"方法越少越好"，过度拆分会导致类爆炸。**判断标准是"变更原因"：两个不同的业务变化会同时修改这个类，就该拆。**

### 28.2.2 O：开闭原则（OCP）

**定义**：对扩展开放，对修改关闭（加新功能不改老代码）。

**反例**：

```java
// ❌ 每加一种支付方式，就要改这段 if-else
public double pay(String type, double amount) {
    if ("alipay".equals(type)) {
        return amount * 1.0;       // 支付宝
    } else if ("wechat".equals(type)) {
        return amount * 0.98;      // 微信 98 折
    } else if ("unionpay".equals(type)) {
        return amount * 0.95;      // 银联 95 折
    }
    throw new UnsupportedOperationException();
}
// 第 4 种支付方式来了 → 改这个类 → 有改坏已有逻辑的风险
```

**正例（策略模式）**：

```java
// ✅ 定义支付接口
public interface Payment {
    double pay(double amount);
}

// 每种支付是一个类（扩展新支付 = 新建类，不改老类）
public class Alipay implements Payment {
    public double pay(double amount) { return amount; }
}
public class WechatPay implements Payment {
    public double pay(double amount) { return amount * 0.98; }
}

// 用 Map 注册（Spring 自动注入所有 Payment 实现）
@Service
public class PayService {
    private final Map<String, Payment> paymentMap;

    public PayService(List<Payment> payments) {
        this.paymentMap = payments.stream()
                .collect(Collectors.toMap(p -> p.getClass().getSimpleName().toLowerCase(), p -> p));
    }

    public double pay(String type, double amount) {
        Payment payment = paymentMap.get(type);
        if (payment == null) throw new UnsupportedOperationException();
        return payment.pay(amount);
    }
}
// 新增 "云闪付"：新建 YunPay implements Payment，一行老代码都不用改
```

**开闭原则的本质**：
- 行为可扩展 → **多态**（接口 + 实现）
- 结构不修改 → **依赖抽象**（面向接口编程）
- 落地手法：策略模式、模板方法、装饰器（呼应第十四章）

### 28.2.3 L：里氏替换原则（LSP）

**定义**：子类必须能替换父类且程序行为不变（继承要符合 is-a 关系）。

**反例**：

```java
// ❌ 经典反例：正方形继承长方形
public class Rectangle {
    protected int width, height;
    public void setWidth(int w) { width = w; }
    public void setHeight(int h) { height = h; }
    public int area() { return width * height; }
}

public class Square extends Rectangle {
    // 为了"正方形"，重写 setWidth 让高也变
    @Override
    public void setWidth(int w) { width = height = w; }
    @Override
    public void setHeight(int h) { width = height = h; }
}

// 调用方按父类写逻辑：
public void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(3);
    System.out.println(r.area());   // Rectangle=15，Square 却=9！行为变了
}
// 违反 LSP：Square 替换 Rectangle 后行为不一致
```

**正例**：

```java
// ✅ 正方形和长方形是兄弟（组合/接口），不是父子
public interface Shape {
    double area();
}
public class Rectangle implements Shape { ... }
public class Square implements Shape {
    private double side;
    public double area() { return side * side; }
}
```

**LSP 判定清单**：
1. 子类重写父类方法后，行为是否"更严格"（抛更多异常/返回异常值）？
2. 子类是否继承了不该继承的能力（`Stack` 继承 `Vector` 能插入中间元素）？
3. 用父类类型写代码时，换成子类会不会出问题？
4. **继承到底表达"is-a"还是只是"想复用代码"？** 后者应该用组合。

### 28.2.4 I：接口隔离原则（ISP）

**定义**：客户端不应该依赖它不需要的接口方法（接口要小而专）。

**反例**：

```java
// ❌ 一个大而全的接口
public interface Worker {
    void work();
    void eat();
    void sleep();
}

// 机器人实现：eat/sleep 只能空实现或抛异常
public class Robot implements Worker {
    public void work() { ... }
    public void eat() { throw new UnsupportedOperationException(); }  // 接口污染！
    public void sleep() { throw new UnsupportedOperationException(); }
}
```

**正例**：

```java
// ✅ 拆成小接口
public interface Workable { void work(); }
public interface Eatable { void eat(); }

public class Robot implements Workable {           // 只实现需要的
    public void work() { ... }
}
public class Human implements Workable, Eatable {  // 按需实现
    public void work() { ... }
    public void eat() { ... }
}
```

**接口隔离 vs 单一职责**：SRP 约束"类"，ISP 约束"接口"。共同思想是**高内聚、低耦合**。

**实战判定**：接口方法被实现类大量"空实现/抛异常" → 接口太胖，该拆。

### 28.2.5 D：依赖倒置原则（DIP）

**定义**：高层模块不依赖低层模块，两者都依赖抽象；抽象不依赖细节，细节依赖抽象。

**反例**：

```java
// ❌ 高层直接依赖低层（类）
public class OrderService {
    private final MysqlOrderRepository repository = new MysqlOrderRepository();
    // 想换成 Redis/ES 存储 → 必须改 OrderService 源码
}
```

**正例**：

```java
// ✅ 高层依赖抽象（接口）
public interface OrderRepository {
    Order findById(Long id);
    void save(Order order);
}

public class OrderService {
    private final OrderRepository repository;   // 依赖接口

    public OrderService(OrderRepository repository) {  // 构造注入
        this.repository = repository;
    }
}

public class MysqlOrderRepository implements OrderRepository { ... }
public class EsOrderRepository implements OrderRepository { ... }
// 换存储实现：改配置/改注入，OrderService 一行不动
```

**DIP 落地三板斧（依赖注入容器）**：

```java
// 1. 依赖接口（不 new 具体类）
// 2. 构造器注入（Spring 自动装配）
// 3. 接口属于"高层"定义（如 OrderRepository 由业务侧定义，不写在数据库包里）
```

> **DIP 和 IoC/DI 的关系**：依赖倒置是设计思想（谁依赖谁），控制反转/依赖注入是实现手段（怎么把依赖给进来）。Spring 的 `@Autowired` 就是实现 DIP 的工具。

### 28.2.6 迪米特法则（LoD，最少知识原则）

**定义**：一个对象应该对其他对象保持最少的了解（不和陌生人说话）。

**反例**：

```java
// ❌ 火车类直接操作了乘客的钱包（知道得太多了）
public class Train {
    public void checkTicket(Passenger p) {
        // 一层层往下摸：乘客→钱包→钱
        p.getWallet().getMoney().decrease(10);
    }
}
// 钱包实现变了 → 火车也要改
```

**正例**：

```java
// ✅ 只和"直接朋友"打交道
public class Train {
    public void checkTicket(Passenger p) {
        p.pay(10);   // 只调用乘客的方法，不深入内部
    }
}
public class Passenger {
    public void pay(int amount) { wallet.getMoney().decrease(amount); }
}
```

**应用场景**：门面模式（Facade）、Controller 不直接操作 Entity（用 DTO 中转，呼应第十章 MapStruct）。

## 28.3 组合优于继承

### 28.3.1 继承的问题

```java
// ❌ 多层继承带来的"不该继承的东西"
public class Animal { void eat() {} }
public class Bird extends Animal { void fly() {} }
public class Ostrich extends Bird {          // 鸵鸟不会飞！
    @Override void fly() { throw new RuntimeException("鸵鸟不会飞"); }
}
// 深度继承链：改父类影响所有子类，脆弱
```

### 28.3.2 组合（组合是 has-a，继承是 is-a）

```java
// ✅ 用组合描述"能力"
public class Ostrich {
    private final RunBehavior run = new RunBehavior();   // 组合
    public void run() { run.run(); }
}
public class Eagle {
    private final FlyBehavior fly = new FlyBehavior();
    public void fly() { fly.fly(); }
}
// 能力可变：运行时还能换（策略模式），继承做不到
```

| 对比 | 继承 | 组合 |
| --- | --- | --- |
| 关系 | is-a | has-a |
| 复用 | 破坏封装（看到父类全部） | 只暴露需要的 |
| 扩展 | 改父类影响所有子类 | 只改当前类 |
| 运行时变化 | 不能 | 可以替换组件 |
| 适用 | 稳定的纵向关系 | 绝大多数场景 |

> **经验法则**：不确定用继承还是组合时，**默认用组合**。继承只在"确实是 is-a 且父类稳定"时用。

## 28.4 实战：烂代码重构全过程

### 28.4.1 需求

用户注册后发优惠券：新人券 + 老用户回归券，规则各不相同，未来还会加。

### 28.4.2 初始烂代码（真实项目常见）

```java
@Service
public class CouponService {
    // ❌ 问题 1：if-else 堆业务（违反 OCP）
    // ❌ 问题 2：一个方法干三件事（违反 SRP）
    // ❌ 问题 3：直接 new 依赖（违反 DIP）
    public String issueCoupon(User user) {
        String type;
        if (user.getOrderCount() == 0) {
            type = "新人券";
        } else if (user.getLastOrderTime() > 180L * 24 * 3600 * 1000) {
            type = "回归券";
        } else {
            type = "普通券";
        }

        // 发券逻辑混在里面
        StringBuilder result = new StringBuilder();
        if ("新人券".equals(type)) {
            result.append("送 50 元券");
        } else if ("回归券".equals(type)) {
            result.append("送 30 元券");
        } else {
            result.append("送 10 元券");
        }

        // 短信通知也塞在这里
        new SmsSender().send(user.getPhone(), result.toString());
        return result.toString();
    }
}
```

**问题清单**：
1. 加一种券 → 改这个类（OCP 违反）
2. 判定规则、发券、通知三个职责混合（SRP 违反）
3. `new SmsSender()` 写死（DIP 违反）

### 28.4.3 重构第一步：策略模式拆发券规则（解决 OCP）

```java
// 策略接口：每种券一个实现
public interface CouponStrategy {
    boolean matches(User user);        // 是否匹配该用户
    String issue(User user);           // 发放动作
}

// 新人券
@Component
public class NewUserCoupon implements CouponStrategy {
    @Override
    public boolean matches(User user) { return user.getOrderCount() == 0; }
    @Override
    public String issue(User user) { return "新人 50 元券"; }
}

// 回归券
@Component
public class ReturnCoupon implements CouponStrategy {
    @Override
    public boolean matches(User user) {
        return user.getLastOrderTime() > 180L * 24 * 3600 * 1000;
    }
    @Override
    public String issue(User user) { return "回归 30 元券"; }
}

// 默认券
@Component
public class DefaultCoupon implements CouponStrategy {
    @Override
    public boolean matches(User user) { return true; }   // 兜底
    @Override
    public String issue(User user) { return "普通 10 元券"; }
}
```

### 28.4.4 重构第二步：注入 + 组合（解决 DIP + SRP）

```java
@Service
public class CouponService {

    // Spring 自动收集所有 CouponStrategy 实现（按注册顺序）
    private final List<CouponStrategy> strategies;
    private final NotificationService notification;   // 依赖接口/服务

    public CouponService(List<CouponStrategy> strategies, NotificationService notification) {
        this.strategies = strategies;
        this.notification = notification;
    }

    public String issueCoupon(User user) {
        // 找第一个匹配的策略（顺序很重要：新人 > 回归 > 默认）
        CouponStrategy strategy = strategies.stream()
                .filter(s -> s.matches(user))
                .findFirst()
                .orElseThrow(() -> new IllegalStateException("无匹配券策略"));

        String result = strategy.issue(user);
        notification.sendSms(user.getPhone(), result);   // 通知独立出去
        return result;
    }
}
```

### 28.4.5 重构后的效果

| 变化 | 重构前 | 重构后 |
| --- | --- | --- |
| 新增一种券 | 改 `CouponService` 两处 if-else | 新建一个类，**零修改** |
| 改发券规则 | 动整个类 | 只动对应策略类 |
| 测试 | 难以单独测 | 每个策略可独立单元测试 |
| 依赖 | 手写 `new` | 构造注入，可替换 |

> 这就是"面向扩展开放"的真实落地：**改需求 = 加文件，而不是改文件**。

## 28.5 反模式与代码坏味道（怎么发现该重构）

### 28.5.1 常见坏味道清单

| 坏味道 | 对应违反 | 处理 |
| --- | --- | --- |
| 超大类（上帝类） | SRP | 按职责拆分 |
| 超长方法（> 50 行） | SRP | 提取方法 |
| 大量 if-else 分支 | OCP | 策略/状态/工厂模式 |
| 方法参数太多（> 5 个） | SRP | 提取参数对象 |
| 空实现/抛异常的接口方法 | ISP | 拆分接口 |
| `new` 具体类遍布代码 | DIP | 依赖注入 |
| 数据类只有 getter/setter | 贫血模型 | 方法下沉到实体/领域 |
| 深层调用链 `a.getB().getC()` | LoD | 迪米特法则收紧 |

### 28.5.2 过度设计（另一种坏味道）

```
❌ 没有扩展需求却提前做抽象：
public interface Hello { void say(); }          // 只有一个实现
public class HelloImpl implements Hello { ... } // 为了抽象而抽象

✅ 判断标准：什么时候需要接口？
1. 已有多个实现（支付/存储/通知）
2. 明确知道近期会扩展（如对接新支付）
3. 需要解耦测试（Mock 注入）
```

> **原则不是教条**：小项目一上来就疯狂套接口、套模式，是另一种失败。**先有变化的需求，再引入抽象。**

## 28.6 架构层面的原则应用

### 28.6.1 分层架构与依赖方向（DIP 的架构体现）

```
Controller（表现层）──► Service（业务层）──► Repository（数据层）
      │                     │                    │
  只依赖 Service          依赖 Repository 接口    实现细节
      └──────────── 依赖只能向下，不能向上 ───────────┘
```

**实战准则**：
1. Service 层依赖 Repository **接口**，不依赖具体实现（DIP）
2. Controller 不写业务逻辑，只做参数接收/返回（SRP）
3. 实体 Entity 不直接透出到前端，用 DTO 隔离（LoD，呼应第十章 MapStruct）
4. 公共逻辑下沉，不让 Controller 之间互相调用

### 28.6.2 领域驱动设计（DDD）初步

```
领域模型分层（DDD 简化版）：
┌─────────────────────────────────┐
│  应用层（Application）：用例编排     │  OrderAppService
├─────────────────────────────────┤
│  领域层（Domain）：核心业务规则      │  Order（聚合根）、OrderStatus 值对象
├─────────────────────────────────┤
│  基础设施层（Infrastructure）：实现  │  JpaOrderRepository
└─────────────────────────────────┘
```

```java
// 传统"贫血模型"：实体只是数据袋子，逻辑全在 Service
public class Order {
    private Long id;
    private String status;
    // getter/setter 一堆
}
// Service 里写：if(order.getStatus().equals("PENDING")) { order.setStatus("PAID"); ... }

// DDD"充血模型"：行为放进实体
public class Order {
    private Long id;
    private OrderStatus status;

    public void pay(BigDecimal amount) {
        if (!OrderStatus.PENDING.equals(status)) {
            throw new IllegalStateException("当前状态不可支付");
        }
        if (amount.compareTo(this.amount) < 0) {
            throw new BusinessException("支付金额不足");
        }
        this.status = OrderStatus.PAID;   // 规则在实体内部，别人没法绕过
    }
}
```

**DDD 的价值**：把散落在 Service 里的业务规则收拢到领域对象，业务规则不会被"绕过去"。**中小项目不必强行 DDD，理解概念即可，面试会讲加分。**

## 28.7 小结与练习

**本章重点**：
- 原则是心法，模式是招式；**面试问设计，答原则**
- SOLID 六条（含 LoD），每条都会：定义 → 反例 → 正例 → 判定标准
- **SRP**：变更原因唯一；**OCP**：扩展开放、修改关闭；**LSP**：子类可替换
- **ISP**：接口小而专；**DIP**：高层依赖抽象；**LoD**：不和陌生人说话
- 组合优于继承（is-a vs has-a）
- 坏味道识别 → 重构（策略模式拆分 if-else 是最实用手法）
- 防过度设计：有变化再抽象
- DIP 的架构落地：分层依赖向下、Controller-Service-Repository

**面试题参考**：
