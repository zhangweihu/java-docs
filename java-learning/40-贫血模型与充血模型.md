# 第四十章 贫血模型与充血模型（领域模型设计）

> 本章目标：理解"**业务逻辑应该放在哪**"这一面向对象设计的终极问题。掌握贫血模型（Anemic Domain Model）与充血模型（Rich Domain Model）的概念、特征与本质区别，能用同一业务场景写出两种模型并说清各自的优劣与适用场景，理解它们与 DDD（领域驱动设计）的关系，学会在实际项目中做选型与演进。
>
> 前置知识：第二章 面向对象编程（封装/继承/多态）、第九章 Spring Boot（Service 分层）、第二十八章 设计原则深度（SRP/封装）、第三十一章 Spring Boot 项目实战（标准三层架构）。

## 40.1 从一个"人人都写过"的代码说起

### 40.1.1 打开你的项目，90% 长这样

第三十一章的商城实战中，我们写过这样的代码：

```java
// entity/Order.java —— 一个"纯数据"类
@Data
@TableName("t_order")
public class Order {
    private Long id;
    private String orderNo;
    private Long userId;
    private BigDecimal totalAmount;
    private Integer status;   // 0 待支付 1 已支付 2 已取消 3 已发货
}
```

```java
// service/OrderService.java —— 业务逻辑全在这里
@Service
public class OrderService {
    @Transactional
    public void pay(Long orderId) {
        Order order = orderMapper.selectById(orderId);
        if (order == null) {
            throw new BusinessException(404, "订单不存在");
        }
        if (order.getStatus() != 0) {
            throw new BusinessException(400, "订单状态异常，无法支付");
        }
        // …… 调用支付平台、更新金额等
        order.setStatus(1);
        orderMapper.updateById(order);
    }
}
```

这个模式太熟悉了：**实体类（Entity）只装数据和 getter/setter，所有业务逻辑都堆在 Service 里**。绝大多数 Java 后端项目（Spring Boot + MyBatis-Plus 风格）都是这么写的。

### 40.1.2 但这是"面向对象"吗

第二章我们学了 OOP 三大特征，其中**封装**的意思是：把数据和操作数据的方法放在一起，对外只暴露必要的接口。

```java
// 第二章的 Student 类 —— 有属性也有行为
public class Student {
    String name;
    int age;

    void introduce() {                    // 行为和数据在一起！
        System.out.println("我是 " + name);
    }
}
```

对照上面 40.1.1 的 `Order`：它有状态（`status` 字段），却没有行为（`pay()` 在哪？在 Service）。**订单自己不会"支付"、不会"取消"、不会"计算金额"，它只是一个被 Service 搬来搬去的"数据袋子"。**

于是出现了本领域最有名的两个名词：

> - **贫血模型（Anemic Domain Model）**：对象只有数据没有业务行为，行为全部外置到 Service 层；
> - **充血模型（Rich Domain Model）**：对象既有数据又有业务行为，Service 层退化为"协调者"。

> **一句话记忆**：贫血模型是"**对象是死的，逻辑是外挂的**"；充血模型是"**对象是活的，逻辑是内聚的**"。

## 40.2 贫血模型：现状与真相

### 40.2.1 起源：Martin Fowler 的"吐槽"

贫血模型这个说法来自 Martin Fowler 2003 年的博客 *AnemicDomainModel*。他描述的现象是：

> 很多系统的领域对象看起来是对象（有属性、有 getter/setter），但实际上**没有任何领域行为**，业务规则被搬到 Service 层——Fowler 认为这是**反模式**，因为"它违背了面向对象的核心思想"。

有意思的是，这个"被批评的反模式"后来成了**全球 Java 后端最主流的写法**。为什么？往下看。

### 40.2.2 典型特征

| 特征 | 表现 |
| --- | --- |
| 领域对象 = 数据容器 | Entity/POJO 只有字段 + getter/setter（配合 Lombok `@Data`） |
| 业务逻辑外置 | 所有规则、状态流转、计算都在 Service 层方法里 |
| 依赖基础设施 | Entity 不依赖 Mapper/DAO，Service 注入 Mapper |
| 事务边界在 Service | `@Transactional` 标注在 Service 方法上 |
| 与三层架构契合 | Controller → Service → Mapper，职责单一清晰 |

```java
// 贫血模型完整示例：订单实体（纯数据） + 订单服务（纯行为）
@Data
public class Order {
    private Long id;
    private BigDecimal totalAmount;
    private Integer status;
}

@Service
public class OrderService {
    @Autowired
    private OrderMapper orderMapper;

    // 创建订单：算总价、设初始状态
    public Order create(List<OrderItem> items) {
        BigDecimal total = items.stream()
                .map(OrderItem::getAmount).reduce(BigDecimal.ZERO, BigDecimal::add);
        Order order = new Order();
        order.setTotalAmount(total);
        order.setStatus(0);
        orderMapper.insert(order);
        return order;
    }

    // 支付：校验状态 + 流转状态
    public void pay(Long id) {
        Order order = orderMapper.selectById(id);
        if (order.getStatus() != 0) {
            throw new BusinessException("订单状态异常");
        }
        order.setStatus(1);
        orderMapper.updateById(order);
    }
}
```

### 40.2.3 优点：为什么它统治了业界

1. **简单直接、上手门槛低**：新人看一遍就能写，"数据放实体，逻辑放 Service"一条规则走天下；
2. **与 ORM 完美契合**：MyBatis/MyBatis-Plus/JPA 都基于字段映射，Entity 越"纯"，映射越省事，不用给实体塞 Mapper 依赖；
3. **事务与依赖边界清晰**：Service 方法 = 一个事务单元，注入什么、依赖什么都明明白白；
4. **便于分层与分工**：Controller/Service/Mapper 各管一段，团队协作互不干扰；
5. **序列化友好**：纯数据对象可以直接塞进 JSON、DTO 转换（第 10 章 MapStruct）毫无负担。

### 40.2.4 缺点：四个致命伤

| 缺点 | 具体表现 | 后果 |
| --- | --- | --- |
| **面向对象名存实亡** | 对象没有行为，封装被架空 | 与第二、二十八章学的 OOP/封装原则背道而驰 |
| **Service 变成上帝类** | 所有规则堆在一个方法里，动辄几百行 | 违反 SRP，改一个规则要全局搜索 |
| **业务规则分散** | "订单能否支付"的规则可能在 pay/取消/退款各写一遍 | 规则不一致，Bug 藏身之处 |
| **领域知识丢失** | 状态机、不变量、业务术语全淹没在 Service 细节里 | 代码读不懂业务，新人接手困难 |

> **典型案例**：某系统 `pay`、`refund`、`cancel`、`autoClose` 四个 Service 方法各自判断"订单状态是否合法"，后来新增了状态 4（部分退款），**漏改了两处**，导致线上出现"已部分退款的订单还能整单取消"的严重事故。规则不收敛，就是这个下场。

## 40.3 充血模型：让对象"活"过来

### 40.3.1 核心思想

把"和订单自身强相关的业务行为"放回 `Order` 对象内部，让对象**自己管好自己的状态**：

```java
// 充血模型：数据 + 行为都在实体里
public class Order {
    private Long id;
    private BigDecimal totalAmount;
    private Integer status;

    // 领域行为 1：支付
    public void pay() {
        if (this.status != 0) {
            throw new IllegalStateException("只有待支付订单才能支付，当前状态：" + status);
        }
        this.status = 1;          // 状态流转发生在对象内部
    }

    // 领域行为 2：取消
    public void cancel() {
        if (this.status != 0) {
            throw new IllegalStateException("只有待支付订单才能取消");
        }
        this.status = 2;
    }

    // 领域行为 3：计算总价（需要明细，由外部传入即可，不依赖 Mapper）
    public void recalc(BigDecimal discount) {
        this.totalAmount = this.totalAmount.subtract(discount);
    }

    // 只暴露必要的 getter（不暴露 setter，防止外部乱改状态！）
    public Long getId() { return id; }
    public Integer getStatus() { return status; }
}
```

```java
// Service 变薄了：只做"找对象、调用行为、落库"三件事
@Service
public class OrderService {
    @Autowired
    private OrderMapper orderMapper;

    public void pay(Long id) {
        Order order = orderMapper.selectById(id);   // 1. 取出来
        order.pay();                                 // 2. 让对象自己处理业务
        orderMapper.updateById(order);               // 3. 存回去
    }

    public void cancel(Long id) {
        Order order = orderMapper.selectById(id);
        order.cancel();
        orderMapper.updateById(order);
    }
}
```

### 40.3.2 关键设计要点

1. **状态流转封装在实体**：`pay()`/`cancel()` 内部校验"当前状态是否允许"，外部无法绕过——规则只写一次；
2. **弱化 setter**：贫血模型用 `@Data` 把 setter 全暴露，任何人都能 `order.setStatus(5)`；充血模型只留必要的修改入口（构造器 + 行为方法），**把"非法状态"消灭在编译/运行入口**；
3. **实体不依赖基础设施**：`Order` 不需要 `OrderMapper`。如果业务规则需要查数据（如"支付前检查账户余额"），怎么办？见 40.5.4 的领域服务与依赖倒置；
4. **Service 只管协调**：取对象、调用行为、落库、开事务、调用外部系统——Service 是"编排者"不是"规则仓库"。

### 40.3.3 优点

- **高内聚**：一个对象的行为都在自己身上，改订单规则只动 `Order`；
- **规则不重复**：`pay`/`cancel`/`refund` 共享同一份状态校验，杜绝"漏改一处"；
- **可测试性更好**：单元测试直接 `new Order(...)` 然后断言 `order.pay()` 抛异常/改状态，**不需要 Mock Mapper**；
- **符合 OOP 本质**：这才是第二章讲的"数据 + 行为 = 对象"；
- **业务可读性高**：读 `Order` 类就能读懂订单的全部业务规则（状态机一目了然）。

### 40.3.4 缺点

- **上手门槛高**：需要设计"哪些行为放实体、哪些放 Service"，对团队建模能力要求高；
- **ORM 映射要小心**：实体携带业务逻辑后，与 MyBatis 的字段映射仍没问题，但如果把行为塞进带状态的实体并序列化，可能把不该暴露的内部结构暴露出去；
- **依赖注入变难**：实体用 `new` 创建（不是 Spring 容器管理的 Bean），如果业务逻辑里硬编码依赖 Mapper 就"脏"了，必须靠领域服务/仓储接口倒置（40.5.4）；
- **简单场景过度设计**：一个纯 CRUD 的"用户管理"页面，强行建模充血模型只会增加复杂度。

## 40.4 正面硬刚：同场景两种写法的完整对照

### 40.4.1 维度对比表

| 对比维度 | 贫血模型 | 充血模型 |
| --- | --- | --- |
| 对象职责 | 纯数据容器 | 数据 + 领域行为 |
| 业务逻辑位置 | Service 方法 | 实体方法（Service 只剩协调） |
| 封装性 | 弱（setter 全开） | 强（只留行为入口） |
| 状态流转控制 | 分散在各 Service 方法 | 集中在实体方法 |
| 事务边界 | Service 方法 | Service 方法（不变） |
| 单元测试 | 需 Mock Mapper/Service | 直接 new 实体测行为 |
| ORM 契合度 | 极好 | 好（需避免实体依赖容器） |
| 学习成本 | 低 | 高 |
| 适用复杂度 | 简单 CRUD / 后台管理 | 复杂业务规则 / 核心领域 |
| 与 OOP 一致性 | 违背封装 | 符合封装 |
| 主流框架契合 | Spring Boot + MyBatis-Plus 默认风格 | DDD 风格（Spring Modulith / Axon / jMolecules） |
| 维护风险 | Service 上帝类、规则重复 | 边界不清时实体膨胀 |

### 40.4.2 同业务（订单状态机）逐行对照

| 业务规则 | 贫血模型写法 | 充血模型写法 |
| --- | --- | --- |
| "只有待支付才能支付" | `OrderService.pay()` 里 `if (order.getStatus() != 0) throw ...` | `Order.pay()` 内部校验 |
| "只有待支付才能取消" | `OrderService.cancel()` 里再写一遍同样的 if | `Order.cancel()` 复用同一规则 |
| "外部想改状态" | `order.setStatus(99)` 直接改，无拦截 | 没有 setter，改不了 |
| "新增'部分退款'状态" | 搜所有 `status ==` 判断逐个改（易漏） | 只改 `Order` 内部行为方法 |
| "验证非法状态" | 需 Mock 一堆依赖才能测 Service | `new Order(...)` 一行即可测 |

### 40.4.3 领域模型四形态（补充概念）

除了"贫血/充血"二分，业界还常用四个递进词：

| 形态 | 特征 | 评价 |
| --- | --- | --- |
| **失血模型** | 连 getter/setter 都少，纯粹是"数据结构 + 参数对象" | 最底层，DTO 可归此类 |
| **贫血模型** | 有状态（数据）无行为（逻辑在 Service） | 主流但被 Fowler 批评 |
| **充血模型** | 有状态有行为，规则内聚 | DDD 推崇 |
| **胀血模型** | 行为和状态全塞进一个类，连基础设施也耦合进来（实体里调 Mapper） | 反模式：实体变成上帝类 |

> 面试加分点：能说出"失血 → 贫血 → 充血 → 胀血"四形态，并指出**胀血不是充血**（很多人把"实体里调 Mapper"误当充血模型，那其实是更糟糕的胀血）。

## 40.5 到底怎么选：决策框架

### 40.5.1 决策树

```
业务复杂度高吗？（规则多、状态机复杂、业务术语密集、多对象联动）
├── 否 → 贫血模型（简单 CRUD、后台管理、报表、配置类系统）
└── 是 ↓
    团队有 DDD/建模能力吗？（能分清实体/值对象/聚合，愿意投入建模）
    ├── 否 → 贫血模型 + 规则收敛到 Service（至少在 Service 内部做状态机封装）
    └── 是 ↓
        该模块是系统核心域吗？（订单/支付/风控/计费 vs 用户管理/字典/日志）
        ├── 否 → 贫血模型（非核心域不值得投入）
        └── 是 → 充血模型（核心域用领域模型承载业务规则）
```

**一句话结论**：**"核心复杂域用充血，外围简单域用贫血"，二者可以在一个系统里共存。**

### 40.5.2 典型场景速查

| 系统/模块 | 推荐模型 | 理由 |
| --- | --- | --- |
| 电商订单、支付、退款 | 充血 | 状态机 + 金额规则多，规则必须收敛 |
| 保险核保、理赔 | 充血 | 业务规则极其复杂，术语密集 |
| 银行账户、转账、风控 | 充血 | 不变量多（余额约束），漏规则 = 资损 |
| 后台管理系统 CRUD | 贫血 | 增删改查 + 表单，建模无收益 |
| 用户注册登录 | 贫血 | 规则简单，Service 足够 |
| 报表、数据看板 | 贫血 | 只读查询，无行为 |

### 40.5.3 渐进式演进路线（实战最优解）

不要一上来就 DDD，推荐"**贫血起步 → 局部充血 → 核心域 DDD**"的渐进路线：

```
第 1 步：标准贫血模型，先跑起来（多数项目止步于此，够用）
   ↓
第 2 步：把"状态机/计算类"规则从 Service 下沉到实体方法（轻度充血，收益最大）
   ↓
第 3 步：对核心复杂域引入完整充血模型：实体 + 值对象 + 聚合 + 领域服务 + 仓储
   ↓
第 4 步：引入 DDD 战术设计（限界上下文、防腐层）——这才是完整 DDD
```

> **本章最重要的实操建议**：即使你决定整体用贫血模型，**至少把"状态流转"和"金额计算"这类规则封装到实体里**（第 2 步），这一个动作就能消灭大多数"规则重复导致的事故"。

### 40.5.4 充血模型如何处理"需要查数据"的行为（依赖倒置）

充血模型最大的拦路虎："支付前要查用户账户余额，实体总不能依赖 Mapper 吧？"——正确解法是**依赖倒置 + 领域服务**：

```java
// 1. 仓储接口（接口定义在领域层，实现在基础设施层）——对 MyBatis 的依赖从实体"倒置"出去
public interface OrderRepository {
    Order findById(Long id);
    void save(Order order);
}

// 2. 领域服务：协调"多个对象 + 外部查询"的跨对象规则（不属于任何一个实体的行为放这里）
@Service
public class PaymentService {
    @Autowired private AccountRepository accountRepository;
    @Autowired private OrderRepository orderRepository;

    @Transactional
    public void pay(Long orderId, Long accountId) {
        Order order = orderRepository.findById(orderId);   // 通过仓储拿对象
        Account account = accountRepository.findById(accountId);
        order.pay();                                        // 对象内部只校验自己的状态
        account.deduct(order.getTotalAmount());             // 账户对象自己扣款
        orderRepository.save(order);
        accountRepository.save(account);
    }
}
```

- **实体不碰 Mapper**，它只和"参数/另一个实体/接口"打交道；
- **需要外部数据的跨对象规则**放"领域服务"（`PaymentService`），而不是塞进实体；
- 这样 `Order.pay()` 可以纯内存单测，`PaymentService` 注入 Mock 仓储做集成测试。

## 40.6 与 DDD 的关系（面试高频）

### 40.6.1 DDD 不是"充血模型"，但离不开充血模型

- **DDD（Domain-Driven Design，领域驱动设计）**：一套从"业务领域"出发做软件设计的方法论，包含战略设计（限界上下文、上下文映射）和战术设计（实体、值对象、聚合、领域服务、仓储）；
- 战术设计的核心载体就是**充血模型**——DDD 要求领域对象承载业务规则，否则"领域驱动"就名存实亡；
- 但**只有充血模型 ≠ DDD**：很多项目把实体塞几个方法、Service 改叫 DomainService，就宣称"我们用了 DDD"，这被业内称为**"伪 DDD / 贫血 DDD"**。

### 40.6.2 DDD 战术元素 vs 三层架构对照

| DDD 元素 | 职责 | 类比三层架构 |
| --- | --- | --- |
| 实体（Entity） | 有唯一标识、有生命周期、可变 | Entity（但要有行为） |
| 值对象（Value Object） | 无标识、不可变、靠值相等（如金额、地址） | DTO / 参数对象 |
| 聚合与聚合根（Aggregate/AggregateRoot） | 一组对象的一致性边界，对外只经聚合根操作 | Service + 一组 Entity |
| 领域服务（Domain Service） | 跨对象、不属于任何单一实体的规则 | 部分 Service |
| 仓储（Repository） | 持久化抽象，领域层只依赖接口 | Mapper |
| 防腐层/应用服务（Application Service） | 编排用例、开事务、调领域对象 | Service 的剩余职责 |

### 40.6.3 贫血模型在 DDD 语境下的重新审视

- DDD 语境里 Service 拆成两层：**应用服务**（编排用例、事务、调仓储，通常是贫血的"瘦"服务） + **领域服务**（跨对象规则，通常是充血对象之间的粘合）；
- 严格说，Fowler 批评的是"**领域对象没有行为**"，而**应用服务本身"贫血"是正常的**——它本来就不该有领域规则。

> 面试回答模板："贫血模型把规则放在 Service，充血模型把规则放在实体。DDD 的战术设计（实体/值对象/聚合/领域服务）天然要求充血模型，但很多伪 DDD 项目只是把三层架构的 Service 换个名，领域对象依然是贫血的。我的实践是：核心复杂域用充血模型 + 仓储抽象，外围简单域保持贫血模型。"

## 40.7 实战改造：把第 31 章的商城代码"充血化"

### 40.7.1 改造对象与目标

以第三十一章订单模块为例，改造前（贫血）：规则全在 `OrderService`；改造后（充血）：规则沉入 `Order`，`OrderService` 只做协调。

**改造前（31 章的写法）**：

```java
// Order.java —— 纯数据
@Data
public class Order {
    private Long id;
    private BigDecimal totalAmount;
    private Integer status;    // 0 待支付 1 已支付 2 已取消
}

// OrderService.java —— 规则全堆在这
@Service
public class OrderService {
    @Transactional
    public Order createOrder(OrderCreateDTO dto, Long userId) {
        // ...校验商品、扣库存（略）
        Order order = new Order();
        order.setTotalAmount(...);
        order.setStatus(0);
        orderMapper.insert(order);
        return order;
    }

    public void pay(Long orderId) {
        Order order = orderMapper.selectById(orderId);
        if (order.getStatus() != 0) throw new BusinessException("订单状态异常");
        order.setStatus(1);                      // ← 规则与流转散落
        orderMapper.updateById(order);
    }

    public void cancel(Long orderId) {
        Order order = orderMapper.selectById(orderId);
        if (order.getStatus() != 0) throw new BusinessException("订单状态异常");
        order.setStatus(2);                      // ← 同样的规则再写一遍
        orderMapper.updateById(order);
    }
}
```

**改造后（充血）**：

```java
// Order.java —— 数据 + 行为，状态机收敛在实体
public class Order {
    public static final int PENDING = 0;    // 待支付
    public static final int PAID = 1;       // 已支付
    public static final int CANCELLED = 2;  // 已取消

    private Long id;
    private BigDecimal totalAmount;
    private Integer status;

    // 构造器：创建订单是实体的职责之一
    public Order(Long id, BigDecimal totalAmount) {
        this.id = id;
        this.totalAmount = totalAmount;
        this.status = PENDING;
    }

    // 行为 1：支付
    public void pay() {
        ensureStatus(PENDING, "支付");
        this.status = PAID;
    }

    // 行为 2：取消
    public void cancel() {
        ensureStatus(PENDING, "取消");
        this.status = CANCELLED;
    }

    // 统一的规则校验：所有状态流转共用一份，新增状态只改这里
    private void ensureStatus(int expected, String action) {
        if (this.status != expected) {
            throw new IllegalStateException("订单当前状态不允许" + action +
                    "，当前状态：" + this.status);
        }
    }

    // 只有 getter，不暴露 setter——外部无法绕过行为改状态
    public Long getId() { return id; }
    public BigDecimal getTotalAmount() { return totalAmount; }
    public Integer getStatus() { return status; }
}
```

```java
// OrderService.java —— 变薄：只做"取对象 → 调行为 → 落库"
@Service
public class OrderService {
    @Autowired private OrderMapper orderMapper;

    @Transactional
    public void pay(Long orderId) {
        Order order = orderMapper.selectById(orderId);
        order.pay();                            // 规则在实体里
        orderMapper.updateById(order);
    }

    @Transactional
    public void cancel(Long orderId) {
        Order order = orderMapper.selectById(orderId);
        order.cancel();
        orderMapper.updateById(order);
    }
}
```

### 40.7.2 改造收益对比

| 维度 | 改造前（贫血） | 改造后（充血） |
| --- | --- | --- |
| 状态规则数量 | pay/cancel 各写一遍（2 处） | 实体 `ensureStatus` 一处 |
| 新增"退款"状态流转 | 在 Service 里再加方法 + 再写一遍校验 | 在 `Order` 里加 `refund()` 方法 |
| 非法改状态 | `setStatus(99)` 拦不住 | 无 setter，编译期就杜绝 |
| 单元测试 | Mock OrderMapper 才能测 | `new Order(...)` 直接测 `pay()/cancel()` |
| 业务可读性 | 规则埋在 Service 大方法里 | 读 `Order` 类 = 读订单规则 |

```java
// 改造后的实体单元测试：不依赖 Spring、不 Mock，跑得飞快
class OrderTest {
    @Test
    void pay_待支付订单_应成功() {
        Order order = new Order(1L, BigDecimal.TEN);
        order.pay();
        assertEquals(Order.PAID, order.getStatus());
    }

    @Test
    void pay_已支付订单_应拒绝() {
        Order order = new Order(1L, BigDecimal.TEN);
        order.pay();
        assertThrows(IllegalStateException.class, order::pay);   // 重复支付被拦
    }

    @Test
    void cancel_已支付订单_应拒绝() {
        Order order = new Order(1L, BigDecimal.TEN);
        order.pay();
        assertThrows(IllegalStateException.class, order::cancel);
    }
}
```

### 40.7.3 完整改造清单（可直接照抄）

```
改造 1：实体去掉 @Data，改为 构造器 + 私有字段 + 行为方法 + 必要 getter
改造 2：状态常量（PENDING/PAID/CANCELLED）定义在实体里，替代魔法数字
改造 3：Service 里所有 "if (order.getStatus() != x) throw" 下沉为实体的行为方法
改造 4：金额计算（总价、折扣）沉入实体方法（recalc/discount），Service 不再手算
改造 5：需要查外部数据的跨对象规则，抽成"领域服务 + 仓储接口"（40.5.4）
改造 6：实体方法保持纯内存可测，不要注入任何 Mapper/Service
```

## 40.8 常见坑与最佳实践

### 40.8.1 高频坑

| 坑 | 表现 | 规避 |
| --- | --- | --- |
| **胀血模型伪装充血** | 实体里注入 Mapper 直接查库 | 实体保持纯内存；查数据走仓储接口/领域服务 |
| **setter 全开** | `order.setStatus(5)` 绕过规则 | 去掉 setter，用行为方法 + 构造器 |
| **规则只下沉一半** | 状态机下沉了，金额计算还在 Service | 属于"实体自身"的计算类规则全部下沉 |
| **Service 没变薄** | 实体加了方法，Service 依旧几百行 | Service 只做：取对象 → 调行为 → 落库 → 事务 |
| **贫血/充血混合无边界** | 同一个模块一半规则在实体一半在 Service | 按"规则归属"划界：属实体的进实体，跨对象的进领域服务 |
| **把 DTO 当实体充血** | 给入参/出参 DTO 塞业务方法 | DTO 是传输对象，永远别带行为（第 10 章 MapStruct 场景） |
| **事务边界失控** | 实体方法里想开事务/调远程 | 事务归应用服务；实体行为保持本地纯逻辑 |
| **强行 DDD** | 简单 CRUD 也建聚合、领域服务 | 按 40.5.1 决策树，简单域保持贫血 |

### 40.8.2 最佳实践清单

```
□ 规则归属判定法：这个规则是"订单自己该知道的事"吗？→ 是则进 Order，否则留 Service/领域服务
□ 状态流转统一走实体方法，禁止外部 setStatus
□ 实体不依赖任何 Spring 容器、Mapper、远程调用
□ 实体行为保持"纯函数"风格：输入参数 + 改自己状态 + 抛异常，不产生副作用
□ 核心域（订单/支付/账户）优先充血，外围 CRUD 保持贫血
□ 跨对象协作放领域服务，仓储接口定义在领域侧、实现在基础设施侧（依赖倒置）
□ 用"状态机"表达复杂流转（可配合第 14 章状态模式，后续也可引入状态机框架如 Spring StateMachine）
```

> **与第二十八章呼应**：贫血模型的本质是违反 SRP（Service 职责过重）与封装；充血模型是让"内聚"落地。设计模式的"状态模式"与"策略模式"往往和充血模型天然搭配——把复杂的 `if/else` 状态机进一步拆成状态对象。

### 面试高频问题清单

| 问题 | 答案要点 |
| --- | --- |
| 什么是贫血模型？ | 对象只有数据与 getter/setter，业务逻辑全部在 Service 层；Martin Fowler 提出的反模式，却是业界主流 |
| 什么是充血模型？ | 对象既有数据又有业务行为，规则内聚在实体，Service 退化为协调者；DDD 战术设计的基础 |
| 两者本质区别？ | 业务逻辑放哪 + 封装性：贫血"数据与行为分离"、充血"数据与行为内聚" |
| 为什么国内主流是贫血模型？ | 上手简单、与 MyBatis-Plus 等 ORM 契合、三层架构分工清晰；缺点是规则易散落、Service 易膨胀 |
| DDD 一定要求充血模型吗？ | DDD 战术设计要求领域对象承载规则，天然倾向充血；但充血模型 ≠ DDD（还需限界上下文、聚合等） |
| 实体需要查数据怎么办？ | 依赖倒置：领域侧定义仓储接口，基础设施侧实现；跨对象规则放领域服务，实体保持纯内存 |
| 什么是失血/胀血模型？ | 失血=纯数据结构；胀血=实体里耦合基础设施（反模式），比贫血更糟 |
| 你们项目用哪种？为什么？ | 核心域充血 + 外围域贫血；说明渐进路线（40.5.3）与规则下沉收益 |
| 充血模型的事务边界在哪？ | 事务仍在应用服务（Service）层；实体行为是纯内存逻辑，不自行开事务 |
| 如何避免"伪 DDD"？ | 真 DDD = 战略设计（限界上下文）+ 战术设计（聚合/仓储/领域服务）+ 充血模型；只改命名不算 DDD |

### 本章小结

- **问题本质**（40.1）：业务逻辑放哪——贫血放 Service、充血放实体，对应"对象是否拥有行为"；
- **贫血模型**（40.2）：特征、优（简单/ORM 契合）劣（封装失效/规则散落/上帝类），Fowler 批评却成主流；
- **充血模型**（40.3）：数据 + 行为内聚、setter 收敛、实体不依赖基础设施，Service 变薄；
- **对比与四形态**（40.4）：维度对照表 + 失血/贫血/充血/胀血递进；
- **选型框架**（40.5）：决策树"核心复杂域充血、外围简单域贫血"、渐进演进三步走、依赖倒置与领域服务；
- **DDD 关系**（40.6）：DDD 战术设计基于充血模型，但充血 ≠ DDD，警惕伪 DDD；
- **实战改造**（40.7）：第 31 章订单模块"贫血→充血"全流程 + 纯内存单测收益；
- **坑与最佳实践**（40.8）：胀血伪装、setter 全开、规则只下沉一半、事务边界归属等 8 坑。
