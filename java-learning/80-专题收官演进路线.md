## 80.4 团队协作：Conway 定律 × 模块边界 × 团队拓扑

### 80.4.1 Conway 定律

> "设计系统的组织，其产生的设计等同于组织内的沟通结构。"

> —— Melvin Conway, 1968

应用到 DDD：模块边界 = 团队边界。

| 组织结构 | 系统架构 |
| --- | --- |
| 1 个团队 | 单体 |
| 3 个团队（按业务线） | 模块化单体（3 模块） |
| 5+ 个团队 | 微服务（5+ 服务） |
| 10+ 团队 + 多 BU | 中台 + 多 BU 服务 |

### 80.4.2 团队拓扑（Team Topologies）

> Matthew Skelton & Manuel Pais 提出的四种团队类型：

- **Stream-aligned team**：业务对齐的交付团队
- **Enabling team**：帮助其他团队提升能力的专家团队
- **Complicated subsystem team**：维护复杂子系统的专家团队
- **Platform team**：提供平台能力的团队

**应用**：

- 业务团队 = Stream-aligned team，按业务模块组织
- ArchUnit 工具 = Platform team 提供
- DDD 教练 = Enabling team 提供

## 80.5 常见误区（10 条）

### 误区 1：分层过度——CRUD 项目用 DDD

> 反例：用户管理工具用模块化单体 + 六边形 + CQRS

正解：CRUD 用三架构层足矣。

### 误区 2：分层不足——复杂业务用三层

> 反例：订单/支付/库存用 MVC + Service

正解：复杂业务用 DDD 四层 + 充血实体。

### 误区 3：领域贫血

> 反例：Order 只有 setter，逻辑全在 Service

正解：业务规则在 Order 行为方法内。

### 误区 4：DTO 穿透边界

> 反例：Controller 直接返回 Order 实体

正解：Controller 返回 DTO + Assembler 转换。

### 误区 5：仓储接口放在 Service 层

> 反例：OrderRepository 接口与 Service 同层

正解：仓储接口在领域层，实现在基础设施层。

### 误区 6：事务开在领域层

> 反例：Order.pay() 加 @Transactional

正解：@Transactional 只开在应用层。

### 误区 7：跨进程同步调用 Saga

> 反例：订单上下文同步 Feign 调用支付冻结接口

正解：异步事件 + Saga + Outbox。

### 误区 8：微服务焦虑——单体业务硬拆微服务

> 反例：3 人团队拆 5 个微服务

正解：先模块化单体，未来再拆。

### 误区 9：状态机滥用——简单流程上 Spring StateMachine

> 反例：单状态字段用 StateMachine

正解：StateMachine 用于多状态多迁移的复杂流程。

### 误区 10：ArchUnit 摆设——写了但不入 CI

> 反例：archunit 测试在本地跑，CI 不接入

正解：ArchUnit 测试接入 CI，违规红灯阻断。

### 答案提纲

> 每题 1 分钟标准答案（仅列要点）：

1. MVC 视图导向，三层业务导向，DDD 领域导向。
2. 源代码依赖由外向内，业务核心独立于技术细节。
3. 入口端口 = 业务核心能做什么；出口端口 = 业务核心需要什么。
4. 入口端口被主适配器调用；出口端口由从适配器实现。
5. 业务核心保持纯净，可纯 JUnit 测试，技术升级无侵入。
6. 用例编排 + 事务边界 + 跨聚合协调。
7. 业务规则在领域层；事务是"用例"概念，必须在应用层。
8. 命令 = 祈使句；查询 = 命名查询；都强类型不可变。
9. 本地事务 / 领域事件 / Saga。
10. 至少一件商品；状态机约束；对外只读视图。
11. 用表格列出 state + event + target_state。
12. 接口归调用方 / 降级兜底 / 数据转换。
13. 任一字段 ≥ 0；总和守恒；CHECK 防 DB 直接写入破坏。
14. 领域层校验业务不变量；SQL 原子条件防高并发 TOCTOU。
15. 余额非负 / 冻结非负 / 总额守恒 / 操作幂等。
16. 应用层先查；DB 不重复返查；唯一约束保底。
18. 编排式：中心化、易控、单点故障。协同式：去中心化、扩展好、调试难。
19. saga_id / step / status / payload / error / created_at。
20. 失败计数 + 指数退避 + 死信队列 + 人工处理。
21. 单体 → 模块化单体 → 微服务 → 云原生。
22. 模块边界清晰 + 单进程部署；模块边界靠 Maven + ArchUnit。
23. Maven / 包名 / ArchUnit / Checkstyle / SonarQube。
24. 模块边界 = 团队边界；按业务线组织团队。
25. 业务团队按业务模块组织；ArchUnit 工具由 Platform team 提供。
26. ArchUnit 测试作为 CI 必跑项，违规红灯阻断。
27. 跨服务调用链路过长 / 团队规模 < 服务数 / 拆分后业务不变量被破坏。
28. 业务规则永远在领域层（聚合根或领域服务）。
29. 演示一个完整重构案例；强调业务价值（可演进性）。
30. 用工程约束换长期可演进性。

## 80.8 致读者与专题结语

亲爱的读者：

完成本专题的 10 章内容 + 4 个示例工程后，你已经掌握了 Java 中 DDD 与分层架构的完整工程能力。

本专题的核心不是"再讲一遍 DDD"，而是：

> **把 40-46 章的"模式"串成"分层架构下的工程实现"**，
> **把"架构师口中的话"变成"工程师手上的代码"**，
> **把"短期收益"换成"长期可演进性"**。

分层架构不是银弹。CRUD 项目强行上 DDD 是过度设计；复杂业务不上 DDD 是技术债。**关键是匹配**——业务规则复杂度 × 团队规模 × 长期愿景，决定分层方案的强度。

DDD 也不是银弹。**DDD 的最大价值不是模式本身，而是"领域专家与开发团队用同一套语言对话"**。如果团队没有这个习惯，再精细的分层都是装饰。

愿你在项目中找到"恰到好处"的分层方案，在代码中实现"业务价值与工程美感"的平衡。

—— 写于第 80 章的最后一个字。
