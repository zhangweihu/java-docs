# 第四十七章 企业级架构专题（上）：高并发与高可用

> 本章目标：把前面所有章节的"术"汇入企业级架构的"道"——掌握架构演进路线（单体→集群→微服务）、高并发架构的核心手段（缓存、异步、分库分表、限流熔断降级）、高可用架构的保障手段（冗余、故障转移、多活、容灾）与 RPO/RTO 指标，能对订单系统做高并发改造实战并完成容量规划。
>
> 前置知识：第三十三章 MySQL（读写分离/分库分表）、第三十四章 Redis（缓存）、第十六章 RabbitMQ / 第二十七章 Kafka（异步）、第三十章 微服务治理（限流熔断降级）、第三十五章 Docker（部署）、第三十二章 实战（拆分）。

## 47.1 企业级架构全景：先看全局

### 47.1.1 什么是"企业级架构"

不是"用上了微服务"就叫企业级架构。企业级架构关注四个核心目标：

| 目标 | 回答的问题 | 典型手段 |
| --- | --- | --- |
| **高并发** | 1 万 QPS 打过来扛得住吗？ | 缓存、异步削峰、分库分表、水平扩展 |
| **高可用** | 机器挂了/机房挂了，业务断吗？ | 冗余、故障转移、多活、容灾 |
| **可观测** | 出问题能多快定位？ | 日志、监控、链路追踪（第 48 章） |
| **可演进** | 业务变了能低成本改吗？ | 分层、微服务、架构治理（第 48 章） |

> **一句话记忆**：企业级架构 = **并发扛得住 + 故障不停机 + 问题找得快 + 变更改得动**。本章解决前两个，第 48 章解决后两个。

### 47.1.2 性能指标（先统一度量衡）

| 指标 | 含义 | 经验参考 |
| --- | --- | --- |
| **QPS** | 每秒请求数（Query Per Second） | 单机 Spring Boot ≈ 500~2000 QPS（简单接口） |
| **RT** | 响应时间（Response Time） | 95 线 < 200ms 常见目标；TP99 < 500ms |
| **并发数** | 同时在处理的请求数（= QPS × RT） | 小公式：`并发数 = QPS × RT` |
| **吞吐量** | 单位时间处理量（TPS/QPS 同义不同场景） | 峰值 = 均值 × 3~5 倍（容量规划用） |

**并发数 = QPS × RT**（Little's Law）——这个公式贯穿本章：RT 压不下去，就得靠并行/异步提高吞吐。

## 47.2 架构演进路线：从单体到微服务

### 47.2.1 四步演进（每步都有动机与代价）

```
① 单体应用（单机 + 单库）
   │  动机：快速上线
   │  瓶颈：QPS 到天花板、单点故障
   ▼
② 集群化（多实例 + 负载均衡 + 共享数据库）
   │  动机：水平扩展（加机器就加 QPS）
   │  瓶颈：数据库成为新的单点（读写都打它）
   ▼
③ 读写分离 + 缓存（主从复制、Redis 缓存热数据）
   │  动机：读多写少，把读流量从主库卸下来
   │  瓶颈：写流量增长、单库容量
   ▼
④ 分库分表 + 异步化（sharding、MQ 削峰、消息解耦）
   │  动机：突破单库写瓶颈、解耦峰值
   │  瓶颈：分布式事务、跨分片查询（第 46 章、第 33 章）
   ▼
⑤ 微服务拆分（按业务拆服务，独立部署演进）
   │  动机：团队独立、独立扩展、独立故障域
   │  瓶颈：分布式复杂性（治理/事务/可观测）
   ▼
⑥ 云原生（容器化 + K8s + 弹性伸缩 + Service Mesh）
      动机：弹性、秒级扩缩容、基础设施自动化
```

> **关键认知**：每一步都是**"收益 > 新增复杂度"才走**。第 32 章 32.1 问过"什么时候该拆微服务"——同样道理，**大多数系统止步在 ③④ 就够用了**，别为了"先进"而拆。

### 47.2.2 演进原则（三条铁律）

1. **先优化，再扩展**：SQL 索引、连接池、缓存（第 25/33/34 章）没做就谈分库分表是本末倒置；
2. **增量演进**：每次只前进一步，每步可回滚（灰度发布见第 48 章）；
3. **瓶颈在哪解在哪**：QPS 上不去先看是 CPU/IO/DB/网络哪个瓶颈，对症下药。

## 47.3 高并发架构：四个常用武器

### 47.3.1 武器一：缓存（读多写少的第一选择）

把热点数据放 Redis（第 34 章），数据库压力瞬间下降：

```
请求 ──► 读缓存 ──命中──► 直接返回（90% 请求不到 DB）
             │未命中
             ▼
          查 DB ──► 回填缓存（带过期时间）
```

- **缓存什么**：热点商品详情、用户信息、配置、排行榜；
- **三大经典问题**（第 34 章详述）：缓存穿透（查不存在数据→打爆 DB，用空值/布隆过滤器）、缓存击穿（热点 key 过期瞬间并发打 DB，用互斥锁/逻辑过期）、缓存雪崩（大量 key 同时过期，用随机过期时间/多级缓存）；
- **缓存与 DB 一致性**：先更 DB 再删缓存（Cache Aside），配合延迟双删/版本号。

### 47.3.2 武器二：异步化（削峰填谷）

把"必须同步等结果"的链路拆开，峰值用 MQ 削平（第 16/27 章）：

```
同步（峰值打满）：用户点击 ──► 下单 ──► 扣库存 ──► 发短信（用户等 3 秒）
异步（削峰）：    用户点击 ──► 下单 ──► 返回"处理中" ──► MQ ──► 扣库存/发短信（后台慢慢做）
```

- **适用**：秒杀、抢购、批量通知、报表——**对响应时间不敏感的环节**；
- **注意**：异步引入最终一致（第 46 章）、消息可靠性（Outbox/事务消息）、幂等消费。

### 47.3.3 武器三：读写分离 + 分库分表（突破单库瓶颈）

```
读写分离（主从，第 33 章）：写走主库，读走从库（一主多从，读压力分摊）
分库分表（第 33 章）：     单表 > 500 万行/单库写满 → 按分片键水平拆分
  分片键选择（关键）：订单按 user_id 分片（同用户数据聚一起）、订单号含分片位
  代价：跨分片查询/聚合难、分布式 ID、全局唯一、扩容搬迁（第 38 章）
```

> **决策**：先读写分离（简单、无侵入），顶不住了再分库分表（复杂、慎重）。分库分表是"最后一招"，不是"标配"。

### 47.3.4 武器四：限流 / 熔断 / 降级（保护系统不倒）

**保护优先级：系统存活 > 部分可用 > 全部崩溃**（第 30 章 Sentinel 的治理思想）：

| 手段 | 作用 | 典型实现 |
| --- | --- | --- |
| **限流** | 挡住超出处理能力的流量 | 令牌桶/漏桶、Sentinel、网关层限流（第 36 章 Kong） |
| **熔断** | 下游故障时快速失败，不再傻等 | 熔断器三态（关闭/打开/半开）、Feign 降级 |
| **降级** | 主动砍掉非核心功能保核心 | 返回兜底数据、关闭推荐/评论、服务降级开关 |

```yaml
# Sentinel 限流规则示例（第 30 章）
# 下单接口：QPS > 200 直接拒绝（保护 DB）
# 评论接口：QPS > 50 降级返回空列表（核心交易不受影响）
```

> **顺序**：网关限流（入口）→ 服务限流熔断（内部）→ 降级兜底（保核心）。第 32 章 mall-cloud 已用 Sentinel，这里讲清"为什么"。

### 47.3.5 高并发口诀

```
读多 → 缓存； 写多 → 异步/分库； 峰值 → 削峰； 风险 → 限流熔断降级；
扛不住 → 水平扩展（加机器）； 优化顺序：索引 → 缓存 → 异步 → 分库分表 → 微服务
```

## 47.4 高可用架构：让故障"无感"

### 47.4.1 高可用的核心思想：冗余 + 故障转移

单点 = 必挂点。高可用 = **把每个单点都做成"挂了还能顶上"**：

| 层 | 单点风险 | 冗余方案 |
| --- | --- | --- |
| 应用层 | 单实例挂 | 多实例 + 负载均衡（Nginx/K8s） |
| 缓存层 | Redis 单点 | 主从 + 哨兵 / 集群（第 34 章） |
| 数据库 | MySQL 主库挂 | 主从 + MHA/半同步、PXC、双主 |
| 注册中心 | Nacos 挂 | 三节点集群（第 37 章） |
| 消息队列 | Broker 挂 | 镜像队列/集群、多副本 |
| 网关 | 网关挂 | 多网关 + DNS/LVS 前置 |
| 机房 | 机房挂 | 异地多活（47.4.3） |

**关键配套**：应用必须**无状态**（session 放 Redis，第 34 章）——否则任意实例都能接管请求。

### 47.4.2 健康检查与故障转移流程

```
负载均衡器/注册中心：
  定期健康检查（心跳/探活）──► 实例不健康 ──► 摘除流量 ──► 触发新实例拉起（K8s ReplicaSet）
  恢复健康 ──► 重新接入
```

配套机制：**重试**（超时重试下游）、**幂等**（重试不产生副作用，第 46 章）、**超时**（快速失败，不拖死调用方）。

### 47.4.3 容灾与多活：RPO / RTO 是核心指标

| 指标 | 含义 | 追求 |
| --- | --- | --- |
| **RPO**（恢复点目标） | 最多丢失多少数据（时间粒度） | 越小越好（0 = 不丢数据） |
| **RTO**（恢复时间目标） | 多久恢复服务 | 越小越好 |

```
容灾等级（从低到高）：
① 本地备份：每日全量备份（RPO=1 天, RTO=小时级）—— 能恢复但丢一天数据
② 同城灾备：异步复制到同城机房（RPO=秒级, RTO=分钟级）—— 挂了手动切
③ 两地三中心：主 + 同城灾备 + 异地冷备 —— 行业标准
④ 异地多活：双活/三活，流量智能调度（RPO≈0, RTO≈分钟级）—— 极贵极难
```

> **实践**：99.9%（每年 8.7 小时宕机）与 99.99%（每年 52 分钟）之间，是**钱与架构复杂度**的差距。**先定 SLA（服务可用性目标），再定架构**——RPO/RTO 是合同数字，不是口号。

### 47.4.4 故障演练：高可用是"练"出来的

- **定期演练**（第 48 章混沌工程）：主动杀进程、断网、停库，验证故障转移真的生效；
- **备份恢复演练**：光有备份不够，**定期演练恢复**（RPO/RTO 实测达标才算数）；
- **应急预案**：每个故障场景一张卡（谁发现、谁处理、怎么切、怎么回）。

## 47.5 容量规划：用数据决定加不加机器

### 47.5.1 容量估算公式

```
日请求量 × 高峰系数（3~5）÷ 秒 = 峰值 QPS
所需实例数 = 峰值 QPS ÷ 单实例可承受 QPS × 冗余系数（1.5~2）
例如：日活 100 万，人均 20 次请求 → 日请求 2000 万
    高峰系数 4 → 峰值 ≈ 2000万×4÷86400 ≈ 926 QPS
    单实例 1000 QPS → 需 1 台 + 冗余 1 台 = 2 台（留 50% 余量）
```

### 47.5.2 压测：容量规划的验证手段

- **工具**：JMeter / Gatling / wrk / 全链路压测（第 32 章提过）；
- **指标**：单实例最大 QPS、TP99 RT、资源水位（CPU/内存/IO）；
- **节奏**：性能基线 → 压力测试 → 瓶颈定位（慢 SQL、GC、锁、连接池）→ 优化 → 复测。

### 47.5.3 弹性伸缩（云原生）

- K8s HPA（水平自动扩缩）：CPU/内存/自定义指标触发，秒级拉起新 Pod（第 35 章）；
- 定时扩容：大促前按计划提前扩容（避开冷启动）；
- 缩容保护：流量回落后**延迟缩容**（防止抖动来回伸缩）。

## 47.6 实战：订单系统高并发改造

用第 31 章 mall-boot 订单模块走一遍改造：

```
现状（单体）：
  下单接口：查库存 → 写订单 → 扣库存（全部同步 DB，QPS ~500）

改造后（高并发版）：
  ① 缓存层：商品详情/库存走 Redis（读 90% 命中）           [武器一]
  ② 下单入口：写订单 → MQ 异步扣库存（先返回"下单中"）       [武器二]
     库存扣减用 Redis 原子操作防超卖（第 31 章）→ 异步回写 DB
  ③ 网关/服务限流：下单 QPS 限 2000，超出排队/拒绝           [武器四]
  ④ DB：读写分离（订单列表读从库）；订单表按 user_id 分片     [武器三]
  ⑤ 故障转移：服务 2 实例 + Redis 哨兵 + MySQL 主从         [高可用]

效果：QPS 500 → 5000+，单机故障不影响，RPO≈0（主从），RTO≈分钟级（自动切换）
```

> **改造原则**：每一步单独上线 + 压测验证（容量规划），不要一次性全上。**第 48 章的灰度发布是这些变更的安全网**。

## 47.7 练习与思考

1. **练习 A**：计算你正在做的系统容量：日活、人均请求、高峰系数 → 峰值 QPS → 需要几台机器（含冗余）；
2. **练习 B**：为订单列表页设计缓存方案（key 设计、过期策略、三大穿透问题防御）；
3. **练习 C**：给下单链路设计限流/熔断/降级三件套的规则与阈值，画保护顺序图；
4. **练习 D**：设计一个"两地三中心"方案：给出 RPO/RTO 目标、复制链路、切换流程。
