## 71.1 "分层"的本质：把变化频率不同的层切开

"分层"这个词在工程师日常里至少有三个含义，几乎所有的方案之争都源于把这三个含义混为一谈。

| 含义 | 关注点 | 典型代表 |
| --- | --- | --- |
| **物理分层** | 进程/部署单元分层 | 单体 / 微服务 / Serverless |
| **逻辑分层** | 同进程内代码组织分层 | MVC / 三层 / DDD 四层 |
| **架构分层** | 依赖方向与边界规则 | 整洁架构 / 六边形 |

本章讨论的是**逻辑分层 + 架构分层**——"代码如何在 Spring Boot 工程内分组"以及"组与组之间的依赖方向"。

### 71.1.1 为什么一定要分层

所有分层方案都试图回答同一个问题：

> **当业务规则变化时，我们希望只改某一个文件，而不是改一千个文件。**

为了让"修改收敛"，必须把变化频率不同的代码切开：

```
┌────────────────────────────────────────────────────────┐
│ 接口层（Interface）  ── 变化频率：最高                  │
│   Web API、CLI、定时任务、消息消费者                    │
├────────────────────────────────────────────────────────┤
│ 应用层（Application）  ── 变化频率：较高                 │
│   用例编排、事务边界、跨聚合协调                       │
├────────────────────────────────────────────────────────┤
│ 领域层（Domain）  ── 变化频率：低（业务规则稳定）       │
│   实体、值对象、聚合、领域服务、领域事件               │
├────────────────────────────────────────────────────────┤
│ 基础设施层（Infrastructure）  ── 变化频率：中（外部依赖）│
│   MyBatis、Redis、MQ、Feign、文件系统                  │
└────────────────────────────────────────────────────────┘
```

> 经验法则：业务规则稳定 = 变化频率低 = 不轻易改动 = 应当被外层保护。

### 71.1.2 分层的三大纪律

无论选择哪种分层方案，工程师必须遵守三条铁律：

1. **依赖方向单向**：外层可以依赖内层，内层绝对不能反向依赖外层。
2. **跨边界用接口**：当内层需要"某外层能力"时，定义接口让外层实现（依赖倒置）。
3. **跨边界传 DTO**：绝不把数据库 PO 直接传给 Controller，也绝不把 Controller 的请求 JSON 直接传给领域实体。

任何"破例"都要明确标注并 review——因为一旦破例，再好的分层都会被腐蚀。

## 71.2 MVC 模式（Model-View-Controller）

MVC 是 1979 年 Xerox PARC 提出的，最初用于桌面 GUI（Smalltalk），后来被 Web 框架吸收。

### 71.2.1 角色与职责

- **Model**：业务数据 + 业务行为。早期 Model 是贫血对象，行为都在 Service。
- **View**：渲染界面（JSP、Thymeleaf、Vue 模板）。
- **Controller**：接收请求 → 调用 Model → 选 View。

### 71.2.2 在 Spring Boot 下的退化

Web MVC 落地到 Spring 后，"View" 这一层通常被 JSON 取代，于是 Model-View-Controller 退化成 **"Controller-Service-Dao"**——这其实就是后两节式的"三层架构"。所以 MVC 与三层的界限实际很模糊。

```java
// Spring MVC 风格的 OrderController
@RestController
@RequestMapping("/orders")
public class OrderController {
    private final OrderService orderService;

    @PostMapping
    public OrderDTO create(@RequestBody CreateOrderRequest req) {
        return orderService.create(req);
    }
}
```

### 71.2.3 MVC 的强项与弱点

| 强项 | 弱点 |
| --- | --- |
| 学习曲线最低 | Model 容易退化为贫血对象 |
| 团队上手快 | 业务规则散落在 Service，跨 Service 复用难 |
| 与 Web 框架天然契合 | 大型项目"Service 爆炸"（每个业务一根 Service） |

## 71.3 三层架构（Presentation / Business / Data Access）

三层架构是 1990 年代 Java 企业版（J2EE）的主流分层，直到今天仍是国内大多数团队的默认选择。

### 71.3.1 经典三层

```
┌─────────────────────────────────┐
│ 表现层（Presentation Layer）    │   ← Controller、UI
├─────────────────────────────────┤
│ 业务层（Business Layer）        │   ← Service（事务脚本为主）
├─────────────────────────────────┤
│ 数据访问层（Data Access Layer） │   ← DAO / Mapper
└─────────────────────────────────┘
```

### 71.3.2 三层代码骨架

```java
// 1. Controller（表现层）
@RestController
public class OrderController {
    private final OrderService orderService;       // 依赖业务层
    @PostMapping("/orders")
    public Result<Long> create(@RequestBody OrderDTO dto) {
        return Result.ok(orderService.create(dto));
    }
}

// 2. Service（业务层，事务脚本）
@Service
@Transactional
public class OrderService {
    private final OrderDao orderDao;               // 依赖数据层

    public Long create(OrderDTO dto) {
        Order order = new Order();
        BeanUtils.copyProperties(dto, order);
        orderDao.insert(order);
        return order.getId();
    }
}

// 3. DAO（数据访问层）
@Repository
public class OrderDao {
    private final JdbcTemplate jdbc;
    public void insert(Order order) { /* INSERT */ }
}
```

### 71.3.3 三层的"Service 爆炸"问题

业务复杂后，每个用例都需要一个新 Service 方法，久而久之 OrderService 会有 50+ 方法、2000+ 行。更糟的是：

- **跨业务复用**：两个 Service 互相调用，形成网状依赖。
- **事务滥用**：所有方法都 `@Transactional`，事务边界模糊。
- **领域对象贫血**：Order 只是一个 setter 容器，所有逻辑在 Service。

> 这些问题正是 Eric Evans 在《领域驱动设计》中批评的——他称之为"**领域贫血症**"。

## 71.4 DDD 四层（User Interface / Application / Domain / Infrastructure）

Eric Evans 在《领域驱动设计》中提出的标准四层（后经 Vaughn Vernon 在《实现领域驱动设计》中规范化）。

### 71.4.1 四层角色与典型类

| 层 | 角色 | 典型类 |
| --- | --- | --- |
| User Interface（用户界面层） | 处理用户请求、渲染响应 | Controller、Page、CLI 入口 |
| Application（应用层） | 用例编排、事务边界、跨聚合协调 | AppService、Command、Query |
| Domain（领域层） | 业务规则、模型不变量 | Entity、ValueObject、Aggregate、DomainService、DomainEvent |
| Infrastructure（基础设施层） | 技术实现：DB、缓存、消息、远程调用 | MyBatis Mapper、Redis Client、Feign Client |

### 71.4.2 与三层的关键差异

```
三层架构                            DDD 四层
┌────────────────────┐              ┌────────────────────┐
│ Presentation        │              │ User Interface     │
├────────────────────┤              ├────────────────────┤
│ Business Service   │ ← 拆分为 →  │ Application Service│（用例编排）
│                    │              ├────────────────────┤
│                    │              │ Domain Model       │（充血模型）
├────────────────────┤              ├────────────────────┤
│ Data Access (DAO)   │              │ Infrastructure     │（PO/Mapper）
└────────────────────┘              └────────────────────┘
```

**核心差异**：

1. **业务层被拆为两层**：应用层（薄薄胶水）+ 领域层（业务规则承载）。
2. **领域对象充血**：Order 不再是 setter 容器，而是有行为方法（`pay()`、`cancel()`、`ship()`）。
3. **仓储接口在领域层**：领域层定义 `OrderRepository`，基础设施层实现 `MybatisOrderRepository`（依赖倒置）。

### 71.4.3 一个真正的 DDD 实体

```java
public class Order {
    private final OrderId id;
    private final CustomerId customerId;
    private OrderStatus status;
    private final List<OrderItem> items = new ArrayList<>();

    public Order(OrderId id, CustomerId customerId, List<OrderItem> items) {
        if (items.isEmpty()) throw new IllegalArgumentException("订单至少一件商品");
        this.id = id;
        this.customerId = customerId;
        this.items.addAll(items);
        this.status = OrderStatus.PENDING;
    }

    public void pay() {
        enforceStatus(OrderStatus.PENDING, "支付");
        this.status = OrderStatus.PAID;
        registerEvent(new OrderPaidEvent(this.id, Instant.now()));
    }

    public Money total() {
        return items.stream().map(OrderItem::subtotal)
                    .reduce(Money.ZERO, Money::add);
    }

    private void enforceStatus(OrderStatus expected, String action) {
        if (status != expected) {
            throw new IllegalStateException("当前状态" + status + "不允许" + action);
        }
    }
}
```

> 业务规则（"必须先支付才能发货"、"至少一件商品"）全部封装在 Order 内部——这就是**充血模型**。具体见第 40 章。

## 71.5 整洁架构（Clean Architecture）

Robert C. Martin 在 2012 年博客《The Clean Architecture》中提出，又称"同心圆架构"。

### 71.5.1 同心圆模型

```
              ┌─────────────────────────┐
              │  Frameworks & Drivers   │  ← Web、DB、UI、外部
              │  ┌───────────────────┐  │
              │  │ Interface Adapters│  │  ← Controller、Presenter、Gateway
              │  │ ┌───────────────┐ │  │
              │  │ │  Use Cases    │ │  │  ← 应用服务（业务用例）
              │  │ │ ┌───────────┐ │ │  │
              │  │ │ │ Entities  │ │ │  │  ← 领域实体（含业务规则）
              │  │ │ └───────────┘ │ │  │
              │  │ └───────────────┘ │  │
              │  └───────────────────┘  │
              └─────────────────────────┘
```

> **依赖规则**：源代码依赖只能由外向内，**绝不**内向外。内层不知道外层的存在。

### 71.5.2 与 DDD 四层的对应

| 整洁架构层 | DDD 四层 | 典型类 |
| --- | --- | --- |
| Entities（最内） | Domain | Entity、ValueObject、DomainService |
| Use Cases | Application | AppService、Command |
| Interface Adapters | Infrastructure + User Interface | Controller、Gateway、Presenter |
| Frameworks & Drivers（最外） | Infrastructure（具体技术） | Spring、MyBatis、Redis |

整洁架构其实是 DDD 四层的"几何表达"——它强调的不是"目录怎么分"，而是"依赖方向的边界"。

### 71.5.3 跨边界数据转换

整洁架构严格要求**跨边界传 DTO**——实体对象绝不穿透边界到 Controller，反之亦然。

```java
// 跨边界：领域实体 → Controller DTO
@Component
public class OrderResponseAssembler {
    public OrderResponseDTO toResponse(Order order) {
        return new OrderResponseDTO(
            order.getId().value(),
            order.getStatus().name(),
            order.total().amount()
        );
    }
}
```

这样 Controller 层不知道领域的内部结构，未来 Order 增加字段时，DTO 层可以选择不暴露。

## 71.6 六边形架构（Ports & Adapters）

Alistair Cockburn 在 2005 年提出，又称"端口与适配器架构"。

### 71.6.1 核心隐喻

把应用程序想象成一个**六边形**（任意形状都行），内部是业务核心，外部是各类适配器。

```
                  ┌──────────────────────┐
                  │   业务核心（Hexagon） │
                  │   Order、Customer、   │
                  │   Money、Rule        │
                  └──────────┬───────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
   ┌────▼─────┐         ┌────▼─────┐         ┌────▼─────┐
   │ REST API │         │  CLI     │         │   MQ     │  ← 入口适配器
   │ 适配器   │         │ 适配器   │         │  适配器  │  （Inbound Adapter）
   └────┬─────┘         └────┬─────┘         └────┬─────┘
        │                    │                    │
        └────────► Port (UseCase) ◄───────────────┘
                  │
                  ▼
        ┌──────────────────────────────────┐
        │ Port（仓储端口、远程调用端口）   │  ← 出口端口
        └──────────────────────────────────┘
                  ▲
        ┌──────────┼──────────┐
        │          │          │
   ┌────┴────┐ ┌───┴────┐ ┌───┴────┐
   │ MySQL  │ │ Redis  │ │ Feign  │  ← 出口适配器
   │ 适配器 │ │ 适配器 │ │ 适配器 │  （Outbound Adapter）
   └─────────┘ └────────┘ └────────┘
```

### 71.6.2 关键概念

- **Inbound Port（驱动端口）**：业务核心对外暴露的能力，对应 UseCase 接口。
- **Outbound Port（被驱动端口）**：业务核心需要的外部能力，对应 Repository、Gateway 接口。
- **主适配器（Driving Adapter）**：调用业务核心（如 REST Controller）。
- **从适配器（Driven Adapter）**：被业务核心调用（如 MyBatis 实现仓储接口）。

### 71.6.3 与整洁架构的关系

> 一句话：**六边形 = 整洁架构的简化工程表达**。

整洁架构强调"同心圆 + 依赖规则"，六边形强调"端口与适配器"。两者的本质诉求一致：**业务核心独立于外部技术**。

## 71.7 模块化单体（Modular Monolith）

### 71.7.1 提出的动机

微服务不是免费的午餐。Sam Newman 在《Building Microservices》第 2 版反复强调："**先单体，后微服务；先模块化，后拆分**。"

模块化单体就是把"未来可能要拆微服务的模块"提前在单体工程内做物理隔离。

### 71.7.2 工程结构

```
modular-monolith/
├── pom.xml                                  ← 父 POM（packaging=pom）
├── modular-common/                          ← 共享：DTO、异常、Util
├── modular-user/                            ← 用户上下文
│   ├── src/main/java/com/ddd/modular/user/
│   │   ├── domain/                          ← 领域层
│   │   ├── application/                     ← 应用层
│   │   └── infrastructure/                  ← 基础设施层
├── modular-order/                           ← 订单上下文（结构同上）
├── modular-inventory/                        ← 库存上下文
├── modular-payment/                         ← 支付上下文
├── modular-app/                             ← Spring Boot 启动模块
└── modular-archunit/                        ← 边界守护测试
```

### 71.7.3 模块边界守护手段

| 手段 | 作用 |
| --- | --- |
| Maven 模块依赖单向 | 物理层面杜绝反向依赖 |
| 包名规范 `com.ddd.modular.{ctx}.domain.*` | 视觉层面一眼识别模块 |
| ArchUnit 测试 | 运行时检测违规依赖 |
| 内部包 vs 对外 API 包分离 | 只暴露 `application.api`，不暴露 `domain` 内部 |

### 71.7.4 何时拆微服务

| 触发条件 | 拆法 |
| --- | --- |
| 单一模块需要独立部署频率 | 把该 Maven 模块拆出为独立服务 |
| 单一模块需要独立伸缩 | 同上，配合 K8s HPA |
| 团队按业务线拆分 | 每个模块对应一个团队、一个仓库 |
| 跨团队协作冲突 | 同上，物理隔离解决政治问题 |

> **本章第 75 章会详解 Modular Monolith 的工程实现**。

## 71.8 六种架构对比表

| 维度 | MVC | 三层 | DDD 四层 | 整洁 | 六边形 | 模块化单体 |
| --- | --- | --- | --- | --- | --- | --- |
| 业务承载 | Service | Service | Domain Model | UseCase+Entity | Domain+Port | Domain Model |
| 依赖方向 | 弱约束 | 单向（隐式） | 单向（强制） | 单向（强制） | 单向（强制） | 单向（强制 + 物理隔离） |
| 依赖倒置 | 几乎无 | 偶尔有 | 必须有 | 必须有 | 必须有 | 必须有 |
| 测试便利 | 难 | 一般 | 易 | 易 | 最易 | 易 |
| 上手成本 | 最低 | 低 | 中 | 中 | 中 | 高 |
| 适用规模 | 小项目 | 中型 | 中大型 | 中大型 | 中大型 | 中大型，未来拆微服务 |
| 与 Spring Boot 集成 | 天然 | 天然 | 良好 | 良好 | 良好 | 良好（多 Maven 模块） |
| 微服务过渡 | 直接拆（粒度粗） | 直接拆 | 可拆 | 可拆 | 可拆 | 平滑拆（Maven 模块 → Gradle 子项目 → 微服务） |
| 团队规模 | 1~3 人 | 3~8 人 | 5~15 人 | 5~15 人 | 5~15 人 | 10~50 人 |
| 业务复杂度 | 低 | 中 | 中高 | 中高 | 中高 | 高 |

> **核心观察**：从左到右，每一档都"多一份约束、多一份能力"。约束越多，演化空间越大。

## 71.9 实战：同一业务（订单）在六种分层下的代码骨架对照

业务描述：**创建订单**。客户端传 `customerId` 与 `items`，服务端创建 Order 实体、落库、返回 `orderId`。

### 71.9.1 MVC 风格

```java
@RestController
public class MvcOrderController {
    private final MvcOrderService service;

    @PostMapping("/mvc/orders")
    public Long create(@RequestBody MvcOrderRequest req) {
        return service.create(req);
    }
}

@Service
public class MvcOrderService {
    private final MvcOrderDao dao;

    @Transactional
    public Long create(MvcOrderRequest req) {
        MvcOrder order = new MvcOrder();
        order.setCustomerId(req.getCustomerId());
        order.setStatus("PENDING");
        order.setItems(req.getItems());
        dao.insert(order);
        return order.getId();
    }
}
```

### 71.9.2 三层风格

```java
@RestController
public class ThreeTierOrderController {
    private final ThreeTierOrderService service;
    @PostMapping("/three/orders")
    public Long create(@RequestBody ThreeTierOrderRequest req) {
        return service.create(req);
    }
}

@Service
public class ThreeTierOrderService {
    private final ThreeTierOrderMapper mapper;
    @Transactional
    public Long create(ThreeTierOrderRequest req) {
        ThreeTierOrder order = new ThreeTierOrder();
        BeanUtils.copyProperties(req, order);
        mapper.insert(order);
        return order.getId();
    }
}
```

### 71.9.3 DDD 四层风格

```java
@RestController
public class DddOrderController {
    private final DddOrderAppService appService;
    @PostMapping("/ddd/orders")
    public OrderId create(@RequestBody SubmitOrderCommand cmd) {
        return appService.submit(cmd);
    }
}

@Service
public class DddOrderAppService {
    private final OrderRepository repository;

    @Transactional
    public OrderId submit(SubmitOrderCommand cmd) {
        Order order = Order.create(
            OrderId.generate(),
            new CustomerId(cmd.getCustomerId()),
            cmd.getItems().stream().map(OrderItem::of).toList()
        );
        repository.save(order);
        return order.getId();
    }
}

// 仓储接口定义在领域层
public interface OrderRepository {
    void save(Order order);
    Optional<Order> findById(OrderId id);
}
```

### 71.9.4 整洁架构风格

```java
// 适配器层：Controller
@RestController
public class CleanOrderController {
    private final SubmitOrderUseCase useCase;
    @PostMapping("/clean/orders")
    public OrderResponseDTO create(@RequestBody OrderRequestDTO req) {
        SubmitOrderCommand cmd = OrderRequestAssembler.toCommand(req);
        OrderId id = useCase.execute(cmd);
        return new OrderResponseDTO(id.value());
    }
}

// 用例层（接口 + 实现）
public interface SubmitOrderUseCase {
    OrderId execute(SubmitOrderCommand cmd);
}

@Service
public class SubmitOrderUseCaseImpl implements SubmitOrderUseCase {
    private final OrderRepository repository;
    @Override
    public OrderId execute(SubmitOrderCommand cmd) {
        Order order = Order.create(/* ... */);
        repository.save(order);
        return order.getId();
    }
}
```

### 71.9.5 六边形风格

```java
// 入口适配器
@RestController
public class HexOrderController {
    private final SubmitOrderPort port;
    @PostMapping("/hex/orders")
    public void create(@RequestBody OrderRequestDTO req) {
        port.execute(SubmitOrderCommand.from(req));
    }
}

// 入口端口（业务核心对外）
public interface SubmitOrderPort {
    void execute(SubmitOrderCommand cmd);
}

// 业务核心（实现端口）
@Service
public class OrderService implements SubmitOrderPort {
    private final OrderRepositoryPort repository;        // 出口端口
    @Override
    public void execute(SubmitOrderCommand cmd) {
        Order order = Order.create(/* ... */);
        repository.save(order);
    }
}

// 出口端口
public interface OrderRepositoryPort {
    void save(Order order);
}

// 出口适配器（基础设施层）
public class HexOrderRepositoryAdapter implements OrderRepositoryPort {
    private final OrderMapper mapper;
    @Override
    public void save(Order order) { mapper.insert(OrderAssembler.toPO(order)); }
}
```

### 71.9.6 模块化单体风格

模块化单体**不是"另一种分层"，而是"用 Maven 多模块承载 DDD 四层/六边形"**——结构与 DDD 四层一致，但每个上下文是独立 Maven 模块。

```java
// modular-order 模块内
package com.ddd.modular.order.application.service;

@Service
public class OrderAppService {
    private final OrderRepository repository;
    public OrderId submit(SubmitOrderCommand cmd) { /* 同 DDD 四层 */ }
}

// modular-app 模块聚合所有上下文
@SpringBootApplication
public class ModularApplication {
    public static void main(String[] args) {
        SpringApplication.run(ModularApplication.class, args);
    }
}
```

## 71.10 选型决策树

```
你的项目当前状态是什么？
│
├── 1~3 人小团队、原型/工具型项目
│   │
│   ├── 业务规则简单（CRUD 为主） ──► 三层架构 ✅
│   └── 有复杂业务规则 ──► DDD 四层 ✅（从一开始就正确建模）
│
├── 3~8 人中型团队、中型项目
│   │
│   ├── 业务规则中等 ──► 整洁架构（Spring Boot 工程内） ✅
│   ├── 业务规则复杂 ──► 六边形架构 ✅
│   └── 计划未来拆微服务 ──► 模块化单体 ✅
│
├── 10~50 人大团队、大型企业应用
│   │
│   ├── 已经具备清晰业务边界 ──► 模块化单体（按上下文拆 Maven 模块）✅
│   ├── 已经在多个微服务上 ──► 评估是否回到模块化单体（避免分布式复杂度）⚠️
│   └── 高并发/高可用场景 ──► 微服务（同时应用六边形约束业务核心）✅
│
└── 50+ 人超大团队、超大规模
    │
    ├── 业务条线清晰 ──► 微服务 + 模块化单体（每个微服务内部）✅
    └── 业务条线模糊 ──► 先重构到模块化单体，再拆微服务 ⚠️
```

> **一句话选型原则**：**业务规则越复杂，分层约束要越强；团队规模越大，分层物理隔离要越明显**。

### 本章小结

- 分层的本质是"变化频率分层 + 依赖方向约束"。
- 6 种方案从弱约束到强约束递进：MVC → 三层 → DDD 四层 → 整洁 → 六边形 → 模块化单体。
- 业务复杂度和团队规模决定分层方案的强度。
- **本专题剩余章节将逐一落地 6 种方案**，配 4 个可运行 Spring Boot 示例工程。
