# 第四十九章 K8s 深度专题（从会部署到懂原理）

> 本章目标：第十九章、第三十五章带你"会用 K8s"，本章带你"懂 K8s"——吃透控制面/数据面架构、控制器循环（Reconcile）设计思想、调度策略、CNI 网络模型、PV/PVC 存储体系、RBAC 安全模型，并完成 Java 应用在 K8s 上的生产级部署（滚动更新、HPA 弹性伸缩、优雅停机、探针与资源 QoS），具备排查与设计生产集群的能力。
>
> 前置知识：第十九章 Docker 与 K8s、第三十五章 Docker 系统学习（镜像/Compose）、第三十六章 Kong 网关（K8s Ingress）、第三十章微服务治理、第三十一章 Spring Boot 项目实战。

## 49.1 为什么要"深挖"K8s

### 49.1.1 从"会部署"到"懂原理"的鸿沟

前两章你已经会：写 Deployment、暴露 Service、用 Ingress 访问。但生产集群里一次 Pod 卡在 `ContainerCreating`、一次滚动更新全部 502、一次节点宕机后应用 10 分钟没恢复——这些才是真正的日常。

K8s 是**声明式**系统：你描述"期望状态"（desired state），K8s 自己持续把"当前状态"（current state）逼近它：

```
用户声明：replicas: 3, image: mall:1.2.0
     │
     ▼
控制器循环（无限跑）：观测现状 → 对比差异 → 采取措施 → 再观测
现状 2 个副本 → 差异 -1 → 创建 1 个 Pod → 现状 3 个 → 无差异 → 睡觉
```

> **一句话记忆**：K8s 不是"帮我部署"的工具，而是一台"期望状态驱动器"——你只负责声明，它负责收敛。理解这条循环，就理解了 K8s 的 90% 设计。

### 49.1.2 与 Docker Compose 的本质差异

| 维度 | Docker Compose | Kubernetes |
| --- | --- | --- |
| 运行位置 | 单机 | 集群（多节点） |
| 状态维护 | 命令式（up/down） | 声明式（期望状态收敛） |
| 故障自愈 | 无 | 控制器自动重建/迁移 |
| 弹性伸缩 | 手动 | HPA 自动扩缩容 |
| 服务发现 | 依赖内部网络别名 | Service + DNS + 负载均衡 |
| 存储 | 本地卷/命名卷 | PV/PVC 动态供给 |
| 配置 | env_file | ConfigMap/Secret |

## 49.2 集群架构：控制面与数据面

### 49.2.1 一张图看懂架构

```
                    ┌─────────────── 控制面（Master，管全局）───────────────┐
                    │  kube-apiserver（唯一入口，所有操作的"门卫"）            │
                    │      │  认证→授权→准入控制→写 etcd → 通知订阅者           │
                    │  etcd（键值存储，集群唯一真相）                          │
                    │      ▲                                               │
                    │  kube-controller-manager（各种控制器，如 Deployment 控制器）│
                    │  cloud-controller-manager（云负载均衡/存储等，云上才有）     │
                    │  kube-scheduler（给新 Pod 挑节点）                       │
                    └──────────────────────────────────────────────────────┘
                                        │ watch
      ┌───────────────┬─────────────────┴───────────────┬───────────────┐
      ▼               ▼                                 ▼               ▼
┌───────────┐  ┌───────────┐                    ┌───────────┐    ┌───────────┐
│ Node 1    │  │ Node 2    │                    │ Node N    │    │  数据面   │
│ kubelet   │  │ kubelet   │                    │ kubelet   │    │（干活的人）│
│ kube-proxy│  │ kube-proxy│                    │ kube-proxy│    │           │
│ 容器运行时 │  │ 容器运行时 │                    │ 容器运行时 │    │           │
│ (Pod 们)   │  │ (Pod 们)   │                    │ (Pod 们)   │    │           │
└───────────┘  └───────────┘                    └───────────┘    └───────────┘
```

- **kube-apiserver**：集群"大脑入口"。所有 kubectl、控制器、kubelet 都通过它通信，只有它读写 etcd；
- **etcd**：raft 一致性键值库，存所有对象（Deployment、Pod、ConfigMap……），是"唯一真相源"；
- **kube-controller-manager**：一堆控制器进程，各自盯着自己负责的对象跑 Reconcile 循环；
- **kube-scheduler**：为待调度 Pod 打分选节点（资源、亲和性、污点……）；
- **kubelet**：每台 Node 上的"监工"，向 apiserver 汇报，并负责启停 Pod 里的容器、执行探针；
- **kube-proxy**：维护 Service 的 iptables/IPVS 规则，把流量转发到后端 Pod。

> **排障金句**：Pod 起不来先看 `kubectl describe pod`；调度不了看 `Events`；网络不通先看 Service 的 endpoints 是否有 Pod。

### 49.2.2 一次完整请求的旅程（Pod 创建）

```
kubectl apply -f deploy.yaml
  1. kubectl → kube-apiserver（认证 + 校验 + 准入）→ 写入 etcd
  2. Deployment 控制器 watch 到新对象 → 创建 ReplicaSet（同样走 apiserver）
  3. RS 控制器 watch 到 → 创建 Pod 对象（无节点）
  4. Scheduler watch 到未调度 Pod → 选节点 → 把 nodeName 写回 Pod
  5. 目标 Node 的 kubelet watch 到 → 调 CRI 创建容器（拉镜像→创建→启动）
  6. 容器运行 → kubelet 汇报状态 → Pod 进入 Running
```

## 49.3 核心对象与控制器设计

### 49.3.1 控制器分层：Deployment → ReplicaSet → Pod

```
Deployment（你要什么版本、几个副本）
    │ 管理
    ▼
ReplicaSet（固定镜像版本的"副本确保者"）
    │ 管理
    ▼
Pod（真正的运行单元，含 1~N 个容器 + 共享网络/存储）
```

滚动更新时，Deployment 不是改现有 Pod，而是**新建一个 RS**（新版本），旧 RS 缩容、新 RS 扩容，所以**回滚=把 RS 切回去**：

```
kubectl rollout history deployment/mall
kubectl rollout undo deployment/mall --to-revision=2
```

### 49.3.2 控制器家族：什么时候用谁

| 控制器 | 适用场景 | 关键特性 |
| --- | --- | --- |
| **Deployment** | 无状态应用（Java Web 服务） | 滚动更新、回滚、HPA 挂载点 |
| **StatefulSet** | 有状态应用（MySQL/ES/Kafka/ZK） | 稳定网络标识（pod-0）、稳定存储、有序启停 |
| **DaemonSet** | 每节点必须一个（日志采集/监控探针） | 新节点加入自动补一个 |
| **Job** | 一次性任务（数据迁移、批处理） | 跑完即完成 |
| **CronJob** | 定时任务（XXL-Job 替代/报表） | 按 Cron 周期创建 Job |

> **Java 场景提醒**：你写的 Spring Boot 服务一律用 Deployment；如果自己做 XXL-Job 执行器想省调度中心，可考虑 CronJob，但更推荐保留 XXL-Job（第 18 章）。

### 49.3.3 探针：K8s 眼中的"健康"标准

K8s 不知道你的应用逻辑，探针就是它判断"活没活、能不能接流量"的标准：

| 探针 | 回答 | 失败后果 | Java 典型配置 |
| --- | --- | --- | --- |
| **livenessProbe** | 进程还活着吗？ | 重启容器 | `GET /actuator/health/liveness` |
| **readinessProbe** | 能接流量吗？ | 从 Service 摘除（不重启） | `GET /actuator/health/readiness` |
| **startupProbe** | 启动完成了吗？ | 重启（保护慢启动应用） | Spring Boot 3 内置，给 60s 宽限 |

Spring Boot 3 的 `spring-boot-starter-actuator` 直接提供 liveness/readiness 两个探针端点，Java 应用在 K8s 里**必须配全三个探针**，这是"优雅上下线"的基础。

## 49.4 调度：Pod 放到哪台机器

### 49.4.1 调度过程与策略

Scheduler 给每个待调度 Pod 打分（资源充足度、亲和性、分散性……），选最高分节点。你可以用**约束**影响它：

| 机制 | 作用 | 示例 |
| --- | --- | --- |
| `nodeSelector` | 精确按 label 挑节点 | 有 GPU 的节点 |
| `nodeAffinity` | 软/硬偏好（比 selector 强大） | `preferredDuringScheduling` 尽量放高内存机器 |
| `podAffinity` | 与某类 Pod 靠一起 | 缓存与业务同节点（少跨机） |
| `podAntiAffinity` | 与某类 Pod 分开 | 同服务的两个副本**绝不能同节点**（容灾） |
| `taints/tolerations` | 污点：节点"标记拒绝"，容忍：Pod "偏要上" | 专用节点、隔离故障节点 |

> **生产铁律**：多副本无状态服务必须配 `podAntiAffinity` 或 `topologySpreadConstraints`，否则一次节点宕机=整组服务全挂。

### 49.4.2 Java 服务调度配置示例

```yaml
affinity:
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels: { app: mall-order }
          topologyKey: kubernetes.io/hostname   # 副本尽量分散到不同节点
```

## 49.5 网络模型：流量怎么走

### 49.5.1 从 Pod IP 到 Service 到 Ingress

```
用户 ──► Ingress（域名/路径路由，可用 Kong/Nginx Ingress Controller）
            │
            ▼
        Service（ClusterIP，虚拟 IP + iptables/IPVS 规则，做负载均衡）
            │   selector 匹配 Pod label
            ▼
        Pod A / Pod B（同一 Deployment 的两个副本，共享 ClusterIP 流量）
```

- **Pod 网络**：集群内每个 Pod 有独立 IP，Pod 之间直接互通（CNI 插件实现，如 Calico/Flannel/Cilium）；
- **Service 四种类型**：`ClusterIP`（集群内）、`NodePort`（节点端口暴露）、`LoadBalancer`（云 LB）、`Headless`（无 VIP，直连 Pod，给 StatefulSet 用）；
- **DNS**：`<service>.<namespace>.svc.cluster.local`，Java 服务间调用只需用服务名，K8s 自动解析。

### 49.5.2 Java 侧的影响

- 服务间调用（Feign/HTTP）直接写服务名 + 端口，K8s DNS 解析到 Service；
- **不要缓存 DNS/IP**（Pod 重建 IP 会变），连接池要能感知重建（Spring Cloud LoadBalancer 已处理）；
- `kubectl port-forward` 是本地调试神器：把集群里 Pod 端口映射到本机。

## 49.6 存储：有状态应用的根基

### 49.6.1 PV/PVC/StorageClass 三层

```
StorageClass（"存储模板"：用什么存储后端、什么策略）
    │ 动态供给：PVC 一申请，自动创建 PV
    ▼
PV（PersistentVolume：一块真实存储，如云盘/NFS/本地盘）
    ▲
PVC（PersistentVolumeClaim：应用"申请"一块盘，像声明资源）
    │
    ▼
Pod 挂载使用
```

- **静态供给**：管理员先建好 PV，PVC 去匹配；
- **动态供给**：配置 StorageClass 后 PVC 自动触发 PV 创建（云上标配，如 `alicloud-disk`）；
- **StatefulSet + volumeClaimTemplates**：每个副本自动获得独立 PVC，数据不共享（MySQL 主从分盘的基础）。

### 49.6.2 Java 应用存储选择

| 数据类型 | 建议 | 原因 |
| --- | --- | --- |
| 日志 | 不落盘，走 stdout → 采集 | 容器可随时删，日志不能依赖本地盘 |
| 临时文件 | emptyDir（内存/临时盘） | 生命周期随 Pod |
| 配置/密钥 | ConfigMap / Secret | 挂载为文件或环境变量 |
| 数据库数据 | 托管数据库（云 RDS）或 StatefulSet+云盘 | 别把 MySQL 跑在无状态 Deployment 里 |

## 49.7 配置与安全：ConfigMap / Secret / RBAC

### 49.7.1 配置管理的三种形态

| 形态 | 用途 | 注意 |
| --- | --- | --- |
| 环境变量（from ConfigMap） | 简单键值（日志级别、开关） | 变更需重启 Pod |
| 挂载文件（from ConfigMap） | 配置文件（application.yml 分环境） | 变更后部分应用热加载 |
| Secret | 密码/Token/证书 | Base64 只是编码，生产要加密（KMS/SealedSecrets） |

**Spring Boot 实践**：把 `application-prod.yml` 做成 ConfigMap 挂载覆盖，环境差异全部外置；敏感信息用 Secret，配合 `spring-cloud-starter-kubernetes` 或 Vault 更佳。

### 49.7.2 RBAC：最小权限

```
ServiceAccount（Pod 的身份）──绑定──► Role/RoleBinding（命名空间内）
                                    └─► ClusterRole/ClusterRoleBinding（全局）
```

Java 服务若要操作 K8s API（如自研 Operator、动态配置），务必为它建专用 ServiceAccount 并只授权需要的资源，**不要用默认账户 + cluster-admin**。

## 49.8 Java 应用生产部署实战

### 49.8.1 一次完整的滚动更新配置

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mall-order
  labels: { app: mall-order }
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1        # 更新期间最多 1 个不可用
      maxSurge: 1              # 最多多起 1 个新副本（先起新再退旧）
  selector:
    matchLabels: { app: mall-order }
  template:
    metadata:
      labels: { app: mall-order }
    spec:
      containers:
        - name: order
          image: registry.cn-hangzhou.aliyuncs.com/mall/order:1.2.0
          ports: [{ containerPort: 8080 }]
          resources:
            requests: { cpu: "500m", memory: 512Mi }   # 调度与 QoS 依据
            limits:   { cpu: "2",    memory: 1Gi }      # 超限被杀
          startupProbe:                                 # 慢启动保护
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            initialDelaySeconds: 15
            periodSeconds: 10
            failureThreshold: 6
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8080 }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /actuator/health/liveness, port: 8080 }
            periodSeconds: 10
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 10"]       # 优雅停机宽限
      terminationGracePeriodSeconds: 60                 # 等 Spring 平滑下线
```

### 49.8.2 优雅停机为什么必须做

容器被删时 K8s 发 SIGTERM，但**新流量还在进**——Spring Boot 默认会立刻断开连接，导致 502。三步闭环：

1. readinessProbe 先把 Pod 从 Service 摘掉（不再收新流量）；
2. `preStop` sleep 10s 留出摘除生效窗口；
3. Spring Boot 收到 SIGTERM 后优雅关闭线程池/连接池（默认已支持），在 `terminationGracePeriodSeconds` 内完成在途请求。

### 49.8.3 HPA：按负载自动伸缩

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: mall-order-hpa
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: mall-order }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 60 }  # CPU>60% 扩容
    - type: Resource
      resource:
        name: memory
        target: { type: Utilization, averageUtilization: 80 }
```

> 与第 47 章呼应：HPA 是"容量规划"的自动化补充——突发流量自动扩，闲时自动缩。但**扩容有冷启动延迟**（镜像拉取+JVM 启动），大促前要配合 `minReplicas` 预热 + 压测验证扩容速度。

### 49.8.4 资源 QoS：别让你的 Pod 被随机杀掉

| requests/limits 组合 | QoS 等级 | 节点资源不足时 |
| --- | --- | --- |
| 都不设 | BestEffort | **最先被杀** |
| requests=limits | Guaranteed | 最晚被杀（推荐生产） |
| requests < limits | Burstable | 中间 |

**Java 注意**：JVM 堆（`-Xmx`）要小于 Pod 的 memory limit（建议 limit 的 50~70%），否则容器被 OOMKill 时 JVM 还没触发 GC；CPU limit 别设太小，否则 GC 线程被限流导致吞吐崩。

## 49.9 生产实践：故障与治理

### 49.9.1 常见故障排查表

| 症状 | 排查路径 |
| --- | --- |
| Pod `Pending` | `kubectl describe pod` 看 Events：资源不足/污点/亲和性无节点 |
| Pod `CrashLoopBackOff` | 看日志：启动失败/探针失败/镜像不存在 |
| `ImagePullBackOff` | 镜像名/私有仓库认证/网络问题 |
| 滚动更新 502 | 探针未生效、优雅停机没做、Ingress 缓存旧端点 |
| Service 不通 | `kubectl get endpoints` 是否为空；selector label 是否匹配 |
| 节点 NotReady | 登录节点看 kubelet 日志、磁盘满、网络抖动 |

### 49.9.2 运维治理要点

- **PDB（PodDisruptionBudget）**：声明"最多允许几个副本同时不可用"，防止节点维护（drain）时整组服务被赶下线；
- **资源配额（ResourceQuota/LimitRange）**：限制命名空间总量，防止某个团队占满集群；
- **集群升级**：先升级控制面再逐节点滚动升级数据面，升级前确认 etcd 备份；
- **日志/监控/追踪**：把第 48 章的 ELK/Prometheus/SkyWalking 通过 DaemonSet 部署到集群，实现"开箱可观测"。

## 49.10 练习与思考

1. **练习 A**：用 kind/minikube 起一个本地集群，部署一个 Spring Boot 服务（含探针+优雅停机+资源限制），执行滚动更新并观察 `kubectl rollout status`；
