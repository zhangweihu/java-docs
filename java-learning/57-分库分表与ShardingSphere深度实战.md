# 第五十七章 分库分表与 ShardingSphere 深度实战（从概念到生产）

> 本章目标：第三十三章讲了分库分表"是什么"，第四十七章讲了"何时用"，本章讲透"怎么做"——掌握垂直/水平拆分的完整方法论、分片键设计铁律、四大分片策略与扩容对比，用 ShardingSphere-JDBC/Proxy 完成订单系统分库分表实战，并解决分布式 ID、跨分片查询、数据迁移扩容、分布式事务协同等生产难题，形成"要不要分 → 怎么分 → 怎么接 → 怎么运维"的完整闭环。
>
> 前置知识：第三十三章 MySQL（主从/读写分离）、第三十四章 Redis、第四十六章 分布式事务与 Saga、第四十七章 高并发架构、第三十八章 数据迁移。

## 57.1 先回答"要不要分"：触发条件与决策顺序

分库分表是"最后一招"，不是"标配"。动手之前先用一张决策表自检：

| 信号 | 阈值参考 | 优先手段（先做这些） | 何时才轮到分库分表 |
| --- | --- | --- | --- |
| 单表数据量 | > 2000 万行 | 索引优化（25 章）、归档冷数据 | 冷数据都清了还在涨 |
| 单表写 QPS | > 2000~3000 | 连接池/批处理/缓存写回 | 写入成为硬瓶颈 |
| 单库连接数 | 连接池打满 | 池参数/读写分离 | 连接仍是瓶颈 |
| 单库容量 | 磁盘/备份超时 | 冷热分层、清理 | 容量规划无法满足 |

```
决策顺序铁律：索引 → 缓存（34 章）→ 读写分离（33 章）→ 分库分表 → 微服务拆分
                                        │
                    分库分表是"结构性手术"，一次决定，终身跟随，尽量晚做
```

> **一句话记忆**：分库分表解决的是"单机物理上限"（容量 + 写并发），凡是能用钱和代码解决的（加索引、加缓存、加从库），都不要先动刀。

## 57.2 拆分的四象限：垂直 vs 水平 × 库 vs 表

| 拆分维度 | 库（Database） | 表（Table） |
| --- | --- | --- |
| **垂直**（按业务/字段） | 按业务域拆库：用户库/订单库/库存库（微服务天然伴随） | 拆宽表：核心字段表 + 扩展字段表（字段 > 20 个、热点字段分离） |
| **水平**（按数据行） | 同一张表散到多个库：`order_db_0` ~ `order_db_7` | 同一张表散到多张表：`order_0` ~ `order_15` |

四个象限组合出三种常见形态：

```
形态一：水平分表（单库）      order_db → order_0 / order_1 / ... / order_15
形态二：分库分表（最常用）    order_db_0→order_0..7、order_db_1→order_0..7（库表双分）
形态三：垂直分库 + 水平分表   业务域分库，库内再水平分表（订单域、库存域各自分）
```

**选型判断**：

| 场景 | 推荐 |
| --- | --- |
| 单表大、但库压力不大 | 先水平分表（最轻） |
| 单库写入/连接成为瓶颈 | 分库（水平分库） |
| 业务天然多域 | 垂直分库（和微服务拆分同步做） |
| 大宽表、字段冷热不均 | 垂直分表（垂直拆表，少见但有效） |

## 57.3 分片键设计：决定成败的第一铁律

**分片键（Sharding Key）= 查询路由的依据 = 数据分布的依据**，选错了整个架构都救不回来。三条铁律：

1. **选查询最频繁、最均匀的字段**：订单系统选 `user_id`（用户维度查询最多），而不是 `order_no`（几乎不做范围遍历）。
2. **同用户数据必须落在同一片**：`user_id` 分片 → 一个用户的所有订单在同一库表 → 用户维度的分页/聚合/事务都是单片操作。
3. **主键必须与分片键解耦且全局唯一**：主键用分布式 ID（见 57.9），分片键独立存储。

```
❌ 反例：按 order_id 分片，却要高频查"某用户的订单列表" → 全分片扫描
✅ 正例：按 user_id 分片，订单列表天然单片；按 order_id 点查 → 用 用户ID→订单 索引表 或 order_id 内嵌分片位
```

**分片位内嵌（推荐技巧）**：让主键直接可路由。例如订单号 = `时间戳 + 用户分片位 + 序列号`，点查订单号时无需知道 user_id 就能算出分片。

> **面试高频**：为什么订单表按 user_id 分片而不是按 order_no？答：查询模式决定分片键——绝大多数流量是"查我的订单"，按 user_id 分片保证该查询是单片操作；若按 order_no 分片，用户订单列表必须广播到所有分片再合并。

## 57.4 分片策略：四种算法与扩容成本对比

| 策略 | 规则 | 优点 | 缺点 | 扩容 |
| --- | --- | --- | --- | --- |
| **哈希取模** `user_id % 8` | 均匀 | 最均匀、实现简单 | 扩容需全部搬迁 | 难（翻倍扩容法缓解） |
| **范围分片** `按时间/ID 段` | 区间 | 天然支持范围查询、扩容只搬新片 | 热点（新数据集中） | 易（加新区间） |
| **一致性哈希** | 哈希环 | 扩容影响小（只迁移环上相邻节点） | 实现复杂、虚拟节点调优 | 中 |
| **时间分片** `yyyyMM` 月表 | 时间 | 归档友好、天然冷热分层 | 单一时间点查询热点 | 易 |

**生产组合打法**：哈希 + 时间双维度（一级按 `user_id` 哈希分片、二级按月归档），兼顾均匀与冷热。

> **扩容的代价是核心指标**：取模 8 扩容到 16，理论上迁移量 = 约一半数据；一致性哈希只迁移约 1/N；时间分片几乎零迁移。选策略前先想清楚"两年后要不要扩容"。

## 57.5 读写分离 × 分库分表组合架构

分库分表通常和读写分离叠加（每片一主多从），完整数据访问层形态：

```
应用
 │  ShardingSphere-JDBC（客户端，内嵌于应用）
 ├─► 路由：user_id % 8 → 分片 order_db_0 ~ order_db_7
 ├─► 读写分离：每片内 写→主库，读→从库（负载均衡/权重）
 └─► SQL 改写 / 结果归并（跨片聚合、分页）
```

| 形态 | 写路径 | 读路径 |
| --- | --- | --- |
| 单片（同用户） | 直达该片主库 | 该片从库 |
| 跨片（管理端/后台） | 各片主库 | 各片从库 + 归并 |

> **后台查询的解药**：C 端查询都按分片键走，但运营后台要"全量聚合查询"——不要硬扛，把数据同步到 ES（20 章）或数仓，后台查询走 ES。**分库分表后，禁止所有表做全片扫**。

## 57.6 ShardingSphere 生态：JDBC vs Proxy 怎么选

Apache ShardingSphere 提供两种接入形态：

| 维度 | **ShardingSphere-JDBC**（客户端） | **ShardingSphere-Proxy**（代理） |
| --- | --- | --- |
| 形态 | 以 jar 依赖内嵌应用，作为 JDBC 驱动 | 独立部署的透明数据库代理（独立进程） |
| 优点 | 性能最好（本地路由零网络跳）、代码侵入小 | 语言无关（任何客户端）、免改应用、集中治理 |
| 缺点 | 仅 Java、每应用一份配置 | 多一跳网络延迟、需运维代理集群 |
| 适用 | Java 微服务直连（首选） | 多语言团队、DBA 统一管理、已有系统无改造接入 |
| 治理 | 各应用自带 | 集中式 |

> **选型经验**：Java 技术栈首选 **JDBC 形态**（性能与灵活性兼得）；有跨语言/运维管控诉求选 **Proxy**；两者可混合（同集群 JDBC + Proxy 并存）。

## 57.7 实战：订单系统分库分表（ShardingSphere-JDBC + Spring Boot）

### 57.7.1 引入依赖

```xml
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc-core-spring-boot-starter</artifactId>
    <version>5.4.1</version>
</dependency>
```

### 57.7.2 配置：数据源 + 分片规则（以 user_id 哈希分 8 库 16 表）

```yaml
spring:
  shardingsphere:
    mode:
      type: Standalone            # 独立模式；集群环境用 Cluster + ZooKeeper/Nacos
    datasource:
      names: ds0, ds1             # 逻辑库 = ds0 + ds1（2 库）
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        driver-class-name: com.mysql.cj.jdbc.Driver
        url: jdbc:mysql://192.168.1.10:3306/order_db_0
        username: root
        password: root
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        url: jdbc:mysql://192.168.1.11:3306/order_db_1
        username: root
        password: root
    rules:
      sharding:
        tables:
          t_order:                                          # 逻辑表
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..7} # 2 库 × 8 表 = 16 片
            table-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: order-table-hash   # 表级哈希
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: order-db-hash      # 库级哈希
        sharding-algorithms:
          order-db-hash:
            type: HASH_MOD
            props:
              sharding-count: 2        # 库数量
          order-table-hash:
            type: HASH_MOD
            props:
              sharding-count: 8        # 每库表数量
    props:
      sql-show: true                  # 生产关闭；调试看真实路由 SQL
```

### 57.7.3 代码：零改动的 MyBatis

```java
// 插入：根据 user_id 自动路由到对应库表，业务代码无需感知分片
@Insert("INSERT INTO t_order(order_id, user_id, amount, status) "
        + "VALUES(#{orderId}, #{userId}, #{amount}, #{status})")
int insert(Order order);

// 点查：WHERE 带分片键 user_id → 单库单表路由
@Select("SELECT * FROM t_order WHERE user_id = #{userId} ORDER BY create_time DESC LIMIT 20")
List<Order> listByUserId(Long userId);

// 危险操作：WHERE 不带分片键 → 广播到全部 16 片再归并（管理端勿用）
@Select("SELECT * FROM t_order WHERE order_no = #{orderNo}")
Order getByOrderNo(String orderNo);
```

> **关键认知**：ShardingSphere 帮你做"路由 + 改写 + 归并"，但**路由粒度由 SQL 的 WHERE 决定**——带分片键是单片性能，不带分片键是广播性能。代码可以不变，查询习惯必须变。

## 57.8 分片后的数据访问难题：跨片查询/聚合/分页

| 难题 | 表现 | 解决方案 |
| --- | --- | --- |
| 跨片聚合 | `COUNT/SUM` 全片 | 提前聚合到汇总表/数仓；实时用 ES |
| 跨片排序分页 | 第 N 页要全片取 N×片数 | C 端按分片键查（天然单片）；全局翻页走 ES/数仓 |
| 跨片关联 JOIN | 不允许 | 冗余字段 / 宽表 / 应用层聚合（ID in 多次查） |
| 唯一约束 | 单库唯一索引失效 | 唯一性靠分片键内保证 + 分布式 ID（见 57.9） |
| 分布式事务 | 跨片写 | 见 57.10（连接 46 章方案） |

```
分页真相：SELECT ... LIMIT 10,10 路由到 16 片 = 每片取 20 条再归并取 10
          → 翻页越深成本越高（LIMIT 10000,10 = 每片取 10010 条）
          → C 端用"游标分页"（where id > ? limit n），天然适配分片
```

## 57.9 分布式 ID：全局唯一的四套方案

分库分表后单库自增 ID 会冲突，需要全局唯一 ID：

| 方案 | 组成 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **雪花算法（Snowflake）** | 时间戳(41) + 机器ID(10) + 序列(12) | 趋势递增、无中心、高性能 | 依赖机器时钟（时钟回拨需处理） |
| **号段模式** | 数据库发号（一次取一段，如 1000 个） | 简单可靠 | 有中心依赖、号段耗尽需等 |
| **UUID** | 随机 128 位 | 最简单、无中心 | 无序（索引碎片）、太长 |
| **Redis INCR/组合** | 自增 + 前缀 | 简单、可有序 | 依赖 Redis、需保证高可用 |

**生产推荐**：雪花算法（如美团的 Leaf、百度的 UidGenerator）或号段模式。**雪花 + 分片位内嵌**是最优组合——主键自带分片信息，点查无需分片键即可路由（见 57.3）。

```java
// 雪花算法核心结构（示意）
// 41bit 时间戳(ms) | 10bit 机器ID | 12bit 序列号 → 19 位 Long
// 64 位容量 ≈ 69 年不重复；单机每毫秒 4096 个
long id = ((timestamp - epoch) << 22) | (workerId << 12) | sequence;
```

> **面试题**：雪花算法时钟回拨怎么办？答：短回拨（< 5ms）自旋等待；中等回拨用备用机器 ID 或拒绝发号；长回拨记录日志并告警，必要时切换发号中心。

## 57.10 分库分表后的分布式事务与数据一致性

分片后"跨片写"不再是单库事务，必须选一致性方案（与 46 章方案衔接）：

| 场景 | 推荐方案 | 说明 |
| --- | --- | --- |
| 跨片强一致（金额类） | Seata AT/TCC（46 章） | 分片内的本地事务不变，跨片走 Seata |
| 最终一致（订单→库存） | 本地消息表 / MQ 事务消息 | 异步解耦，幂等消费 |
| 长时间流程 | Saga 编排 | 状态机驱动补偿 |
| 尽量规避 | —— | **设计上让一个用户的操作落在同一片**，90% 事务回到单库 |

> **架构铁律**：分片键选得好，分布式事务数量骤减——这是"user_id 分片"的隐藏价值：用户下单、查单、支付确认全部单片，只有跨用户场景（如后台对账）才涉及多片。

## 57.11 数据迁移与扩容：分库分表的"终身课题"

- **初次分片**：存量数据按分片键搬迁（59 章大规模迁移详细讲：全量 + 增量 + 双写切换）。
- **扩容**（8 库 → 16 库）：
  - 翻倍扩容法：`new_shard = old_shard + 8`，一半数据无需搬迁；
  - 一致性哈希：只迁移环上邻接节点；
  - 双写过渡：新旧拓扑并行，对账后切换。
- **必须提前规划**：分片策略在 57.4 就决定了扩容成本，不要在扩容时才后悔。

## 57.12 生产踩坑清单与面试速查

**踩坑清单（每条都是线上教训）**：

| 坑 | 后果 | 对策 |
| --- | --- | --- |
| WHERE 忘记分片键 | 广播全片、慢查询拖垮库 | 代码评审强制；监控"无分片键 SQL" |
| 分片键变更 | 数据无法路由 | 分片键一旦上线**永不修改**（迁移成本巨大） |
| 跨片 JOIN/子查询 | 性能灾难 | 禁 JOIN，冗余/ES/应用聚合 |
| 翻页过深 | 归并内存暴涨 | 游标分页 |
| 分布式 ID 依赖时钟 | 时钟回拨重复 ID | 雪花算法加回拨保护 |
| 唯一索引依赖单库 | 跨片重复数据 | 分片键内唯一 + 全局 ID |
| 扩容不演练 | 切换失败丢数据 | 59 章迁移方法论 + 演练 |

**面试速查**：

| 问题 | 一句话答案 |
| --- | --- |
| 什么时候分库分表？ | 索引→缓存→读写分离之后，容量/写并发到物理上限 |
| 分片键怎么选？ | 查询最频繁且分布均匀的字段，同用户数据同片 |
| 分库分表的最大代价？ | 跨片查询/事务/扩容三大难题，复杂度线性上升 |
| ShardingSphere-JDBC vs Proxy？ | Java 直连选 JDBC，跨语言/集中治理选 Proxy |
| 分片后主键怎么生成？ | 雪花算法/号段，推荐分片位内嵌 |
| 跨片分页怎么做？ | C 端游标分页，管理端走 ES/数仓 |

### 本章小结

- **决策**（57.1）：缓存 → 读写分离 → 分库分表，分库分表是最后一招；
- **拆法**（57.2）：垂直分业务域、水平分数据行，四象限组合；
- **分片键**（57.3）：查询模式决定分片键，同业务实体同片，一经确定不修改；
- **策略**（57.4）：哈希最均匀、范围可扩展、一致性哈希扩容友好，扩容成本是选型核心；
- **落地**（57.5~57.7）：ShardingSphere-JDBC 零代码侵入接入，WHERE 决定路由粒度；
- **代价**（57.8~57.10）：跨片查询走 ES/数仓、分布式 ID 全局唯一、跨片事务用 46 章方案并尽量规避；
- **运维**（57.11~57.12）：扩容是终身课题，踩坑清单就是生产守则。
