# 第五十九章 大规模数据迁移与不停机扩容（搬数据不停机的完整方法论）

> 本章目标：第三十八章讲了 Schema 迁移（Flyway/Liquibase），本章讲**数据搬移**——把 TB 级存量数据从 A 库搬到 B 库、从单库迁到分库分表、从 8 片扩到 16 片，全程业务不停机。掌握迁移全流程（评估/演练/双写/切换/回滚/对账）、全量+增量同步（DataX/Canal）、双写与灰度切换方案、影子表验证、扩容 rehash 的数学原理，并建立"迁移是可回滚的工程"的思维。
>
> 前置知识：第三十八章 数据迁移（三类迁移边界）、第三十三章 MySQL（binlog/主从）、第五十七章 分库分表、第四十六章 分布式事务（幂等/双写）。

## 59.1 与 38 章的边界：三种"迁移"别混为一谈

| 类型 | 38 章（Schema 迁移） | 本章（数据搬移） |
| --- | --- | --- |
| 对象 | 表结构 DDL | 存量数据 DML |
| 工具 | Flyway/Liquibase | DataX / Canal / 双写代码 |
| 量级 | 字段级、秒级 | TB 级、小时~天级 |
| 核心诉求 | 版本化、可重复执行 | 不停机、不丢数据、可回滚 |

> **一句话记忆**：38 章管"库长什么样"，本章管"数据怎么搬"。分库分表（57 章）触发的大规模搬移，正是本章主战场。

## 59.2 迁移全流程：七步方法论（先设计再动手）

```
① 评估 → ② 目标架构 → ③ 工具选型 → ④ 全量同步 → ⑤ 增量追平 → ⑥ 灰度切换 → ⑦ 对账收尾
   │          │              │              │             │             │            │
 数据量/停机    新表结构/分片    是否双写/全增      老→新搬历史    新老数据拉平    分批切流量     数据校验、切走老库
 窗口/风险     规则/索引       同步引擎选择       数据                                  + 回滚预案
```

| 步骤 | 关键产物 | 常见坑 |
| --- | --- | --- |
| 评估 | 数据量、增长速率、停机窗口、表清单 | 低估数据量（注意大字段/历史表） |
| 目标架构 | 目标表结构、分片规则（57 章）、索引 | 目标结构未对齐业务新需求 |
| 工具选型 | 全量引擎 + 增量引擎（下表） | 增量能力不足导致追不平 |
| 全量同步 | 批量搬移任务、断点续传 | 源库大事务拖垮线上 |
| 增量追平 | 延迟监控到秒级以下 | binlog 保留期不够 |
| 灰度切换 | 灰度批次、回滚开关 | 切换失败无预案直接事故 |
| 对账收尾 | 数据校验报告、老库下线计划 | 对账不充分遗留脏数据 |

## 59.3 同步引擎选型：DataX（全量）+ Canal（增量）黄金组合

| 引擎 | 定位 | 原理 | 适用 |
| --- | --- | --- | --- |
| **DataX** | 全量批量 | 分片并行读源库 → 写入目标 | 历史数据一次性搬运（TB 级） |
| **Canal** | 增量实时 | 伪装从库订阅 binlog → 同步到目标 | 全量之后的增量追平、实时同步 |
| 双写代码 | 业务双写 | 应用同时写新旧库 | 需要业务改造/转换的迁移 |
| Flink CDC | 增量 + 加工 | binlog → Flink 流处理 | 需要加工转换的同步 |

```
迁移组合拳：
① 先 DataX 全量搬历史（低峰执行、分片并行、限速保护源库）
② 期间 Canal 订阅 binlog，从"DataX 启动时间点"开始累积增量
③ 全量完成 → 回放 Canal 增量 → 新老数据追平到秒级
④ 追平后进入双写/灰度切换阶段
```

**Canal 关键配置（示意）**：

```yaml
# canal.properties
canal.instance.master.address = 192.168.1.10:3306   # 伪装成从库
canal.instance.dbUsername = canal
canal.instance.dbPassword = canal
canal.instance.filter.regex = mall\\.t_order      # 只同步目标表
```

> **前提条件**：源库 binlog 格式必须为 `ROW`（`binlog_format=ROW`），且保留期覆盖迁移时长（如 `expire_logs_days=7`）。**binlog 保留期不够 = 增量追不平 = 迁移失败**。

## 59.4 双写方案：不停机的核心手段

全量+增量追平后，用"双写 + 灰度切换"把流量切过去：

```
阶段一：双写（写新又写老，读老）
   应用写 → 旧库 + 新库（事务内或异步，失败不影响主链路）
   读仍走旧库 → 观察新库数据正确性

阶段二：灰度读（读新验证）
   小比例流量（如 1%→5%→20%）切到新库读，对比新旧读结果

阶段三：切换写（切写，停双写）
   应用只写新库，旧库停止写入（保留只读）

阶段四：收尾
   对账 → 观察期（1~2 周）→ 旧库下线/归档
```

**双写实现的两条路线**：

| 路线 | 实现 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 应用内双写 | 事务内先写新库再写旧库（或 MQ 异步双写） | 可控、可做数据转换 | 侵入业务、双写失败需补偿 |
| 中间件双写 | Canal 订阅 binlog 回放到新库（等同做增量同步） | 零侵入 | 依赖 Canal 稳定 |

> **双写补偿**：双写期间新库写入失败 → 记录补偿任务，定时从旧库补拉。**双写阶段的对账任务必须先行建好**（见 59.7），否则无法判断何时可以切写。

## 59.5 影子表：低风险验证新架构

影子表（Shadow Table）是把流量复制一份到新架构做验证，**不真实影响用户**：

| 类型 | 做法 | 用途 |
| --- | --- | --- |
| 数据影子表 | 新表 + 影子表，双写只写影子表 | 验证新表结构/分片规则 |
| 流量影子（影子库） | 按规则复制线上流量到影子环境 | 全链路压测新架构（结合 32 章压测） |
| 查询影子 | 新老库同查对比返回 | 验证 SQL 改写/分片路由正确性 |

```
ShardingSphere 影子库配置（示意）：
  enable shadow: true
  data-sources:  shadow-ds   # 影子数据源
  影子判定：请求头带 shadow=true 的流量 → 路由到影子库
  → 压测流量与线上真实流量隔离，互不污染
```

> **影子表的价值**：分库分表改造（57 章）最怕"路由错了都不知道"，影子表让你在真实流量下验证路由/改写/归并的正确性，而用户无感知。

## 59.6 扩容 rehash：从 8 片到 16 片的数学与实操

分库分表后扩容是最难的迁移（与 57.4 选型衔接）：

### 59.6.1 三种扩容路线的迁移量对比（N 旧片 → 2N 新片）

```
取模扩容（朴素）：mod 8 → mod 16，几乎所有数据都要搬迁       迁移量 ≈ 100%
翻倍扩容法：      新片 = 旧片 + 8（数据整体搬到另一半），
                   旧片 0~7 的数据一半留下、一半搬到 8~15    迁移量 ≈ 50%
一致性哈希扩容：   只迁移环上相邻节点                        迁移量 ≈ 1/2N
```

**翻倍扩容法原理**：

```
原分片：shard = user_id % 8          → 扩容后：shard = user_id % 16
关键性质：user_id % 16 = (user_id % 8) 或 (user_id % 8 + 8)
验证：  user_id=10 → 10%8=2（旧片2），10%16=10（新片10=2+8）✅ 搬到 2+8
        user_id=15 → 15%8=7（旧片7），15%16=15（新片15=7+8）✅ 搬到 7+8
结论：每片数据"一半留原片、一半平移 +8"，搬一半即可，可用 59.3 的组合拳搬
```

### 59.6.2 扩容实操步骤（结合 59.2 七步法）

```
① 评估：现有分片、数据分布、新拓扑（8→16 库表）
② 建新片：新建 8~15 片（含主从）
③ 全量+增量：DataX 搬"需要平移的数据"到新片，Canal 追平
④ 双写：写路径按 16 片规则双写（新分片规则兼容旧：见上文性质）
   注意：双写期间"留原片的数据"两个规则都写原片 → 无重复
⑤ 灰度切换读 → 切写 → 对账 → 观察期 → 旧片下线
```

> **扩容铁律**：分片规则一旦从 8 变 16，**应用必须同时支持新旧两套路由**（双写阶段），否则切换瞬间路由不一致直接丢数据。这就是为什么 57.4 就强调"提前想清楚扩容成本"。

## 59.7 对账与校验：迁移可信的最后证明

迁移"做完"不算完，**对账通过才算完**：

| 层级 | 对账方式 | 粒度 |
| --- | --- | --- |
| 行数 | `COUNT(*)` 逐片对比 | 粗粒度 |
| 抽样 | 按主键抽样逐字段比对 | 中粒度 |
| 全量 checksum | 分块 MD5/校验和比对（参考 58.8 pt-table-checksum） | 细粒度 |
| 业务对账 | 关键指标：订单总数/金额总和/用户数 | 业务可信度 |

```
对账任务设计（可定时重复跑）：
表维度：新库总行数 = Σ旧库各片行数
字段维度：金额字段 SUM、状态分布 COUNT GROUP BY 一致
关键字段：主键无重复、无 NULL 非空字段
```

> **对账的三个时机**：全量后（验证搬移完整性）、双写期间（验证增量正确性）、切写后（验证正式链路）。**任何一步对账不通过，都先回滚查因，不要强行推进**。

## 59.8 回滚预案：迁移必须"可回退"

| 阶段 | 回滚方式 | 触发条件 |
| --- | --- | --- |
| 全量/增量中 | 停止任务，数据未切流量，业务无感 | 引擎故障、源库压力异常 |
| 双写中 | 停双写（应用回退单写旧库） | 新库持续对账失败 |
| 灰度读中 | 回退读路由到旧库 | 灰度用户反馈异常 |
| 切写后（观察期） | 反向双写（新→旧）再切回 | 观察期发现严重问题 |
| 旧库下线后 | 无法回滚（只能用备份恢复） | —— |

> **回滚红线**：旧库**至少保留到观察期结束**（推荐 2~4 周），期间旧库只读+每日备份。**提前删旧库是迁移事故的头号原因**。

## 59.9 实战案例与踩坑清单

**案例：订单表从单库迁移到 8 库 16 表（全程不停机）**

```
① 评估：2 亿行、80GB、目标 8 库 16 表（user_id 哈希，57 章）
② 建新库新表：8 个分片库 × 16 张分片表 + 各自从库
③ 全量：DataX 按 user_id 分片并行搬历史（限速 30MB/s，避开高峰）
④ 增量：Canal 订阅 binlog 追平，延迟监控 < 5s
⑤ 影子验证：影子库跑压测流量，验证路由正确性
⑥ 双写：应用按 16 片规则双写；对账任务每小时跑一次
⑦ 灰度：读流量 1%→5%→20%→50%→100% 切新库
⑧ 切写：停双写、旧库只读；观察 2 周后旧库归档下线
```

**踩坑清单**：

| 坑 | 后果 | 对策 |
| --- | --- | --- |
| binlog 保留期太短 | 增量追不平，重新全量 | 迁移前评估保留期，至少覆盖全程 |
| 源库大事务 | 主从延迟飙高、DataX 拖垮线上 | 限速 + 低峰执行 + 监控源库 |
| 双写无补偿 | 新库漏写无感知 | 双写失败入补偿队列 |
| 对账口径不一致 | 误判迁移失败 | 对账 SQL 先评审，口径统一 |
| 切写瞬间路由不一致 | 数据写入错误分片 | 双写阶段新旧规则并存验证 |
| 提前删旧库 | 无法回滚 | 旧库保留至观察期结束 |

### 本章小结

- **边界**（59.1）：本章管"数据搬移"，与 38 章 Schema 迁移互补；
- **七步法**（59.2）：评估 → 目标 → 选型 → 全量 → 增量 → 灰度切换 → 对账，先设计再动手；
- **引擎**（59.3）：DataX 全量 + Canal 增量黄金组合，binlog=ROW 是前提；
- **双写**（59.4~59.5）：双写 + 灰度读 + 切写三步走，影子表低风险验证；
- **扩容**（59.6）：翻倍扩容法只搬一半数据，新旧路由并存是安全底线；
- **收尾**（59.7~59.8）：对账通过才算完成，回滚预案贯穿全程，旧库保留到观察期结束。
