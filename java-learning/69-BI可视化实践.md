# 第六十九章 BI 可视化实践（从指标到决策的最后一公里）

> 本章目标：第六十一~六十八章把数据"采、存、算、湖、预测"全打通，本章完成最后一公里——把数据变成人看得懂、用得上的决策信息。以 Java 后端视角掌握：BI 工具选型（成品 vs 自研）、指标体系设计（北极星/OSM/分层）、指标平台（口径统一的核心矛盾）、报表与大屏设计、自助分析（即席查询），并用一套"Java 后端 BI 架构"（元数据 → 查询 → 缓存 → API → 可视化）把 64/66 章的分析引擎接成可用的 BI 产品，收官大数据专题（61~69）。
>
> 前置知识：第六十五/六十六章（平台与 Hive）、第六十四章（ClickHouse/Doris）、第六十二/六十三章（数仓分层）、第九/十六章（Spring Boot/消息）。

## 69.1 BI 全景：数据平台"应用层"的收口

65 章六层架构的最后一层是"应用层"，BI 就是应用层的主角：

```
┌────────────────────────────────────────────┐
│ 应用层（69 章）：BI 报表 / 大屏 / 自助分析 / 决策  │
│   ↑ 指标平台（口径统一）                      │
├────────────────────────────────────────────┤
│ 分析层（64 章）：ClickHouse / Doris / ES      │
│ 计算层（63/66）：Spark / Hive / Flink        │
│ 存储层（67 章）：Hive / Iceberg / Kafka      │
│ 采集层：binlog / 日志                        │
└────────────────────────────────────────────┘
```

**BI 的本质**：把数仓算好的 DWS/ADS（62 章）用"指标 + 维度 + 图表"呈现，让业务能自助看数、追数、做决策。

> **Java 后端视角**：BI 不是"画图工具"那么简单，核心工程是三件事——**指标怎么定义（口径）**、**查询怎么又快又稳（引擎）**、**权限怎么控制（安全）**。

## 69.2 BI 工具选型：成品 or 自研

| 方案 | 代表 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- | --- |
| 商业成品 BI | Tableau / Power BI / 帆软 | 开箱即用、图表丰富、服务好 | 贵、定制受限、数据安全在第三方 | 预算足、标准报表需求 |
| 开源 BI | **Superset / Metabase** | 免费、可定制、支持即席 SQL | 自助分析能力一般、要自己运维 | 中小团队、自建平台 |
| **半自研** | 开源 BI + 自研指标平台/API | 口径统一 + 灵活定制 | 工程量中等 | **中大型团队主流** |
| 全自研 | 自研图表 + 查询层 | 完全掌控、深度集成业务 | 工程量大、图表交互难做 | 业务特殊的头部公司 |

> **生产主流判断**：中小团队先用 **Superset/Metabase** 快速出数；数据口径打架、业务定制多时，演进到"**自研指标平台 + 开源 BI/自研前端图表**"的半自研架构——这也是本章 69.6 实战的形态。

## 69.3 指标体系：北极星、OSM 与分层

BI 的根基不是图表，是**指标**。没有指标体系，BI 就是"各说各话的数字展览"。

### 三层指标体系

| 层级 | 是什么 | 例子 |
| --- | --- | --- |
| **北极星指标** | 全局唯一最关键指标 | 电商：核心 GMV / 有效成交用户数 |
| **核心指标体系** | 北极星的拆解（OSM 模型） | 新客数、复购率、客单价、转化率 |
| **支撑指标** | 下钻诊断用 | 各渠道转化、各品类 GMV、退货率 |

### OSM 模型（目标-策略-度量）

| 目标（Objective） | 策略（Strategy） | 度量（Measure） |
| --- | --- | --- |
| 提升 GMV | 拉新促活 | 新客数、新客首单率 |
| 提升 GMV | 提升复购 | 复购率、复购周期 |
| 提升 GMV | 提升客单价 | 客单价、连带率（件单价） |

```
北极星：GMV = 用户数 × 转化率 × 客单价
   ├─ 用户数 ← 新客/留存/流失召回
   ├─ 转化率 ← 浏览→加购→下单→支付 各环节漏斗（62 章 DWS 漏斗宽表）
   └─ 客单价 ← 连带率/客单提升（推荐 68 章模型提连带）
```

> **口径铁律**：同一个指标全公司只能有一个定义。GMV 是"支付口径"还是"下单口径"？退款算不算？——**口径不统一，BI 就是吵架工具**。解法见 69.4 指标平台。

## 69.4 指标平台：统一口径的核心矛盾

> 数仓团队和业务最痛的问题：**同一指标，报表 A 说 100 万，报表 B 说 95 万，老板问谁对**。指标平台就是解决"口径原子化"的工程方案。

```
传统做法：业务需求 → 数仓写 SQL → 每张报表各算各的 → 口径随人走、随 SQL 走
指标平台做法：
  ① 指标注册：GMV（支付口径）在指标平台定义一次（口径 = 一段标准 SQL/语义层）
  ② 数仓建模：DWS 宽表按指标平台定义产出（62 章）
  ③ 所有报表/自助分析：只能从指标平台"取指标"，不能自己另算
  ④ 指标字典：业务可查"GMV 定义是什么、口径文档、负责人"
```

| 指标平台能力 | 说明 |
| --- | --- |
| 指标注册与元数据 | 名称、口径 SQL、维度、负责人、数据源（65 章元数据/血缘联动） |
| 口径即服务 | 指标通过语义层生成查询，杜绝手写 SQL 漂移 |
| 权限与脱敏 | 指标级权限：财务指标仅财务可见（54 章零信任思路） |
| 质量与告警 | 指标波动超阈值自动告警（48 章可观测性延伸） |

> **一句话**：**指标平台 = 把"口径"从 SQL 里抽出来，变成可注册、可复用、可审计的对象**。它是 BI 从"画图工具"升级为"决策基础设施"的关键一步。

## 69.5 报表、大屏与自助分析

### 报表（固定看板）

- **场景**：日报/周报、经营例会、对账；
- **设计**：顶部 KPI 卡（北极星 + 核心指标）→ 中部趋势图 → 下部明细/排名 → 支持下钻；
- **实现**：预计算 ADS（62 章）+ 定时刷新 + 缓存（29 章）。

### 大屏（指挥中心/对外展示）

- **场景**：实时监控、双 11 战报、数据驾驶舱；
- **设计**：深色科技风、实时数据滚动、地图/排行/仪表盘组合、**核心数字大字号**；
- **实现**：实时指标走 Flink → Kafka → 推送（62 章），图表库 ECharts/DataV；
- **大屏三大坑**：刷新抖动（数据间断）、口径不一致（和日报对不上）、只求炫技不看决策。

### 自助分析（即席查询）

- **场景**：业务自己拉数，不再排队等数仓；
- **技术**：语义层屏蔽底层（用户选指标+维度 → 生成查询跑 ClickHouse/Doris）→ 64 章分析引擎 + 65 章 Ad-hoc（Presto/Trino）；
- **关键约束**：查询超时熔断 + 资源隔离（防止一个慢查询拖垮分析集群）。

## 69.6 实战：Java 后端 BI 架构（元数据 → 查询 → 缓存 → API → 可视化）

一套"指标平台 + 报表 API"的半自研架构（衔接 64 章 ClickHouse/Doris）：

```
┌─ 前端：ECharts 图表 / 大屏（Vue/React）──────────────┐
│   ▲ 报表数据 API（JSON）                            │
├─ Java BI 服务（Spring Boot）────────────────────────┤
│ ① 指标元数据服务：指标定义（口径/维度/权限）注册与查询    │
│ ② 查询服务：指标+维度 → 生成 SQL → 查 ClickHouse/Doris │
│ ③ 缓存服务：热点指标 Redis 缓存 + 预计算（29 章）      │
│ ④ 权限服务：指标级权限 + 行级过滤（租户/部门）         │
├─ 数据源：DWS/ADS（62 章）+ ClickHouse/Doris（64 章）─┤
└───────────────────────────────────────────────────┘
```

### 核心代码：指标查询服务

```java
@Service
public class MetricQueryService {

    private final MetricMetaRepository metricMetaRepo; // ① 指标元数据
    private final JdbcTemplate clickhouse;             // ④ 分析引擎（64 章）
    private final StringRedisTemplate redis;           // ③ 缓存（29 章）

    /**
     * 查询指标：metricCode + 维度 + 时间范围
     * 例如：gmv（支付口径）按 category 分组，近 7 天
     */
    public QueryResult query(String metricCode, String dim, LocalDate from, LocalDate to, Long deptId) {
        // ① 拿指标定义（口径 SQL 片段 + 权限要求）
        MetricMeta meta = metricMetaRepo.findByCode(metricCode);
        checkPermission(meta, deptId);                 // ④ 指标级权限

        // ② 缓存命中直接返回（热点指标 60 秒缓存）
        String cacheKey = "bi:" + metricCode + ":" + dim + ":" + from + ":" + to + ":" + deptId;
        String cached = redis.opsForValue().get(cacheKey);
        if (cached != null) return JsonUtils.parse(cached, QueryResult.class);

        // ③ 由指标定义生成查询：SELECT dim, SUM(amount) ... GROUP BY dim
        String sql = buildQuery(meta, dim, from, to);
        List<Map<String, Object>> rows = clickhouse.queryForList(sql);
        QueryResult result = new QueryResult(meta.getName(), rows);

        redis.opsForValue().set(cacheKey, JsonUtils.toJson(result), Duration.ofSeconds(60));
        return result;
    }
}
```

### 指标元数据表设计（口径原子化的载体）

```sql
CREATE TABLE bi_metric (
  id            BIGINT PRIMARY KEY,
  metric_code   VARCHAR(64) NOT NULL,     -- 指标编码，如 gmv_paid
  metric_name   VARCHAR(128),             -- 展示名：支付 GMV
  caliber_sql   VARCHAR(512),             -- 口径 SQL 片段：SUM(amount) WHERE status='PAID'
  source_table  VARCHAR(128),             -- 数据源：dws_gmv_daily
  dims          VARCHAR(256),             -- 可用维度：category_id, channel_id
  owner         VARCHAR(64),              -- 负责人（口径有问题找谁）
  UNIQUE KEY uk_code (metric_code)
);
```

> **这套架构的胜负手**：查询只允许走"指标元数据生成"的 SQL，业务永远拿不到裸 SQL 权限——**口径统一 + 权限可控 + 缓存加速**一次解决。慢查询熔断：加 `LIMIT` + ClickHouse 查询超时参数（64 章）。

## 69.7 数据讲故事：报表与指标的价值闭环

BI 的最终目标不是"能画图"，而是**推动决策**：

```
数 → 指标（69.3）→ 报表/大屏（69.5）→ 发现异常 → 下钻定位 → 策略 → 再验证
   每个环节都要能回答：这个数字为什么变？变化是好事还是坏事？
```

| 报表套路 | 怎么讲 |
| --- | --- |
| 看趋势 | 环比/同比（66 章窗口函数算）|
| 看结构 | 渠道/品类占比（饼图/堆叠） |
| 看漏斗 | 转化链路逐层流失（62 章漏斗宽表） |
| 看排名 | Top 用户/商品（下钻定位重点） |
| 做诊断 | 指标波动归因（拆分维度逐层下钻） |

> **大屏 ≠ 决策**：一个"数字好看但没人行动"的大屏是失败的 BI。衡量 BI 是否成功的唯一标准是——**业务是否因为数据做出了不同决策**。

### 本章小结

- **选型**（69.1~69.2）：成品/开源/半自研三级，中大型团队主流是"指标平台 + 自研查询"；
- **指标**（69.3~69.4）：北极星 + OSM 分层；指标平台解决"口径原子化"这一核心矛盾；
- **呈现**（69.5）：报表讲完整、大屏看实时、自助分析给自由，但口径必须一致；
- **落地**（69.6~69.7）：Java BI 架构（元数据→查询→缓存→权限→API），数据讲故事推动决策；
- **收官**（69.8）：61~69 大数据九连形成"引擎→数仓→离线→分析→平台→湖仓→预测→决策"完整闭环。
