## 9.1 Rust 测试三层体系

| 层级 | 位置 | 用途 |
| --- | --- | --- |
| 单元测试 | 与代码同文件 `#[cfg(test)] mod tests` | 测试私有函数/模块内部逻辑 |
| 集成测试 | `tests/` 目录独立 crate | 通过公开 API 验证对外行为 |
| 文档测试 | `doc comment` 中的代码块 | 示例即测试，文档永不腐烂 |

```rust
// 单元测试示例（与实现同文件）
fn classify(score: u32) -> &'static str {
    match score {
        90.. => "excellent",
        60.. => "pass",
        _ => "retry",
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn 及格线判断() {
        assert_eq!(classify(60), "pass");
        assert_eq!(classify(89), "pass");
        assert_eq!(classify(59), "retry");
        assert_eq!(classify(95), "excellent");
    }

    #[test]
    #[should_panic]                      // 期待 panic 的用例
    fn 越界访问会panic() {
        let v = vec![1, 2];
        let _ = v[9];
    }
}
```

```rust
// 集成测试示例 tests/cli_test.rs —— 把库当黑盒测
use word_freq::top_words;                // 测试外部 crate：用 lib.rs 暴露的 API

#[test]
fn 集成级别词频() {
    let out = top_words("a a b b b c", 2);
    assert_eq!(out.len(), 2);
    assert_eq!(out[0].0, "b");
}
```

```rust
/// 示例即测试：运行 cargo test 时文档中的代码会被编译执行
///
/// ```
/// let greeting = format!("Hello, {}!", "Rust");
/// assert_eq!(greeting, "Hello, Rust!");
/// ```
pub fn example() {}
```

运行与精细控制：

```bash
cargo test                 # 全部测试
cargo test 名称子串         # 只运行名字包含"名称子串"的测试
cargo test -- --ignored    # 运行 #[ignore] 的慢测试
cargo test --release       # 优化模式下测
```

## 9.2 属性测试：让随机输入找 Bug

单元测试只能覆盖你想到的样例。**属性测试**用随机生成的输入验证"对任意输入都应成立的性质"。

```rust
// Cargo.toml: proptest = "1"
use proptest::prelude::*;

/// 反转两次等于原串：对任意字符串都成立
proptest! {
    #[test]
    fn double_reverse_identity(s: String) {
        let once: String = s.chars().rev().collect();
        let twice: String = once.chars().rev().collect();
        prop_assert_eq!(twice, s);
    }
}
```

对排序函数验证"任意 Vec 排序后长度不变、有序、元素集合相同"这类不变量，能覆盖手写用例难以触及的边界。适合纯函数与领域规则，不适合重度 I/O。

## 9.3 测试的工程习惯

- **黄金比例**：核心逻辑（领域规则、解析、状态机）必须有单元/属性测试；I/O 薄层用集成测试；
- 编写"失败才显示断言消息"的辅助函数，如 `assert_eq!(left, right, "错误详情 {}", ctx)`；
- 测试中避免依赖真实网络/时间：抽象出 trait（`TimeProvider`、`HttpFetcher`），测试注入假实现（第八章 `TaskRepository` 精神）；
- 覆盖率工具 `cargo llvm-cov`；CI 里让 clippy + fmt 作为门禁的一部分，而不是只在本地跑。

## 9.4 代码质量门禁：fmt + clippy

```bash
cargo fmt --check            # 格式检查（不修改文件）
cargo clippy --all-targets --all-features -- -D warnings   # lint：把警告当错误
```

常见 clippy 建议：`&*` 冗余解引用、`map_or` 可替换为 `is_some_and`、未使用变量、可推导的 `let x = ...`。开发期会提示 `clippy::pedantic`（更严格），生产通常用默认 + 少量显式允许项。把命令放进 CI，让"格式化+无警告"成为提交门槛。

## 9.5 可观测性：tracing

- `tracing`：结构化日志 + span（跨 await 的上下文关联，异步下比传统日志更合适）；
- 日志级别：`error/warn/info/debug/trace`，`RUST_LOG` 运行时控制；
- `tracing-subscriber` 输出到控制台/JSON；生产可接 OpenTelemetry。

```rust
use tracing::{info, instrument};

#[instrument(skip(pool))]              // 自动记录入参，方法级 span
async fn find_account(pool: &sqlx::SqlitePool, id: i64) -> anyhow::Result<Option<Account>> {
    info!(account_id = id, "查询账户");
    // ...
}
```

Axum 侧加 `TraceLayer` 即可得到每个请求的 method/path/status/耗时。**RUST_LOG=debug** 开发、**RUST_LOG=info** 生产是起步配置。

## 9.6 打包：Docker 多阶段构建

追求"小镜像"，采用 **多阶段构建**：阶段一用官方 Rust 镜像编译（依赖缓存层），阶段二把静态产物放进精简运行镜像。

```dockerfile
# 阶段一：编译
FROM rust:1.84-slim AS builder
WORKDIR /app
COPY Cargo.toml Cargo.lock ./
# 先拷贝源码并构建依赖层缓存（仅当依赖变化时才重编）
COPY src ./src
RUN cargo build --release

# 阶段二：运行
FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y ca-certificates && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY --from=builder /app/target/release/todo-api /usr/local/bin/todo-api
EXPOSE 8080
CMD ["todo-api"]
```

> SQLx 若使用 `query!` 编译期校验，Docker 构建需提供 `DATABASE_URL`（`build args` 传入）或 `--offline`。SQLite 用户建议把数据库文件放 volume 并映射。

## 9.7 CI：GitHub Actions 质量门禁

```yaml
name: ci
on: [push, pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          components: clippy, rustfmt
      - uses: Swatinem/rust-cache@v2
      - run: cargo fmt --check
      - run: cargo clippy --all-targets --all-features -- -D warnings
      - run: cargo test --all-features
```

## 9.8 发布与版本

- `cargo build --release` 生成 `target/release/<bin>`（优化 + LTO）；
- 交叉编译到 `x86_64-unknown-linux-musl`（静态链接）便于进镜像：`rustup target add x86_64-unknown-linux-musl`；
- `Cargo.toml` 里维护好 `version`、`description`、`license`、`repository`；
- 服务发布注意：`RUST_LOG`、端口、`DATABASE_URL` 全部走环境变量；日志与健康检查端点（`/healthz`）就绪。

## 9.9 收官实战：可发布的待办 REST 服务

**需求**：把第三章的领域模型 + 第八章的 Web 骨架 + 本章测试/质量/Docker 结合，交付带 CI 的完整待办服务：支持创建/查询/勾选完成/推进状态；数据库 SQLite 持久化；`/healthz` 健康检查；单测+集成测试全覆盖。

建议直接融合前面各章产出，最小文件清单：

```text
todo-api/
├── Cargo.toml              # axum + sqlx + serde + tower-http + tracing + thiserror
├── migrations/0001_init.sql
├── src/
│   ├── main.rs             # 组装 + 启动 + /healthz
│   ├── state.rs            # AppState
│   ├── models.rs           # Task + Status（第三章领域模型 + FromRow/Serialize）
│   ├── repository.rs       # SQLx 数据访问（save/find/pending/advance）
│   ├── error.rs            # ApiError（thiserror + IntoResponse）
│   └── handlers.rs         # 路由处理
├── tests/api.rs            # HTTP 级集成测试
├── .github/workflows/ci.yml
└── Dockerfile
```

**关键设计提示**：

1. **领域与数据层分离**：`models.rs` 定义纯领域逻辑（`Status::advance`、`Task::new`），`repository.rs` 只做持久化映射——测试领域逻辑不需要数据库；
2. **状态推进走服务层**：处理函数先读任务 → 调用领域方法 `advance()` → 写回。**规则不在 SQL 里**；
3. **`thiserror` 定义 `ApiError`**（BadRequest/NotFound/Conflict），`From<sqlx::Error>` 映射 DB 错误；
4. 集成测试直接 `oneshot` 打内存数据库（见 8.8）或用 `tempfile` SQLite 文件。

**验收清单（交付即收官）**：

1. `cargo fmt --check`、`cargo clippy -- -D warnings`、`cargo test` 全绿；
2. 支持接口：`POST /tasks`、`GET /tasks?done=false`、`GET /tasks/{id}`、`POST /tasks/{id}/advance`；
3. 对已完成任务 advance 返回 409 + 统一 JSON 错误（领域规则生效）；
4. `/healthz` 返回 200 并带简单 JSON；
5. `docker build -t todo-api .` 成功且镜像精简；
6. CI 配置就绪（可 push 到 GitHub 验证）。

**扩展方向**：为任务加截止时间与过滤；`/tasks/{id}` PATCH 改标题；权限（按用户隔离）；`axum::middleware` 记录耗时；`cargo dist`/`cargo-binstall` 生成安装包。
