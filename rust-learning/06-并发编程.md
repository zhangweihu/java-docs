## 6.1 Rust 并发哲学：Fearless Concurrency

多线程程序的两大难点是**数据竞争**和**死锁**。Rust 的策略：

- 数据竞争在**编译期**被借用检查与 `Send`/`Sync` 拒绝——能编译的多线程代码天然没有数据竞争；
- 运行期剩下的主要是死锁/饥饿，靠设计（锁粒度、顺序）规避。

核心接口是 `std::thread`：

```rust
use std::thread;
use std::time::Duration;

let handle = thread::spawn(|| {
    thread::sleep(Duration::from_millis(200));
    println!("子线程执行");
});
handle.join().unwrap();           // 等待子线程结束
println!("主线程继续");
```

`thread::spawn` 要求闭包是 `'static`（不能借用栈上的局部值），且 `move` 捕获要传入的所有权数据。

## 6.2 通道 mpsc：消息传递优先

**多用消息传递、少用共享内存**是 Rust 官方指引。`mpsc`（multi-producer, single-consumer）支持多发送端单接收端：

```rust
use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::channel();

// 多发送端：克隆 tx
let tx2 = tx.clone();
thread::spawn(move || {
    tx.send(String::from("来自线程A")).unwrap();
});
thread::spawn(move || {
    tx2.send(String::from("来自线程B")).unwrap();
});
drop(tx);                          // 原始发送端也关闭

// 接收端按发送顺序接收（阻塞）；发送端全关后迭代结束
for msg in rx {
    println!("收到: {msg}");
}
```

接收端迭代 `for msg in rx` 在**所有发送端关闭后自动结束**——这是优雅停机的关键。发送端返回值类型与错误处理用 `send` 的 `Result` 判断对端是否已断开。

## 6.3 共享状态：Arc<Mutex<T>>

确实需要共享可变数据时，用 **`Arc`（原子引用计数，线程安全版 Rc）+ `Mutex`（互斥锁）**：

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));

let mut handles = vec![];
for _ in 0..8 {
    let counter = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        let mut guard = counter.lock().unwrap();   // 加锁，返回 MutexGuard
        *guard += 1;                                // 解引用修改
    }));                                            // guard drop → 自动解锁
}

for h in handles {
    h.join().unwrap();
}
println!("counter = {}", *counter.lock().unwrap());  // 8
```

要点：

- **`MutexGuard` 解引用即访问内部数据**，作用域结束自动解锁（Drop），无需手动 unlock；
- `lock()` 返回 `Result`：对端线程 panic 时返回 `PoisonError`，需处理或 `unwrap`；
- **锁内不做耗时操作**，尽量缩小临界区，避免死锁与性能问题；
- 锁只能保护通过它访问的数据，**多个锁的获取顺序必须全局一致**（否则死锁）。

读多写少场景改用 `RwLock<T>`（读写锁，读可并发，写独占）。写多读少仍用 `Mutex`。原子类型（`AtomicUsize` 等）适合简单计数，无锁开销：

```rust
use std::sync::atomic::{AtomicUsize, Ordering};

let hits = Arc::new(AtomicUsize::new(0));
// 子线程内:
hits.fetch_add(1, Ordering::Relaxed);
```

## 6.4 Send 与 Sync：线程安全的类型契约

Rust 用两个标记 trait 在编译期表达"什么能跨线程"：

- **`Send`**：类型的所有权可转移到另一线程。`Vec`/`String`/`Box` 等拥有数据的是 `Send`；`Rc<T>`（引用计数非原子）不是 `Send`；
- **`Sync`**：类型可被多个线程共享引用（`&T` 是 `Send`）。`Arc<T>` 要求 `T: Send + Sync`；`Rc<T>` 与 `RefCell<T>` 不是 `Sync`（运行期借用计数/借用非线程安全）。

编译器据此阻止不安全的跨线程操作，你基本不需要手动实现它们——多数类型自动满足。只需记住：**跨线程共享数据用 `Arc`，`Mutex` 内数据要能跨线程（自动满足 `Send`）**。

`Mutex<T>` 是 `Sync`（若 `T: Send`）——即使 `T` 不是 `Sync`，用锁包起来也能安全共享，如 `Arc<Mutex<RefCell<...>>>`（虽很少这么写）。

## 6.5 scoped 线程：借用栈上数据

`thread::scope` 允许新线程借用当前栈上的变量（不用 `move` 转移所有权），并保证所有线程在作用域结束前汇合：

```rust
use std::thread;

let mut nums = vec![1, 2, 3, 4, 5, 6, 7, 8];

thread::scope(|scope| {
    // 分成两半并行处理，直接借用 nums（无需 Arc）
    for chunk in nums.chunks_mut(2) {
        scope.spawn(move || {
            for n in chunk.iter_mut() {
                *n *= 10;
            }
        });
    }
}); // scope 结束：所有子线程已 join，之后可安全使用 nums
println!("{nums:?}");
```

适用场景：并行处理一个大数组/分片数据，数据生命周期可控，免去 `Arc` 与跨线程拷贝的开销。

## 6.6 任务并行选型

| 方式 | 适用 | 缺点 |
| --- | --- | --- |
| 直接 `thread::spawn` | 少量、长生命周期任务 | 无复用，`'static` 限制 |
| `thread::scope` | 借用栈上分片并行 | 不能跨作用域 |
| `mpsc` | 生产者-消费者、任务分发/结果回收 | 单消费者需自行 fan-in |
| `Arc<Mutex>` | 共享计数/配置、少量共享状态 | 锁竞争 |
| 线程池 crate（`rayon`） | 数据并行 map/reduce、通用并行计算 | 引入依赖 |
| `crossbeam` | 更灵活的通道/作用域线程（scoped + 并发队列） | 引入依赖 |
| 异步运行时（下章） | I/O 密集高并发 | 不适合 CPU 密集长任务 |

**CPU 密集数据并行**首推 rayon，一行把迭代器变并行：

```rust
// Cargo.toml: rayon = "1"
use rayon::prelude::*;

let sum: u64 = (0..1_000_000u64).into_par_iter().map(|n| n * n).sum();
println!("{sum}");
```

**I/O 密集高并发**用 Tokio 异步（第七章）。判断标准：瓶颈在 CPU（多核并行→rayon/线程）还是 I/O（等待网络/磁盘→异步）。

## 6.7 实战：并发任务调度器

**需求**：模拟并发执行 N 个任务（如"下载/计算"），维护一个共享进度计数，完成后收集每个任务的结果与耗时。主线程等待全部完成并汇总。

```rust
use std::sync::mpsc;
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::{Duration, Instant};

const TASKS: usize = 6;

/// 模拟一个耗时任务：返回 (任务序号, 处理量)
fn do_work(id: usize) -> (usize, u64) {
    thread::sleep(Duration::from_millis((id as u64 + 1) * 50));
    (id, (id as u64 + 1) * 10)     // 模拟产出
}

fn main() {
    let started = Instant::now();
    // 共享进度：每秒由任意线程更新
    let progress = Arc::new(Mutex::new(0usize));
    let (tx, rx) = mpsc::channel();

    // 并发度 3：手动"游标式"分发
    let mut workers = vec![];
    let mut next = 0usize;
    while next < TASKS {
        let idx = next;
        next += 1;
        let progress = Arc::clone(&progress);
        let tx = tx.clone();
        workers.push(thread::spawn(move || {
            let (id, output) = do_work(idx);
            {
                let mut p = progress.lock().unwrap();
                *p += 1;
                println!("任务 {id} 完成（进度 {}/{}）", *p, TASKS);
            }
            tx.send((id, output)).unwrap();      // 结果走通道回收
        }));
    }
    drop(tx);                                     // 关闭发送端，for 循环才能结束

    // 主线程聚合结果（接收端）
    let mut results: Vec<(usize, u64)> = rx.iter().collect();
    results.sort_by_key(|&(id, _)| id);

    for (id, output) in results {
        println!("  => 任务 {id} 产出 {output}");
    }
    println!("总进度: {}", *progress.lock().unwrap());
    println!("并发执行总耗时: {:?}", started.elapsed());
}
```

**注意**：

- 任务用 `thread::spawn` 时需要 `'static`：上面通过 `move` 把 `idx`/`Arc`/`tx` 传入，栈上不再引用；
- `rx.iter()` 只有全部 `tx` 关闭才结束，所以 `drop(tx)` 不能漏；
- 共享进度用锁，结果回收用通道——两种并发模型在同一示例中分工明确。

**验收清单**：

1. 运行后输出 6 个任务结果且"总进度 = 6"；
2. 观察并行耗时显著小于串行（6 × 50~300ms 之和）;
3. 去掉 `drop(tx)` 看程序能否退出，解释原因；
4. 把"进度"换成 `AtomicUsize` 实现，体会与 `Mutex` 的差异。

**扩展练习**：给任务加上优先级队列（`BinaryHeap`），先处理高优先级任务；或改用 rayon 并行 map 重写（`into_par_iter`），比较两种写法的简洁度。

> 关键收获：Rust 的并发原语数量少而语义清晰——**消息传递优先、共享需加锁、锁内代码要短**。你写的并发代码能通过编译，就基本消除了数据竞争这一最难调试的 Bug 类别。下一章进入高并发服务端最常用的模型：异步 Rust。
