## 19.1 LLM 是什么

### 19.1.1 从语言模型到大语言模型

语言模型要回答一个问题：给定前文，接下来出现什么 token 的概率最高？它并不是在数据库里查找一段固定答案，而是根据上下文计算下一个 token 的概率分布，再逐步生成后续内容。

设输入 token 序列为 $x_1, x_2, \ldots, x_n$，自回归语言模型按下面的方式分解整段文本的概率：

$$
P(x_1, x_2, \ldots, x_n) = \prod_{t=1}^{n} P(x_t \mid x_1, x_2, \ldots, x_{t-1})
$$

“大”通常指模型参数、训练数据和计算规模较大，但参数更多不等于任何任务都更好。模型能力还取决于数据质量、训练方法、上下文长度、工具支持、推理成本和服务稳定性。

### 19.1.2 LLM、搜索引擎与传统程序

| 方式 | 核心机制 | 适合解决 | 主要限制 |
| --- | --- | --- | --- |
| 传统程序 | 明确规则和确定性计算 | 金额计算、权限判断、业务状态流转 | 规则需要人编写和维护 |
| 搜索引擎 | 索引并检索已有网页或文档 | 查找来源、获取最新信息 | 需要用户阅读和综合结果 |
| LLM | 根据上下文生成概率性输出 | 总结、改写、分类、问答、代码辅助 | 可能编造；结果不天然可验证 |

工程实践中常把它们组合：程序控制边界和确定性规则，搜索/RAG 提供可追溯资料，LLM 负责理解和生成。LLM 不应被当作权限系统、计算器或权威事实数据库。

### 19.1.3 Transformer 的直观图景

现代主流 LLM 通常基于 Transformer。理解应用不需要从矩阵推导开始，先抓住三个概念：

1. **Token 化**：文本被切分成 token（词片段、字符或符号），模型处理的是 token 序列，不是人类直觉里的“字数”。
2. **注意力（Attention）**：模型在处理当前位置时，按相关性利用上下文中的其他位置，形成上下文表示。
3. **逐 token 生成**：模型输出一个 token 后，把它追加到上下文，再预测下一个，直到结束标记、长度上限或停止条件。

可以把一次生成看成：

```text
提示词 -> tokenizer -> token 序列 -> Transformer 推理 -> 下一个 token 分布
       -> 采样一个 token -> 追加到序列 -> 重复 -> 解码为文本
```

模型内部的隐藏状态、注意力权重不是可靠的“思维过程说明”。解释回答时应看可验证的输入、引用和结果，而不是把生成文本误认为模型真实、完整的内部推理记录。

## 19.2 Token、上下文与生成边界

### 19.2.1 Token 不等于字符或单词

不同 tokenizer 对同一文本的切分可能不同。中文、代码、罕见专有名词和特殊符号的 token 数尤其不能凭字符数准确估算。API 计量通常关注输入 token 和输出 token，具体口径以服务商为准。

```python
text = "请总结这段 Python 代码的作用。"
print(len(text))  # 字符数，不是 token 数
```

生产应用需要使用服务商提供的 tokenizer 或计量接口估算成本；日志中可同时记录字符数和 API 返回的 token 用量，避免用字符数假装精确计费。

### 19.2.2 上下文窗口不是长期记忆

上下文窗口是单次请求可处理的 token 容量，通常包括系统指令、对话历史、用户输入、工具结果和模型输出预算。窗口再大也不意味着模型会永久记住先前会话：大多数 API 调用是无状态的，应用必须自行管理历史或持久化记忆。

对话历史不断增长时，可以采用：

- 只保留最近若干轮；
- 将旧对话压缩成摘要，并保留关键事实及其来源；
- 检索与当前问题相关的历史片段；
- 设置最大输入预算，超限时明确截断或拒绝，而不是静默丢失重要上下文。

### 19.2.3 模型知识的时效性

模型参数来自训练数据，不保证包含训练截止时间之后的事实，也不保证记住所有训练内容。需要最新或私有数据时，应通过搜索、数据库、RAG 或工具调用补充资料，并在回答中保留来源。RAG 的详细实现见第十一章。

## 19.3 模型怎样获得指令跟随能力

常见训练阶段可用下面的简化流程理解：

```text
大规模文本上的预训练
    -> 指令数据监督微调（SFT）
    -> 偏好对齐（例如 RLHF 或 DPO 等方法）
    -> 评测、安全测试与部署
```

- **预训练**：学习文本中的统计规律和语言模式，目标通常与预测后续 token 有关。
- **监督微调（SFT）**：用指令和示范答案训练模型，使其更会按任务格式作答。
- **偏好对齐**：利用人类或合成偏好，让输出更符合期望；不同模型采用的具体算法和数据各不相同。
- **推理（Inference）**：部署后根据输入生成输出。推理不是重新训练模型；把对话历史传入请求，也不会自动改变模型参数。

微调、提示词和 RAG 解决的问题不同：提示词改变当前请求的指令，上下文检索提供外部资料，微调改变模型参数以适配稳定的行为或格式需求。三者可以组合，但不应仅因“模型答错一次”就立刻选择微调。

## 19.4 生成参数：控制输出而不是赋予知识

### 19.4.1 Temperature 与随机性

采样参数会影响模型从候选 token 分布中选择结果的方式。较低 temperature 通常让输出更集中、更稳定；较高 temperature 通常增加变化。低 temperature 不代表事实必然正确，也不一定让输出完全确定。

不同模型和服务对参数支持、默认值、取值范围可能不同。调用前查看目标模型的 API 文档，不要假定所有参数都适用。

### 19.4.2 最大输出长度与停止条件

最大输出 token 数用于控制单次生成的上限，避免输出失控和预算超支。达到上限时答案可能被截断，因此需要检查响应的结束原因；不能仅凭拿到一段文本就认为任务完整。

### 19.4.3 Top-p 与参数调节原则

Top-p 会限制采样候选集合的累计概率范围。通常先固定一个采样控制参数，再通过小规模对照评测调整；同时调整 temperature、top-p 和多种惩罚参数，会让实验结果难以归因。参数改变的是输出分布，不会补充模型缺失的事实。

### 19.4.4 一次只回答一个可检验的问题

调参前定义目标指标，例如分类准确率、格式通过率或人工偏好分数。使用固定测试集比较配置，并记录模型版本、提示词版本、参数、日期和样本结果。不要用少数几个“看起来不错”的例子替代评测。

## 19.5 Python 调用：文本生成、流式与结构化输出

### 19.5.1 配置密钥并发起请求

```powershell
# Windows PowerShell：仅当前终端会话有效
$env:OPENAI_API_KEY = "你的密钥"
```

密钥不要硬编码进源码、Notebook 输出、日志或 Git 仓库。生产环境使用密钥管理服务或受控环境变量，并限制密钥权限与额度。

```python
# llm_basic.py
from openai import OpenAI

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o-mini",  # 替换为当前账号可用、且支持该接口的模型
    messages=[
        {"role": "system", "content": "你是一个严谨的 Python 学习助手。"},
        {"role": "user", "content": "用一句话解释 Python 的生成器。"},
    ],
    temperature=0.2,
)

message = response.choices[0].message
print(message.content)
print("输入 token:", response.usage.prompt_tokens)
print("输出 token:", response.usage.completion_tokens)
```

请求包含完整消息列表；模型不会自动保留上次调用的内容。若服务商或模型不支持某个参数，移除或按其文档调整。

### 19.5.2 多轮对话：应用显式保存历史

```python
from openai import OpenAI

client = OpenAI()
messages = [
    {"role": "system", "content": "你是 Python 助教，回答简洁。"},
]

for question in ["什么是迭代器？", "它和生成器有什么关系？"]:
    messages.append({"role": "user", "content": question})
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=messages,
        temperature=0.2,
    )
    answer = response.choices[0].message.content or ""
    messages.append({"role": "assistant", "content": answer})
    print("AI:", answer)
```

Web 服务中应按会话 ID 隔离历史，并为历史设置长度、权限和保留期限。不要把一个用户的对话列表共享给其他用户。

### 19.5.3 流式输出

```python
from openai import OpenAI

client = OpenAI()
stream = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[{"role": "user", "content": "列出三条编写可维护函数的建议。"}],
    stream=True,
)

for chunk in stream:
    delta = chunk.choices[0].delta.content or ""
    print(delta, end="", flush=True)
print()
```

流式输出可以更早呈现首批内容，但不一定减少模型总生成时间或 token 成本。服务端要处理断连、取消、超时和部分输出；流式文本未完成时不能提前当成最终结果执行。

### 19.5.4 结构化输出与本地校验

当下游需要稳定字段时，要求模型输出结构化数据，并使用 Pydantic 再做本地校验。模型生成的 JSON 仍是不可信输入，校验失败要走明确的错误路径。

```python
from openai import OpenAI
from pydantic import BaseModel, Field


class TicketSummary(BaseModel):
    category: str = Field(description="工单类别")
    priority: int = Field(ge=1, le=5)
    summary: str


client = OpenAI()
response = client.beta.chat.completions.parse(
    model="gpt-4o-mini",
    messages=[
        {"role": "system", "content": "提取工单信息；不确定时在摘要中说明。"},
        {"role": "user", "content": "支付页面一直报错，影响所有用户，急需处理。"},
    ],
    response_format=TicketSummary,
)

result = response.choices[0].message.parsed
if result is None:
    raise ValueError("模型没有返回有效的结构化结果")
print(result.model_dump())
```

结构化输出能降低格式解析成本，但不能保证字段语义正确、事实真实或业务动作安全。最终决策仍要由应用规则验证。

## 19.6 提示词设计：清晰约束，可验证输出

提示词（Prompt）是请求的一部分，不是代码层面的安全边界。把任务、上下文、约束和输出格式说清楚，通常比堆叠“你必须非常聪明”等修饰词更有效。

```text
角色：你是内部知识库的摘要助手。
任务：根据 <资料> 回答 <问题>，不要补充资料之外的事实。
输出：先给出不超过 3 句的结论，再列出支持结论的资料片段。
无法回答：明确回复“资料不足”，并说明缺少什么。

<资料>
...
</资料>

<问题>
...
</问题>
```

实用原则：

1. 一次只指定清晰的主要任务，复杂任务拆成可验证步骤；
2. 明确受众、长度、语气、输出格式和不能做的事；
3. 把用户输入和可信指令分隔，避免把引用文本误作指令；
4. 给出少量代表性示例时，覆盖正常、边界和拒答场景；
5. 对重要结论要求引用输入来源，并在应用侧检查引用是否真实存在；
6. 用一组固定样例做回归测试，提示词修改也按代码变更管理。

提示词注入是输入内容试图覆盖系统规则或诱导执行不安全操作的攻击方式。分隔符和指令声明有帮助，但不能单独防住攻击；权限校验、工具白名单、输出校验和人工确认必须由应用实施。

## 19.7 幻觉、验证与安全边界

### 19.7.1 为什么会产生幻觉

LLM 的核心目标是生成符合训练规律和上下文的后续文本，不是逐句查询事实数据库。它可能以流畅语气给出不存在的 API、引用或数据。提高模型规模或降低 temperature 都无法从原理上消除幻觉。

### 19.7.2 按风险设计验证

| 任务 | 推荐验证 |
| --- | --- |
| JSON / 字段抽取 | Schema 校验、枚举约束、缺失值处理 |
| 数学 / 金额 | 使用 Decimal 或确定性计算代码复核 |
| 数据库查询 / 写入 | 参数化查询、权限隔离、事务和业务规则检查 |
| 知识问答 | 检索可信来源、返回引用、检查引用与结论一致 |
| 对外发送 / 资金操作 | 最小权限、预览、用户确认、审计日志 |
| 代码生成 | 静态检查、测试、沙箱执行；禁止直接运行不可信代码 |

### 19.7.3 LLM 应用安全清单

- **密钥**：从受控配置读取，禁止回显；设置轮换、限额和最小权限。
- **个人信息**：发送前最小化数据；按组织政策处理同意、保留和删除。
- **提示词注入**：将检索内容视为不可信数据；检索到的文本不能自行授予工具权限。
- **工具授权**：由服务端执行身份认证和授权，不以模型声称“用户已授权”为依据。
- **输出处理**：按输出上下文做 HTML 转义、SQL 参数化和路径校验；不拼接执行模型输出。
- **拒答与升级**：定义高风险场景的拒答规则和人工处理路径。
- **日志**：记录模型、参数、耗时、用量和错误类型；避免写入密钥及不必要的敏感原文。

## 19.8 模型选型与成本延迟

不要只按排行榜选模型。用自己的代表性任务集比较质量、延迟、成本、上下文限制、结构化输出能力、工具调用、多模态支持、数据处理条款和服务可用性。

常见优化顺序：

1. 明确任务是否真的需要 LLM；简单规则和 SQL 可能更便宜、更可靠；
2. 缩短不必要的输入，限制历史和输出长度；
3. 使用较小模型处理简单任务，仅将难题路由到更强模型；
4. 对稳定、可复用的结果做缓存，注意用户隔离和缓存失效；
5. 并行执行互不依赖的请求，并设置超时、重试上限和速率限制；
6. 跟踪输入/输出用量、错误率、首 token 延迟及端到端 p95 延迟。

估算单次请求成本时，可按服务商公布的输入和输出单价计算：

$$
\text{成本} \approx \text{输入 token 数} \times \text{输入单价} + \text{输出 token 数} \times \text{输出单价}
$$

实际账单可能还包括缓存、工具、图像/音频等计费项，应以服务商计费说明为准。不要在文档中硬编码很快会变化的模型价格。

## 19.9 自己开发 LLM：技术栈与现实路线

“自己开发 LLM”可能指完全不同的工作，先区分目标，避免把调用 API、微调模型和从零训练混为一谈：

| 目标 | 实际在做什么 | 个人/小团队可行性 |
| --- | --- | --- |
| 开发 LLM 应用 | 调用已有模型 API，编写提示词、RAG、工具与业务逻辑 | 最容易起步，不需要训练 GPU |
| 部署开源模型 | 下载已有权重，在本机或服务器上推理并提供接口 | 可行，模型大小受显存、内存和吞吐要求限制 |
| 微调已有模型 | 用领域样本更新部分或全部权重，常见为 LoRA/QLoRA | 小模型和参数高效微调可在单机 GPU 实践 |
| 继续预训练 | 从已有模型继续用领域语料做语言模型训练 | 需要较多高质量语料、GPU 和训练经验 |
| 从零预训练基础模型 | 准备大规模语料、训练 tokenizer 和全部模型参数 | 教学规模可行；有竞争力的大模型通常需要团队级数据和算力 |

如果目标是做一个能服务用户的产品，通常从应用开发或部署开源模型开始；如果目标是掌握训练，可先微调小模型，再训练一个教学用迷你 Transformer。**从零训练一个能运行的模型**和**训练出能力强、可泛化的大模型**是完全不同的难度。

### 19.9.1 需要掌握的技术

| 技术领域 | 需要理解的内容 | 常见工具/方向 |
| --- | --- | --- |
| Python 与 Linux | Python 工程、命令行、进程、文件、Git、环境和依赖管理 | Python、Linux、Git、虚拟环境 |
| 数学基础 | 向量/矩阵、矩阵乘法、导数与链式法则、概率分布、统计抽样 | 线性代数、微积分、概率统计 |
| 深度学习 | 张量、自动微分、损失函数、反向传播、优化器、训练循环 | PyTorch；先理解训练过程再依赖高层封装 |
| Transformer | Tokenizer、Embedding、位置编码、Attention、残差连接、归一化、因果掩码 | Hugging Face Transformers；实现小型 GPT 加深理解 |
| 数据工程 | 获取有许可的数据、清洗去重、质量过滤、隐私处理、切分训练/验证集 | Datasets、Parquet/JSONL、对象存储、数据校验脚本 |
| GPU 与分布式 | 显存、吞吐、混合精度、梯度累积、检查点、数据并行与多卡通信 | CUDA、bf16/fp16、DDP、FSDP 或 DeepSpeed、NCCL |
| 微调与对齐 | 指令数据、SFT、LoRA/QLoRA、偏好数据与 DPO 的适用场景 | PEFT、TRL；先从参数高效微调开始 |
| 推理与部署 | 权重量化、KV Cache、批处理、并发、流式生成、服务监控 | Transformers、vLLM、llama.cpp、容器与 API 服务 |
| 评测与安全 | 任务指标、基准集、人工抽查、数据污染、偏见/隐私/越狱测试 | 固定评测集、实验记录、红队测试和回归测试 |

工具只是实现手段，不等于掌握原理。至少要能解释：模型输入如何变成张量、损失如何产生梯度、参数怎样更新、验证集如何发现过拟合，以及生成时上下文和 KV Cache 如何影响资源消耗。

### 19.9.2 训练过程的关键工程点

一个简化的自回归预训练流水线如下：

```text
合法且高质量的原始语料
    -> 清洗 / 去重 / 隐私处理 / 质量过滤
    -> tokenizer 编码与样本打包
    -> Transformer 前向计算 next-token loss
    -> 反向传播与优化器更新参数
    -> 定期保存 checkpoint 并在验证集评估
    -> 训练结束后做指令微调、对齐、评测与部署
```

工程中还要处理训练中断恢复、数据重复或泄漏、梯度异常、GPU 利用率、通信瓶颈、实验可复现和模型权重版本管理。训练集 loss 持续下降不代表模型就有用：要监控验证集，并使用与目标任务匹配的独立评测。

### 19.9.3 硬件与成本预期

模型权重本身的显存下限可粗略估算为：参数量 × 每个参数的字节数。例如，10 亿参数以 BF16/FP16 存储，单是权重约需 2 GB。这个数字**不是实际运行所需显存**：推理还要为 KV Cache、临时张量和运行时留空间；全量训练还要容纳梯度、优化器状态和激活值，需求会高出许多。具体用量受序列长度、批量、优化器和框架实现影响。

降低门槛的做法包括：从较小的开源模型开始、使用 LoRA/QLoRA、缩短上下文、降低批量、梯度累积、梯度检查点和量化推理。它们能节省资源，但会带来速度、精度或能力上的权衡；量化一个模型也不等于训练了一个新模型。

### 19.9.4 建议的学习路线

1. **先跑推理**：用 Transformers 或 llama.cpp 加载一个许可合适的小型开源模型，观察 tokenizer、输入长度、生成速度和显存占用；
2. **实现迷你 GPT**：用 PyTorch 在小语料上训练字符级或小词表模型，跑通数据批次、因果 Attention、交叉熵、反向传播和 checkpoint；把它当教学实验，不期待通用能力；
3. **微调现有小模型**：准备少量高质量、合法的指令样本，用 Transformers + PEFT/LoRA 完成 SFT，并与原模型在同一评测集上比较；
4. **做可靠推理服务**：加入量化、请求并发、超时、日志、权限和负载测试，比较本地推理与托管 API；
5. **再学多卡训练**：掌握数据并行、混合精度、检查点和故障恢复，再评估是否真的需要继续预训练或从零训练。

推荐的个人实践边界是“教学模型从零训练 + 真实开源模型微调/部署”。要训练有竞争力的基础模型，还需要规模化数据治理、多卡/多机算力、分布式训练和持续评测能力；不能仅靠一台消费级 GPU 和一份爬来的文本语料解决。

## 19.10 实战：构建带验证的工单摘要器

### 需求

输入一段工单文本，输出类别、优先级和摘要。优先级只能为 1~5；调用失败、解析失败或结果不完整时返回可识别错误，不静默伪造成功。

```python
from openai import OpenAI
from pydantic import BaseModel, Field, ValidationError


class TicketSummary(BaseModel):
    category: str
    priority: int = Field(ge=1, le=5)
    summary: str = Field(min_length=1, max_length=300)


def summarize_ticket(text: str) -> TicketSummary:
    if not text.strip():
        raise ValueError("工单内容不能为空")

    client = OpenAI()
    response = client.beta.chat.completions.parse(
        model="gpt-4o-mini",
        messages=[
            {
                "role": "system",
                "content": (
                    "你负责提取工单信息。只根据工单内容分类和总结；"
                    "优先级为 1 到 5，5 表示最紧急。"
                ),
            },
            {"role": "user", "content": text},
        ],
        response_format=TicketSummary,
    )

    result = response.choices[0].message.parsed
    if result is None:
        raise ValueError("模型未返回有效工单摘要")
    return result


try:
    ticket = summarize_ticket("支付页面报错，所有用户无法付款，请立即处理。")
    print(ticket.model_dump())
except (ValueError, ValidationError) as exc:
    print(f"输入或输出校验失败：{exc}")
except Exception as exc:
    # 生产环境应区分超时、限流、认证失败等错误类型并分别处理。
    print(f"模型服务调用失败：{type(exc).__name__}")
```

这只是最小示例。生产版本还需要把 `OpenAI()` 放在应用生命周期中复用，加入网络超时、限流退避、请求 ID、敏感信息脱敏、费用上限和人工复核；不要无限重试。

### 验收标准

- 空输入被本地拒绝，不产生模型请求；
- 成功结果通过 Pydantic 校验，优先级在 1~5 之间；
- API 不可用或结构化输出缺失时返回明确失败；
- 测试使用 mock 替代真实 API，不在 CI 中消耗真实额度；
- 记录模型名、耗时和 token 用量，但不记录密钥。

## 19.11 本章小结与练习

本章建立了 LLM 应用的基本判断框架：模型按 token 逐步生成概率性文本；上下文窗口不是持久记忆；提示词和生成参数不会自动提供事实；输出需要程序验证；权限和安全边界必须留在应用侧。

练习：

1. 将工单摘要器改成批量输入，统计每条任务的延迟和 token 用量；
2. 为 API 调用加入超时和有限重试，并区分认证错误、限流和服务端错误；
3. 准备 20 条固定工单样例，对比两种提示词的分类准确率和格式通过率；
4. 设计一个“资料不足时拒答”的问答提示词，并检查模型引用是否真的出现在给定资料中；
5. 写一份模型选型表，按质量、成本、延迟、隐私和部署方式比较至少两种方案。
