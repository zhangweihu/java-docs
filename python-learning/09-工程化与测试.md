## 9.1 工程化全景：从"脚本"到"项目"

写脚本（前八章）和写项目（本章）的区别：

| 维度 | 脚本 | 工程项目 |
| --- | --- | --- |
| 代码规范 | 个人习惯 | **PEP 8 + lint 工具强制** |
| 测试 | 偶尔手点验证 | **自动化单测 + 覆盖率**，CI 里必跑 |
| 类型 | 随意 | **mypy 静态检查**，提前暴露 bug |
| 依赖 | 全局 pip install | **虚拟环境 + 锁定版本**，可复现 |
| 交付 | 拷贝 .py 文件 | **打包成库/服务**，pip 安装即用 |
| 质量保障 | 无 | **CI/CD 流水线**：lint → 测试 → 构建 → 部署 |

一个专业 Python 项目标准目录结构：

```
my_project/
├── pyproject.toml          # 工程元数据 + 依赖 + 工具配置（核心）
├── README.md
├── .gitignore
├── src/
│   └── my_project/         # 源码包
│       ├── __init__.py
│       ├── core.py
│       └── utils.py
├── tests/                  # 测试目录（pytest 约定）
│   ├── test_core.py
│   └── conftest.py         # 共享 fixture
├── .github/
│   └── workflows/ci.yml    # CI 流水线
└── requirements-dev.txt    # 开发依赖（lint/测试工具）
```

### 9.2.2 依赖锁定：requirements 与 pip freeze

```bash

pip freeze > requirements.txt
# 内容形如：requests==2.32.3、fastapi==0.115.0
```

**依赖分组**（生产依赖 vs 开发依赖）：

```bash

pip freeze > requirements-dev.txt                                # 开发全量依赖
```

> **对比 Java**：`requirements.txt` ≈ pom.xml 的依赖清单（但更简单）；`venv` ≈ Maven 依赖隔离（按项目而非全局）。现代 Python 推荐用 `pyproject.toml` 替代 requirements（见 9.6）。

## 9.3 PEP 8 代码规范：ruff + black

### 9.3.1 PEP 8 核心规则（写 Python 的"交规"）

| 规则 | 要求 | 反例 → 正例 |
| --- | --- | --- |
| 缩进 | 4 空格（**不用 Tab**） | `x = 1` 前 4 空格 |
| 行宽 | ≤ 88 字符（黑线） | 超长拆行 |
| 命名 | 变量/函数 `snake_case`；类 `CamelCase`；常量 `ALL_CAPS` | `userName` → `user_name`；`UserInfo` 类 |
| 空行 | 函数/类之间空 2 行；类内方法空 1 行 | 连续函数间空 2 行 |
| 导入 | 标准库 → 第三方 → 本地，分组空行 | `import os` 在 `import requests` 前 |
| 空格 | 运算符两侧各 1 空格；逗号后 1 空格 | `a=1+2` → `a = 1 + 2` |
| 引号 | 统一单引号或双引号（ruff 默认双引号） | 混用 |
| 注释 | `# 后跟一个空格` | `#注释` |

```python
# 规范示例（对照上表检查）
import os
import sys

import requests

from my_project import utils

MAX_RETRIES = 3          # 常量大写

class UserService:       # 类 CamelCase
    def get_user(self, user_id: int) -> dict:    # 函数 snake_case + 类型注解
        return {"id": user_id}
```

### 9.3.2 ruff：新一代 lint + 格式化（对标 Checkstyle + Spotless）

```bash
pip install ruff

ruff check --fix src          # 自动修复（大部分规则可自动改）
ruff format src               # 代码格式化（对标 Google Java Format）
```

```bash

# src/core.py:25:9: N802 function name should be lowercase
```

**在 pyproject.toml 里配置 ruff**：

```toml
[tool.ruff]
line-length = 88
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "W", "N", "I", "UP"]   # E=错误 F=未使用 W=警告 N=命名 I=导入排序
```

> **对比 Java**：ruff ≈ Checkstyle + Spotless/Google Java Format 合体；black 只负责格式化（对标 google-java-format）。

## 9.5 pytest：Python 测试框架全解（对标 JUnit）

### 9.5.1 测试目录与最小用例

```python
# my_project/core.py —— 被测代码
def add(a: int, b: int) -> int:
    return a + b

def divide(a: float, b: float) -> float:
    if b == 0:
        raise ValueError("除数不能为 0")
    return a / b

def parse_price(text: str) -> float:
    return float(text.replace("¥", "").replace(",", ""))
```

```python
# tests/test_core.py —— 测试代码（文件名必须以 test_ 开头或 _test 结尾）
import pytest
from my_project.core import add, divide, parse_price

def test_add():
    assert add(1, 2) == 3                      # 断言：对标 JUnit 的 assertEquals
    assert add(-1, 1) == 0

def test_add_commutative():
    assert add(2, 3) == add(3, 2)

def test_divide_zero_raises():
    with pytest.raises(ValueError):            # 断言抛异常（对标 assertThrows）
        divide(1, 0)

def test_parse_price():
    assert parse_price("¥1,299.50") == 1299.5
```

```bash
cd 项目根目录
pytest                        # 自动发现并运行所有 test_*.py
pytest -v                     # 详细输出（每个用例一行）
pytest tests/test_core.py     # 只跑指定文件
pytest -k "add"               # 按名称过滤
pytest -x                     # 失败即停（调试用）
```

**运行机制对比 JUnit**：

| pytest | JUnit |
| --- | --- |
| `def test_xxx():` | `@Test void xxx()` |
| `assert 表达式` | `assertEquals/assertTrue` |
| `with pytest.raises(Exception)` | `assertThrows` |
| `@pytest.fixture` | `@BeforeEach/@AfterEach` + `@Autowired` |
| `@pytest.mark.parametrize` | `@ParameterizedTest` + `@ValueSource` |
| `conftest.py` 共享 fixture | `@TestConfiguration` / 基类 |
| `monkeypatch` | Mockito 的 `when/thenReturn` |

### 9.5.2 fixture：测试准备与清理（对标 @BeforeEach）

```python
# conftest.py —— 所有测试文件共享的 fixture
import pytest

@pytest.fixture
def sample_user() -> dict:
    """每个用例执行前自动调用，执行后自动清理"""
    user = {"name": "张三", "age": 30}
    yield user                 # yield 前 = 准备；yield 后 = 清理
    # 清理逻辑（如关闭数据库连接、删除临时文件）
```

```python
# tests/test_user.py
def test_user_name(sample_user):               # 参数名 = fixture 名，自动注入
    assert sample_user["name"] == "张三"

def test_user_age(sample_user):
    assert sample_user["age"] == 30
```

**fixture 的作用域**（默认每次用例重新执行）：

```python
@pytest.fixture(scope="session")    # 整个测试会话只建一次（对标 @BeforeAll）
@pytest.fixture(scope="module")     # 每个模块一次（对标 @BeforeAll per class）
@pytest.fixture(scope="function")   # 每个用例一次（默认，对标 @BeforeEach）
```

### 9.5.3 parametrize：参数化测试（对标 @ParameterizedTest）

```python
import pytest
from my_project.core import parse_price

@pytest.mark.parametrize("text, expected", [
    ("¥99", 99.0),
    ("¥1,299.50", 1299.5),
    ("1 299,50", None),      # 故意留一个错误用例
])
def test_parse_price(text, expected):
    result = parse_price(text)
    assert result == expected
```

**参数化运行结果**：每个参数组合显示为独立用例（`test_parse_price[¥99-99.0]`），失败互不影响。

### 9.5.4 monkeypatch 与 mock：模拟外部依赖（对标 Mockito）

```python
# my_project/api.py
import requests

def fetch_price(symbol: str) -> float:
    resp = requests.get(f"https://api.example.com/price/{symbol}", timeout=5)
    resp.raise_for_status()
    return resp.json()["price"]
```

```python
# tests/test_api.py —— 不真正请求网络（测试必须快、可离线、可重复）
def test_fetch_price(monkeypatch):
    class FakeResponse:
        def raise_for_status(self): pass
        def json(self): return {"price": 88.8}

    def fake_get(url, timeout=5):
        assert "price/AAPL" in url          # 还可以断言请求 URL 对不对
        return FakeResponse()

    monkeypatch.setattr(requests, "get", fake_get)   # 替换 requests.get
    from my_project.api import fetch_price
    assert fetch_price("AAPL") == 88.8
```

> **monkeypatch** 是对标 Mockito 的核心利器：`setattr` 替换函数/属性，用后自动还原（JUnit 的 `mock()` + `when()`）。

## 9.7 CI/CD 流水线：GitHub Actions / GitLab CI

### 9.7.1 为什么需要 CI

每次提交代码，自动完成：**lint 检查 → mypy 类型检查 → pytest 测试 → 覆盖率 → 打包**。全绿才允许合并——把质量关卡自动化（对标 Java 的 GitLab CI + Jenkins 管线）。

### 9.7.2 GitHub Actions（.github/workflows/ci.yml）

```yaml
name: Python CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: 安装依赖
        run: |
          pip install -e ".[dev]"

      - name: 代码规范检查（ruff）
        run: ruff check src tests

      - name: 类型检查（mypy）
        run: mypy src

      - name: 单元测试 + 覆盖率（pytest）
        run: pytest --cov=src --cov-fail-under=80
        # --cov-fail-under=80：覆盖率低于 80% 直接失败（质量红线）
```

### 9.7.3 GitLab CI（.gitlab-ci.yml，对标 Java 团队的 GitLab 流程）

```yaml
stages: [lint, test, build]

lint:
  stage: lint
  image: python:3.12
  script:
    - pip install ruff mypy
    - ruff check src tests
    - mypy src

test:
  stage: test
  image: python:3.12

  stage: build
  image: python:3.12

  artifacts:

```

### 9.7.4 部署环节（CD）

```yaml
deploy:
  stage: deploy
  image: python:3.12
  only:
    - main                # 仅主干分支触发
```

## 9.8 实战：把一个工具库工程化（综合实战）

把 8.7 章"日志清理"的核心逻辑重构成一个**可测试、可发布、有 CI** 的工程：

```python
# src/log_cleaner/core.py —— 核心逻辑（纯函数，便于测试）
"""日志清理核心：判断过期、归档清理（不依赖 IO 之外的任何东西）"""
import zipfile
from datetime import datetime, timedelta
from pathlib import Path


def is_old(path: Path, days: int) -> bool:
    """文件修改时间是否超过 days 天"""
    mtime = datetime.fromtimestamp(path.stat().st_mtime)
    return mtime < datetime.now() - timedelta(days=days)


def archive_old_logs(log_dir: Path, days: int, dry_run: bool = False) -> int:
    """归档并清理超过 N 天的 .log 文件，返回处理数量。dry_run 只统计不执行。"""
    archive_dir = log_dir / "archive"
    count = 0
    for f in log_dir.glob("*.log"):
        if not is_old(f, days):
            continue
        if dry_run:
            count += 1
            continue
        archive_dir.mkdir(exist_ok=True)
        zpath = archive_dir / f"{f.stem}_{f.stat().st_mtime:.0f}.zip"
        with zipfile.ZipFile(zpath, "w", zipfile.ZIP_DEFLATED) as zf:
            zf.write(f, arcname=f.name)
        f.unlink()
        count += 1
    return count
```

```python
# tests/test_core.py —— 用 tmp_path fixture 构造临时目录测试（pytest 内置）
import pytest
from log_cleaner.core import archive_old_logs, is_old


def _create_log(tmp_path, name, mtime_days_ago):
    """创建修改时间是 N 天前的日志文件"""
    f = tmp_path / name
    f.write_text("log content", encoding="utf-8")
    old = datetime.now() - timedelta(days=mtime_days_ago)
    import os
    os.utime(f, (old.timestamp(), old.timestamp()))
    return f


def test_archive_old_logs_archives_only_old(tmp_path):
    _create_log(tmp_path, "old.log", 10)      # 10 天前 → 应清理
    _create_log(tmp_path, "new.log", 1)       # 1 天前  → 应保留

    n = archive_old_logs(tmp_path, days=7)

    assert n == 1                                        # 只处理了 1 个
    assert not (tmp_path / "old.log").exists()           # 旧文件已删
    assert (tmp_path / "new.log").exists()               # 新文件保留
    assert (tmp_path / "archive" / "old.log.zip").exists()   # 归档文件已生成

def test_dry_run_does_not_delete(tmp_path):
    _create_log(tmp_path, "old.log", 10)

    n = archive_old_logs(tmp_path, days=7, dry_run=True)

    assert n == 1
    assert (tmp_path / "old.log").exists()    # dry-run 不删除


def test_is_old_boundary(tmp_path):
    f = _create_log(tmp_path, "x.log", 7)     # 正好 7 天
    assert is_old(f, 7) == False              # 边界：等于 N 天不算过期
```

```bash
# 跑通整个工程化流程
pip install -e ".[dev]"        # 可编辑安装 + 开发依赖
ruff check src tests           # ① 规范检查
ruff format src tests          # ② 自动格式化
mypy src                       # ③ 类型检查
pytest --cov=src --cov-fail-under=80   # ④ 测试 + 覆盖率红线
python -m build                # ⑤ 构建产物
```

**这个实战演示了工程化的完整闭环**：纯函数核心（易测试）+ pytest（含 tmp_path/边界用例）+ lint/mypy + 覆盖率 + 打包——配合 9.7 的 CI 配置，就是"代码一推，质量自动把关"的现代 Python 交付流水线。

## 9.9 体系总复习与进阶路线

### 练习题（动手做）

5. 运行 `pytest --cov` 找出你项目里覆盖最差的模块，补测试到 80%；
6. 用 ruff 检查你的前八章代码，修复所有报告的问题；
7. 运行 mypy 检查第六章 FastAPI 项目，修复类型错误；
8. 为你的项目写 pyproject.toml，`pip install -e .` 后命令行可用；
9. 在 GitHub 建一个仓库，配置 9.7 的 CI，提交代码观察流水线跑通。

### 面试高频题

| 问题 | 回答要点 |
| --- | --- |
| venv 有什么用？ | 项目级依赖隔离，避免全局污染与版本冲突；激活后 pip 只装进本项目 |
| requirements.txt 怎么用？ | pip freeze 生成、pip install -r 复现；生产/开发依赖分组管理 |
| PEP 8 要点？ | 4 空格缩进、snake_case 变量/CamelCase 类、行宽 88、导入分组 |
| ruff 和 black 区别？ | ruff 是 lint（发现问题）+ 可格式化；black 是纯格式化器（风格统一） |
| mypy 干什么的？ | 静态类型检查，运行前抓类型错误；配合类型注解在 CI 里执行 |
| pytest 怎么发现测试？ | 默认找 test_*.py / *_test.py 文件，文件里 test_ 开头的函数 |
| fixture 是什么？ | 测试准备/清理逻辑复用；yield 前准备、后清理；scope 控制生命周期 |
| 参数化测试怎么写？ | @pytest.mark.parametrize("参数名", [值列表])，每个组合独立成用例 |
| 不联网怎么测 HTTP？ | monkeypatch 替换 requests.get / httpx；或 pytest-httpx/mock 库 |
| 覆盖率怎么算/达标？ | pytest --cov；--cov-fail-under=80 设红线；核心模块 ≥80% |
| pyproject.toml 有什么用？ | 项目元数据 + 依赖 + 工具配置（ruff/mypy/pytest 统一读它）；对标 pom.xml |
| pip install -e 是什么？ | 可编辑安装，改源码即时生效，开发模式标配 |
| CI 里通常跑哪些步骤？ | lint（ruff）→ 类型（mypy）→ 测试+覆盖率（pytest）→ 构建（build） |
| CI 和 CD 区别？ | CI 提交即验证；CD 验证通过自动发布/部署 |
| Python 工程化和 Java 对应关系？ | venv≈依赖隔离、pyproject.toml≈pom.xml、pytest≈JUnit、ruff≈Checkstyle、twine≈mvn deploy |
